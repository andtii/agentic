# @agentic/daemon

`agentic-daemon` — the machine daemon (architecture §5b). It pairs a machine to a workspace once, keeps one reconnecting WebSocket to the platform, reports the machine's execution environments, serves runtime sessions over that socket and bridges platform tool calls. Node ≥ 22.12 (the one-line installer downloads it when missing); Windows, macOS and Linux, each with a background service (#343).

## Use

```sh
agentic-daemon pair <code> --url https://agentic.example [--name my-desktop] [--allow-root C:\src]
agentic-daemon env add --name Work --root C:\src\work [--root …] [--concurrency 2] [--account me@work.example]
agentic-daemon env login env_work
agentic-daemon harness list | install <runtime>… | update [<runtime>…] | rm <runtime> | select <runtime>…|none
agentic-daemon policy show | allow-root <dir> | deny-root <dir> | off | lock | unlock
agentic-daemon doctor
agentic-daemon run [--verbose] [--quota-probe on|off] [--quota-poll-ms <ms>] [--telemetry on|off]
agentic-daemon open [path] [--env <id>] [--no-browser]
agentic-daemon launcher install | remove | show
agentic-daemon update [--channel stable|latest] [--version daemon-v<semver>] [--check] [--now]
node <install root>/supervisor/supervise.mjs --root <install root> [--log <file>] [--daemon <dir>]   # what the service runs, not a subcommand
```

- **env add | list | rm | login** edit `environments.json` so nobody writes it by hand (`src/env-store.ts`, `src/env-cli.ts`). `add` takes `--name` and one or more `--root`, plus `--runtime` (default `claude-code`; it must be one this daemon has a driver for), `--id` (default `env_<name>`), `--concurrency`, `--account`, `--profile-dir`, `--allow-bypass` (lets a chat member run the environment in `bypassPermissions`, every tool unasked — #450, #355); with `--id <id> --replace` it changes an environment in place, keeping its profile and, unless the flag is given again, its bypass allowance. Each environment gets its own profile directory, `<config dir>/profiles/<id>`, and a directory another environment already uses is refused — two environments never share an account. The file is written atomically (temp + rename) and owner-only, like the credentials. `rm <id>` leaves the profile directory, which holds the sign-in. `login <id>` runs the runtime's own sign-in with that profile and the parent's account variables removed, the same rule sessions are opened under:
  - Claude Code runs `claude /login` with `CLAUDE_CONFIG_DIR`, removing `CLAUDE_CONFIG_DIR` / `ANTHROPIC_*`.
  - Copilot CLI runs `copilot login` with `COPILOT_HOME`, removing `GH_TOKEN` / `GITHUB_TOKEN` / `COPILOT_GITHUB_TOKEN`.
  - Codex runs `codex login` with `CODEX_HOME`, removing `OPENAI_*`.

  Claude Code and Codex sign in with the executable of the runtime's installed harness (below) — the one its sessions run; without one, the CLI on `PATH`. Copilot's harness is a runtime, not a CLI, so it always uses `copilot` on `PATH`. `env add` warns when the runtime has no harness.

  `--cli <path>` names another CLI; `--claude <path>` still works for Claude Code.
- **launcher install | remove | show** (#354) writes the `agentic-daemon` command itself: a launcher (`~/.agentic/bin/agentic-daemon`, `%LOCALAPPDATA%\agentic\bin\agentic-daemon.cmd`) that hard-codes the Node and the install folder the install resolved, so it runs where no Node is on `PATH`. The install scripts call it, and it makes the command reachable in the least invasive way that works: its folder already on `PATH` → nothing; `~/.local/bin` or `~/bin` on `PATH` → a symlink; otherwise a fenced block in the shell profile `$SHELL` names, or the **user** `PATH` on Windows (through `[Environment]::SetEnvironmentVariable`, never `setx`). `--no-profile` writes the launcher and changes no `PATH`; `--node` / `--entry` / `--bin-dir` override what is otherwise taken from the running process. Every step is idempotent, and it takes a new terminal. `show` prints where it is, what it runs and what to add to `PATH`; `remove` (the uninstall scripts call it) takes the launcher, the symlink and the profile block or `PATH` entry back out.
- **pair** presents the 6-character code from the Machines page to `POST /auth/pair` and stores the machine token. Case, spaces and dashes in the code are ignored. Each `--allow-root <dir>` (repeatable) lets the web add environments inside `<dir>` (below); every folder is checked before the code is spent.
- **policy show | allow-root | deny-root | off | lock | unlock** edit `policy.json`, the policy for web-managed environments (#238, #355, below). Since #355 the platform sets it too (`policy.request`); a command here says `source: local` and drops what the web asked for, and `lock` makes the file local-only again until `unlock` — every `policy.request` is refused `policy-locked` meanwhile. `show` says who set it and whether it is locked.
- **harness list | install | update | rm** (#369, `src/harness-cli.ts`) manage the runtime harnesses: each runtime's native build (the Claude Code executable, the Copilot runtime, the Codex executable), which the daemon zip does not carry. They live in `<install root>/harnesses/<runtime>/<version>/` with `current.json` naming the one in use (`src/harness.ts`). `install <runtime>…` downloads the build the release manifest names for this platform, checks its sha256 and the unpacked tree against the package's own manifest, and switches `current.json`. The manifest is the release this daemon came from (a stable build), else the `latest` channel's; `--version <semver>` reads `daemon-v<semver>`, `--channel` (or `AGENTIC_CHANNEL`) a channel, `--manifest <url>` any one, and `AGENTIC_RELEASES` another releases URL. `update` does the same for the installed ones when the release moved on. `rm` is refused while an environment runs on the runtime. A running daemon uses a version installed here after its next start, and it removes the versions it no longer uses when it starts. **Selection:** `selection.json` in the store lists the harnesses the machine wants. `install` adds to it, `rm` takes out, and `select <runtime>…|none` replaces it (the installers write `AGENTIC_HARNESSES` there). A daemon that starts under an install root installs any selected harness it lacks from its own channel's release, in the background, and updates one it has in the store that is not the version its build pins (#600) — draining that runtime's turns first, as `harness update` from the Machine page does — so a daemon update carries the pinned harness with it. This is how a machine updated from a build that bundled the runtimes gets them back; with no selection file, all three are selected. A failure is logged, shown by `doctor`, and retried on the next start. From the platform, `harness.request` does the same live (below).
- **doctor** checks the pairing, `environments.json`, a driver per runtime, the working roots, and whatever each runtime driver checks (profile isolation, auth per profile — EXE-07). It also names each runtime's harness: installed (and where), broken, or missing, with the install command. For a missing one it notes a `claude` / `copilot` / `codex` on `PATH`, which the daemon never runs. Exit 1 on any error; having no environments yet is a warning. The token is never printed.
- **open** (#336) starts a chat from the repo you stand in: it resolves `path` (default: the current directory) against every environment's working roots with the same check folder requests use (lexically, then with links resolved), reads the repo's `origin` from its git config (a worktree's through its `commondir`), prints `https://<platform>/chats/new?env=<id>&path=<folder>[&origin=<url>]` and opens it in the browser (`start` / `open` / `xdg-open`). The web prefills New chat with that folder and the project whose git feature names that origin, or offers to create one. Outside every root: exit 1 with the roots listed; under the roots of several environments: exit 2 until `--env <id>` picks one; `--no-browser` only prints the link (a headless box). No daemon frame is involved and the daemon need not be running — only paired, with `environments.json` in place.
- **run** connects and serves until SIGINT / SIGTERM. Logs are JSON lines on stderr; `--verbose` adds debug lines. A missing `environments.json` is zero environments — the machine connects and reports none. While running, the daemon watches the config directory: an `env add` / `env rm` or a hand edit is re-read once it settles (250 ms) and announced with an `env` frame, no restart; an edit that does not validate is logged and ignored, the running environments stay. Environments that are not signed in are inspected again every 30 s (`DaemonOptions.reinspectMs`), so a sign-in shows up on the platform by itself.
- **update** (#364) checks for and applies a new daemon release: it reads the release manifest the installers read (`--channel stable|latest`, default this build's channel; `--version daemon-v<semver>` pins one; `AGENTIC_RELEASES` points at another releases URL), prints what is installed and what is available, and with `--check` stops there. Otherwise it downloads this machine's zip, checks its sha256, stages it as `<install root>/daemon.staged` and asks the running daemon to restart onto it: once no turn is running (up to 10 minutes; `--now` at once). It waits until the new version is up, or says the supervisor rolled it back. It needs the background service's supervisor; without `state/supervisor.json` it says to reinstall with the one-line installer. See [Updates](#updates).
- **Usage limits** (#271): the daemon reports each environment's provider limits as `quota` frames: what `claude` → `/usage` shows, Copilot's monthly premium requests, and Codex's 5-hour and weekly windows. Two sources feed them:
  - **Passive:** every rate-limit event in a live session updates the window it names at once.
  - **Probe:** unless `--quota-probe off`, it reads every account right after connecting, idle environments every 5 min (`--quota-poll-ms`, 0 turns the poll off), and each environment 30 s after a turn ends. One probe runs at a time. No probe makes a model call. For Claude Code it starts Claude Code without a prompt and asks for its usage. For Copilot CLI it calls `account.getQuota` on the environment's runtime, the same process its sessions use. For Codex it opens a short-lived `codex app-server` and calls `account/rateLimits/read`.

  A snapshot equal to the last one sent is not sent again, except every 15 min, so the platform can tell fresh from stale. Only percentages, reset times and the plan name leave the machine; credentials and profile paths never do.
- **Telemetry** (#400): with every heartbeat (30 s) the daemon reports what its sessions cost the machine as a `telemetry` frame — CPU and resident memory per session, per environment, for the daemon itself, and the machine's own totals. It reads the process table once (`ps` on macOS and Linux, `Get-CimInstance Win32_Process` through PowerShell on Windows; `vm_stat` on macOS for the memory in use, since free pages alone would read a Mac as always full) and charges each runtime process and everything under it to its session: a dev server the agent started is that session's cost. Claude Code keeps one process per session, so its sessions are attributed; Codex keeps one app-server per environment, so its environments are and its sessions read unknown; Copilot's SDK starts its own runtime, so both read unknown — never zero. CPU is measured between two samples, so the first one has none. `--telemetry off` sends a `not-reported` snapshot instead. Nothing here ends or throttles a session: the platform warns on memory (a session over 2 GiB, a machine over 90 %), and that is all.
- **--version** (or `version`) prints `agentic-daemon <version> (<commit>, protocol <n>, <channel>)` — `DAEMON_VERSION`, stamped at build: `<semver>` for a `daemon-v<semver>` tag (`stable`), `<package version>-main.<commit unix seconds>.<sha7>` for a `main` build (`latest`), `0.0.0-dev` from source — and exits 0. `hello.daemonVersion` and `hello.build` carry the same; the installer test and the staged-update check use it.
- **supervise** is not a subcommand: the background service runs `node <install root>/supervisor/supervise.mjs --root <install root>` (`scripts/supervise.mjs`, copied there at install; `--log <file>` for its log, `--daemon <dir>` when the daemon is not `<root>/daemon`; `--version` prints `agentic-supervisor 1`), and it runs `agentic-daemon run` — see [Run in the background](#run-in-the-background).

`AGENTIC_DAEMON_HOME` puts the first four in one directory; the rest follow the install root (`AGENTIC_INSTALL_DIR`). There are **no session manifests**: the platform owns resume (it keeps each session's spec and the runtime's ref and re-opens with `spec.resume`), so a restart needs nothing on the machine but the session logs.

`credentials.json` is owner-only: `0600` on POSIX; on Windows inheritance is removed and only the current user is granted (`icacls`) before the token is written — if that fails, nothing is written.

### `environments.json`

What `env add` writes; the shape, for reading or a hand edit:

```json
{
  "environments": [
    { "id": "env_work", "name": "Work", "runtime": "claude-code", "profileDir": "C:/Users/me/.claude-work", "cwdRoots": ["C:/src/work"], "concurrency": 2 },
    { "id": "env_personal", "name": "Personal", "runtime": "claude-code", "profileDir": "C:/Users/me/.claude-personal", "cwdRoots": ["C:/src/oss"] }
  ]
}
```

`profileDir` becomes the runtime's per-account config dir (`CLAUDE_CONFIG_DIR`) and never leaves the machine. `concurrency` is optional — absent means no limit (#694), set or cleared from the environment's Edit dialog on the web — and bounds how many **turns** run at once in the environment, not how many sessions are open (#394): a chat member's session stays open between messages and costs nothing until it is prompted. A session whose `cwd` is outside `cwdRoots` (after symlinks are resolved) or does not exist is refused with a reason, and so is opening one while `concurrency` turns are already running; a prompt that would exceed it is answered with the wire `busy` error, and the platform parks the task until a turn ends here. Removing an environment from the web is refused while any session is hosted in it (the platform closes idle ones first). `cwdRoots` are also the only folders the platform can browse (below).

### Environments from the web: `policy.json` (#238, #355)

The platform can ask this machine to add, change or remove an environment (`env.request`, answered `env.response`; the Machine page, #239). The machine decides, under a policy that names the folders the web may use:

```json
{ "webManaged": true, "allowedRoots": ["C:\\Users\\me", "C:\\src"], "source": "web", "requested": ["~", "C:\\src"] }
```

- **Off by default.** No file, a file that does not parse, or no allowed root: every `env.request` is refused `policy-disabled`. `<dir>` must be an existing local folder outside the daemon's configuration and state folders; it is stored with links resolved, so it cannot later be re-pointed.
- **Set from the web (#355; decisions 2026-09-22)** with `policy.request { op: 'set', policy: { allowedRoots } }` — the Machine page's "Folders the web may use", and the Pair page's preset (`~` by default). Each root goes through the same check `allow-root` runs; `~` and `~/…` expand here, to the daemon user's home, never on the platform. One bad root refuses the whole request (`invalid`, `not-found`, `not-a-directory`, `remote-path`, `protected`) and changes nothing. What is written says `source: "web"` and echoes the roots as asked (`requested`) — the platform compares those strings to tell whether the machine converged. An empty list turns web management off. The `env` frame with the new policy goes out before `policy.response`. `op: 'browse'` lists a folder's subfolders (or, without a path, the machine's roots: the home folder, then the drives or `/`) for the folder picker — folders only, no hidden ones, and the daemon's own folders (configuration, state, every account profile) read as absent. The daemon reaches all of this only through a port `cli.ts` injects (`src/policy-web.ts`); `src/daemon.ts` and `src/env-manage.ts` cannot reach a policy writer, and a test holds them to that.
- **Or on the machine.** `agentic-daemon policy allow-root <dir>` (or `pair --allow-root <dir>`) turns it on for `<dir>`; `deny-root` removes one, `off` forgets them all — each says `source: "local"` and drops `requested`. **`policy lock`** makes the file local-only: every `policy.request` is refused `policy-locked` until `policy unlock` here, and the web sees `locked: true` on the policy. The file is written atomically and owner-only, like the credentials. A running daemon watches it and announces a change with an `env` frame; `hello` and `env` carry the policy (`policy`, with the roots only while it is on, plus `source`, `requested` and `locked`) so the web can explain a refusal. `hello.features` lists `policy` when the daemon answers `policy.request`.
- **Every working root is checked** (`checkWorkingRoot`, `src/policy.ts`): absolute; not a UNC share or a device path (`\\server\share`, `\\?\…`, `\\.\…`, `//…`), also after resolution (a mapped drive); inside an allowed root lexically, so `..` is judged by where it leads, and again after `realpath` of both sides, so a symlink or junction cannot lead out (the folder browser's `checkWithinRoots`) — another spelling of a folder inside (an 8.3 short name, a link to it) counts as that folder, and a folder outside is refused the same whether it exists or not; an existing folder; and overlapping none of the daemon's own folders in either direction: its configuration (the token, this policy, `profiles/`), its state (session logs) and every environment's profile. One bad root refuses the whole request (`outside-allowed-roots`); what is stored is the resolved root.
- **The machine chooses the profile.** A new environment gets `<config dir>/profiles/<id>`; a changed one keeps its own (also the runtime's default one, for a row written by hand) and keeps its `concurrency` and account label unless the request sets them. Nothing on the request can name a profile directory. The runtime must be one this daemon has a driver for, and an environment's runtime is never changed (its profile is signed in for that runtime).
- **Removing** refuses `in-use` while a session runs or opens on the environment and `unknown-environment` for one the machine does not have, and leaves the profile directory (the sign-in) on disk.
- The answer goes out after the `env` frame with the new descriptors. A failure that is the machine's own business (`environments.json` invalid, a write failed) is `io` with a message that names no local path; the details are in the daemon's log.
- `env.request { op: 'put' }` may set `allowBypassPermissions` (`true` sets, `false` clears, absent keeps): the platform admits turning it on to an elevated owner only (#355).
- **Signing in from the web (#484).** `login.request { environmentId }` runs the runtime's own login for that environment's profile with piped stdio (`src/login-relay.ts`, the CLI resolved as `env login` resolves it: the harness executable, else the shipped launcher, else `PATH`) — `claude auth login --claudeai`, `codex login --device-auth`, `copilot login --device-code` (the #483 spike) — and relays it as `login.status`: `started`, the `action` parsed from what the CLI printed (a URL to open and, for Claude Code, a code to paste back; a device code and its page for Codex and Copilot), `waiting`, then `done` on exit 0 or `failed` with the last stderr line. `login.answer { text }` goes to the child's stdin once and is never logged, never written; `login.cancel`, a lost socket, `stop` and the ten-minute cap kill the child. One sign-in per environment (`busy`); `unknown-environment`; `unsupported` for a runtime whose CLI is not here (Copilot needs `copilot` on `PATH`). After either end the environment is inspected again at once and an `env` frame carries the account. `hello.features` lists `login`, and each `CapabilityReport` says `login: 'relay' | 'terminal'`. `agentic-daemon env login <id>` on the machine works as before.

### Installer zip

```sh
pnpm build                                   # at the repo root: the zip is assembled from dist/ directories
pnpm --filter @agentic/daemon package        # → apps/daemon/release/agentic-daemon-<version>-<os>-<arch>.zip  (--unversioned: the release asset name)
node apps/daemon/scripts/package.mjs --harness all   # → harness-<runtime>-<version>-<os>-<arch>.zip per runtime (--harness <runtime> for one)
```

`scripts/package.mjs` copies `bin/`, `dist/`, the production dependency closure into a plain `node_modules/` (workspace packages as their `dist/`; the JavaScript of `@anthropic-ai/claude-agent-sdk`, `@github/copilot-sdk` and `@openai/codex` without any of their native packages, #369 — about 8 MB zipped; no declarations or source maps), the service scripts and, at the zip root, `install.ps1` / `uninstall.ps1` (Windows), `install.sh` / `uninstall.sh` (macOS, Linux; always `0755` and LF in the zip) and a README (`scripts/package/`). The zip needs only Node ≥ 22.12 on the target: the install script checks Node (`-NodePath` / `--node` for one that is not on PATH), pairs, runs `doctor` and registers the background service below. `scripts/lib/zip.mjs` is the dependency-free zip writer/reader; `__tests__/package.test.ts` builds the zip, unpacks it and runs `--version` and `doctor` on plain Node.

**Publishing (#343).** `.github/workflows/daemon-release.yml` builds the zip on Windows, macOS (arm64 and x64) and Linux (x64 and arm64) on every push to `main` that touches the daemon or a package, and uploads them as `agentic-daemon-<os>-<arch>.zip` to the rolling `daemon-latest` pre-release. The one-line installers the web app serves — `apps/web/public/install.ps1` and `install.sh`, printed with the pairing code on the Pair page — download that asset (or `AGENTIC_DAEMON_ZIP=<path or url>`), a portable Node from nodejs.org when the machine has none, unpack to `%LOCALAPPDATA%\agentic\daemon` / `~/.agentic/daemon` and run the zip's install script; re-running them without a code upgrades in place (a daemon from before #364 needs that once; later ones update from the Machine page). Since #361 the zips go out with `.sha256` files and a `manifest.json`: every `main` push refreshes `daemon-latest` (channel `latest`), a `daemon-v<semver>` tag builds the release `daemon-v<semver>` and refreshes `daemon-stable` (channel `stable`), and the installers read those manifests (`AGENTIC_CHANNEL`, `AGENTIC_VERSION`, `AGENTIC_RELEASES`) and check the sha256. The harness zips (`harness-<runtime>-<version>-<os>-<arch>.zip`) are uploaded once per pinned version (#441). Install, update, rollback, harnesses and uninstall: `docs/runbook.md` §5.

### Run in the background

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install-service.ps1     # Windows: a per-user Scheduled Task — at logon, under the supervisor
powershell -ExecutionPolicy Bypass -File scripts\uninstall-service.ps1
```
```sh
sh scripts/install-service.sh [--node <path>]                            # macOS: a launchd agent (KeepAlive); Linux: a systemd user unit (Restart=always); both run the supervisor
sh scripts/uninstall-service.sh
```

Never a system service: the token and each `CLAUDE_CONFIG_DIR` belong to the signed-in user. Output goes to `daemon.log` under the state directory (`%LOCALAPPDATA%\agentic\logs`, `~/Library/Application Support/agentic/logs`, `~/.local/state/agentic/logs` — `DaemonPaths.logFile`, what `log.request` will tail, #481).

The service runs the **supervisor** (`scripts/supervise.mjs`, #362), copied to `<install root>/supervisor/` (`%LOCALAPPDATA%\agentic`, `~/.agentic`, or `AGENTIC_INSTALL_DIR`) so an update of `<root>/daemon` never replaces it. It runs `agentic-daemon run` and on its exit: `0` → stops; `75` → swaps a staged update in (`daemon.staged` → `daemon`, the old one kept as `daemon.prev`); anything else → restarts after a backoff (1 s doubling to 60 s). A swapped-in version that does not write `state/ready` (after its first `welcome`) within 90 s, or exits twice within 2 minutes, is rolled back and `state/update-failed.json` says why. `state/supervisor.json` holds `restarts` and `lastExit`; `state/supervisor.log` every exit, restart and swap. `run` logs `daemon: exiting { reason, code }` on every exit (`signal`, `stop`, `update`, `uncaught`, `unhandled-rejection`, `config`, `error`). Re-running `install-service.*` on an older install replaces its `node bin/agentic-daemon.mjs run` action. `docs/runbook.md` §5.4 has how to read a rollback.

### Updates

**Restart from the web (#481).** `update.request { target: 'restart' }` is the same client and the same drain with nothing downloaded or staged: `draining` → `restarting`, the live sessions closed with code `restart`, exit 75 — and with no `daemon.staged` the supervisor relaunches this build (a staged folder present makes it `failed { code: 'busy' }`: exit 75 would apply that build instead). `agentic-daemon update` still restarts for `update`. **The log (#481).** `log.request { lines }` answers the last lines of `<stateDir>/logs/daemon.log` (`DaemonPaths.logFile`, the file the service scripts point stderr at) through `src/log-tail.ts`: at most 512 KiB read from the end, the first cut line dropped, every line redacted again on the way out, `truncated` when the file holds more; a foreground `run` has no file and answers `no-log`. `hello.features` lists `log` when the daemon runs with the port.

The platform updates a machine with `update.request` (#364; only to a daemon whose `hello.features` lists `update`, which it does when it runs under the supervisor), and `agentic-daemon update` does the same from the terminal. Each step is an `update.status` phase:

1. **downloading** the release zip over `https:` only, to `<install root>/downloads/<version>.zip`, with progress at most every 2 s and a 10-minute limit;
2. **verifying** its sha256 and size against the release — a mismatch deletes it and fails `checksum`, and the running daemon is untouched;
3. **staged**: unpacked to `<install root>/daemon.staged`, which must hold the install scripts and `bin/agentic-daemon.mjs`, and run once with `--version`;
4. **draining**: no new turns — a prompt that would start one is answered `draining` (the platform waits and sends it again after the restart) — while sessions still open; it ends when no turn is running, after the request's `drainTimeoutMs`, or at once with `now`;
5. **restarting**: every live session is closed with code `update` (the platform re-opens them, and offers Resume for an interrupted turn), `state/ready` is deleted and the daemon exits 75, so the supervisor swaps `daemon.staged` in and rolls it back if it does not come up.

A failure is `failed` with a code: `busy` (another update runs or is staged), `insecure-url`, `download`, `checksum`, `bad-package`, `unrunnable`, `no-previous`, `cancelled`, `unsupported` (no supervisor). `target: 'previous'` goes back to `daemon.prev` without a download. `update.cancel` before `restarting` stops it and removes the staged folder. A daemon that restarted mid-update removes what it left on start. `hello` also reports the build (`version`, `commit`, `protocol`, `channel`, `platform` like `win32-x64`) and the supervisor's `restarts`, `lastExit` and a rolled-back `lastUpdate` (reported once).

## How it works

- **Socket.** `wss://<platform>/_agentic/daemon/{machineId}` with `Authorization: Bearer <machine token>` (never in the URL). Redialled forever with exponential backoff and ±20 % jitter (0.5 s → 30 s); a refused token retries at the ceiling.
- **hello.** Environments via each driver's `inspect` (auth status, isolation, `CapabilityReport`) plus the per-environment verdict of the driver's `doctor` (`doctor: { ok, findings, checkedAt }` — the shared-config-dir and auth findings that name the environment, EXE-05/07; a driver whose checks throw gives every one of its environments an error verdict `driver-doctor-failed`, its message stripped of absolute paths by `withoutLocalPaths` — no local path reaches the platform, #274), one report per runtime, and a resume cursor per live session. `env` carries the same after a change. An environment whose runtime has no driver is left out and named by `doctor`.
- **Sessions.** `session.open` → the driver for the environment's runtime (with the session `Policy` compiled from `OpenSpec.policy` by `sessionPolicyOf`, #121 — the agent's approval rules, its tool grants and a delegated task's ancestors' constraints, the same compile the platform uses locally; no policy on the spec → the harness asks on its own terms) → `serveSession(session, { eventLog })` → `session.opened`. Session frames wait for `welcome`; `welcome.wanted` restarts each session's pump from the platform's cursor — from the in-memory buffer, then the NDJSON log, and a hole the log no longer covers is sent as a `gap` frame. A wanted session this daemon no longer runs (it restarted) is replayed from its log and reported `session.closed { code: 'restart' }`; the platform re-opens it under the same id with `spec.resume` (the runtime's ref), and the log continues on the next epoch (#363). A stop closes every live session with its reason as the code (`restart` on SIGINT / SIGTERM, `update`, `harness-update`).
- **Commands.** `session.command` → `ServedSession.handleCommand` (idempotent by `commandId`) → `session.reply`.
- **Folders (`fs.request`, #188, #331).** The platform browses a machine's folders, adds git worktrees and locates a repo's checkouts through `fs.request { requestId, environmentId, op }`, answered by `fs.response { requestId, result | error }` (`src/fs.ts`). The picker lists folders only.
- **Session files (`fs.request` `tree` / `read` / `changes`, #561; feature `files`).** For the Changes and Files views the platform lists one level of a session's folder, reads one file (the working copy, or as committed at `head` or the branch's `base`), or asks what changed (`uncommitted`, or the whole `branch` since its merge-base) — read-only, `path` inside `root` inside `cwdRoots`, checked lexically and after realpath (`src/files.ts`). Version control sits behind `VcsProvider` (`src/vcs/`); git is the default and `DaemonOptions.vcs` takes others. It runs `git` with no shell and a timeout, reading machine formats only. Text is capped at 480 KiB (`too-large` past it); a binary file answers its size only; `.gitignore`d entries are not listed.
  - `list { path }`: the immediate subfolders, sorted case-insensitively, without `.`-prefixed folders and `node_modules`, at most 500 (`truncated` beyond); `parent` unless the path is a root. Each folder carries a git badge read from files, never by running git: a `.git` directory is a `repo` (branch from `.git/HEAD`, or a short sha when detached), a `.git` file pointing into `…/worktrees/<name>` is a `worktree` (branch from that gitdir's `HEAD`). The badge's `origin` is the `url` of `[remote "origin"]` in the repo's common config (`<gitdir>/config`, or for a worktree the config its `commondir` file points to), as written; absent without one.
  - `worktree { repo, branch, base?, path }`: `git -C <repo> worktree add -b <branch> -- <path> [base]` through `execFile` (no shell, 60 s timeout). `repo` must be a repo or worktree inside the roots; `path` must not exist and whatever of its parents exists must be inside the roots; the branch must pass `git check-ref-format --branch` and not exist yet.
  - `locate { origin, depth? }`: every checkout whose badge `origin` names the same repo (core's `sameOrigin`: scheme, user, a trailing `.git` and the host's case do not matter) under the environment's roots — each root in order, walked breadth-first at most `min(depth, 3)` levels down, so the answer is roots first, shallowest first. The walk follows the listing's rules (no `.`-prefixed folders or `node_modules`; a symlink or junction only when it resolves to a folder inside the roots) and never visits a resolved folder twice. At most 20 matches (`truncated` beyond); a root missing on disk holds nothing.
  - **Safety.** Every path is checked lexically against the environment's `cwdRoots` first — `..` and relative paths are refused before the disk is touched — then again after `realpath` of the path and of every root, so a symlink or junction cannot lead out; every read then goes through the resolved path. A symlink in a listing or a locate walk counts only when it resolves to a folder inside a root. `session.open` runs the same check on its `cwd`. Refusals are named: `unknown-environment`, `outside-roots`, `not-found`, `not-a-repo`, `exists`, `branch-exists`, `invalid-branch`, `timeout`, `unsupported` (no git on PATH), `internal`. Each request is logged at debug level (`run --verbose`) with its op and path (or origin).
- **Platform tools.** A driver's `callTool(tool, input)` is sent as `tool.call` and settles on `tool.result` (an `error` rejects with `PlatformToolError`); calls still open across a reconnect are sent again after `welcome`; unanswered calls time out (10 min).
- **MCP connectors (#280).** `src/drivers.ts` gives every driver `openConnector`: Streamable HTTP servers through `openMcpConnector`, stdio servers spawned by `openStdioMcpConnector` (no shell, allowlisted environment plus the connector's credential variables, killed with the session). Credential values are fetched from the platform per session over `tool.call` (`connector_credentials`). The daemon never logs them and never writes them to the event log or any file.
- **Logs.** Every line is redacted: the token, its secret part and anything shaped like a platform bearer token are replaced.
- **Harnesses (#369).** `hello` lists each runtime's harness (`harnesses`, and `harness` in `features`). `harness.request { op, runtime, target?, mode }` installs, updates or removes one, reporting `harness.status` phases:
  - `downloading`, `verifying`, `staged`: the store unpacks the new version beside the current one.
  - `draining`: only that runtime drains. A turn-starting prompt on its sessions is answered `draining` (`drainingReply`), and a new session on it is refused with code `draining`. The drain waits for its running turns (up to 10 min), or not at all with `mode: 'now'`.
  - `applying`: its sessions are closed with code `harness-update` (the `stop` path), its driver is disposed, `current.json` switched, the driver rebuilt, and the old version removed.
  - `done`, then a `harnesses` frame; an `env` frame follows only if what the environments report changed.

  The platform re-opens the sessions from `spec.resume`. `remove` is refused `in-use` while an environment runs on the runtime. A runtime without a harness is still registered (`harnessMissingDriver`): its environments are reported with a `harness-missing` doctor verdict, and `session.open` on them is refused with code `harness-missing`.
- **Drivers.** The daemon consumes only `RuntimeDriver` from `@agentic/core` and never branches on a runtime id. `src/drivers.ts` is the registration point (`builtinRuntimes({ harnesses })`: each driver runs its runtime's located harness — `pathToClaudeCodeExecutable`, the Copilot SDK's stdio connection to `copilot-runtime` via `cliPath`, `codexPath` — and `rebuild(runtime)` builds one again after a harness change). This build ships `claudeCodeDriver()` from `@agentic/runtimes/claude-code` (`"runtime": "claude-code"`) `copilotCliDriver()` from `@agentic/runtimes/copilot-cli` (`"runtime": "copilot-cli"`) and `codexCliDriver()` from `@agentic/runtimes/codex-cli` (`"runtime": "codex-cli"`, #321), with their quota sources. Each probe goes through its driver: the Copilot source uses the driver's own runtime, and the Codex source uses the driver's `connect`. All are disposed when `run` stops.
