# Architecture — Unified Agent Platform

Status: v1 design, 2026-09-17. Requirements: [`requirements.md`](requirements.md). Decisions: [`decisions.md`](decisions.md). Promotion candidates: [`promotion.md`](promotion.md).

Every sub-issue of the tracking issue names the section here it implements. A section is the contract an implementing agent works to; change the section in the same PR when a seam changes.

## 1. Package layout

pnpm monorepo, `@agentic/*`, all private.

```
apps/web               sigx SSR + serverFn + actors host on Cloudflare (Worker + ActorHost Durable Object in one bundle); UI on @sigx/zero + zero-daisyui
apps/daemon            Node 22 bin `agentic-daemon` (pair | run | doctor); Windows first
packages/core          edge-safe types + tiny helpers, zero deps: ids, AgentConfig, ChatEntry, TaskState/WaitReason/TaskContract, EnvironmentDescriptor, CapabilityReport, PluginManifest, MemoryPlugin/LearningPlugin interfaces, daemon frame types, Principal kinds
packages/platform      defineActor definitions + services: Workspace, Agent, Chat, Task, Session, Machine, Schedule, Memory, Inbox, Ledger, Registry, Audit; auth helpers
packages/runtimes      runtime adapters: 'anthropic-api' (modelAgent), 'claude-code' (daemon driver); platform tools (memory.*, delegate, chat.post, task.report, ask_user)
packages/memory        default MemoryPlugin (Memory-actor backed, BM25-ish + recency, no embeddings) + memoryConformance
packages/learning      default LearningPlugin (corrections → lessons; proposals needing review)
packages/daemon-protocol  envelope validators + daemonConformance (types live in core)
packages/ui            @agentic/ui: zero fragment (ai-thread, ai-message, ai-composer, ai-tool-call, ai-reasoning, ai-approval, ai-question) + layout shell (Stack/Row/Col on data-l-*) + StreamingMarkdown on @sigx/markdown
packages/mcp           MCP client (Streamable HTTP, edge-safe; stdio on the daemon) + platform MCP server (orchestration surface)
packages/a2a           A2A 1.0 JSON-RPC server (agent card + tasks) + client adapter implementing the @sigx/ai-agent Agent contract
```

Rules:

- `packages/*` never import the `sigx` umbrella (it drags `@sigx/runtime-dom/platform`). Peer on `@sigx/runtime-core` / `@sigx/reactivity` / `@sigx/actors` only, so packages stay edge-safe and renderer-neutral. Only `apps/web` and `packages/ui` touch the DOM.
- Import order (downward only): core ← daemon-protocol ← memory / learning ← runtimes ← platform ← apps.
- Source layout as in signalxjs/ai: one folder per concern, `index.ts` is the public surface, entry points are folders.
- Every sigx-estate version comes from the `catalog:` in `pnpm-workspace.yaml`.

## 3. Hosting topology

- One Cloudflare Worker (`apps/web`) serves SSR pages, serverFns, static assets, the actor HTTP mount (`/_sigx/actor`), the browser live socket (`createWorkerHandler({socket: {terminate: 'object'}})`), the daemon socket (`/_agentic/daemon/{machineId}`, accepted by the Machine Durable Object), MCP (`/_agentic/mcp`), A2A (`/_agentic/a2a/{agentId}` and `/.well-known/agent-card.json`), webhooks (`/_agentic/hooks/{id}`), OAuth callbacks.
- One Durable Object namespace `ACTORS`, one object per actor, SQLite-backed (`migrations: [{tag: 'v1', new_sqlite_classes: ['ActorHost']}]` — never `new_classes`, it is irreversible), `durableObjectStorage()` + `durableObjectReminders()` (alarms). `wrangler.jsonc` needs `compatibility_flags: ["nodejs_compat"]` and `define: {"__DEV__": "false"}`.
- **Eviction is not deactivation.** `onDeactivate` never runs on Workers. Every mutation ends in `ctx.save()` or `ctx.append()` inside the turn.
- R2 bucket for artifacts, exports and chat attachments (`files/`, #207). Workers Secrets for the OAuth client secret, `WORKSPACE_KEK` (AES-GCM key for stored API keys), VAPID keys are per workspace, not deployment secrets: the Web Push plugin's config and a Registry secret (#244). No D1 in v1.
- Implementation (#33): `apps/web/src/actors.app.ts` holds the registry (`platformActors(ports)`), `createActorHost()` (the `ActorHost` class; `createHostDurableObject` derives storage and reminders from the object's own state, `socket: {}` accepts object-terminated sockets) and `createActorWorker({ fallback })` (the Worker half; server functions and SSR are its fallback). Both halves call `ensureServerApp(env)` first — `createServerApp({ ...serverAuth({ sessionSecret }) })` — so `authorize` sees the same principal in the Worker and after the hop into the object. No `SESSION_SECRET` → every caller is anonymous, never a fallback secret. Ports not wired yet refuse loudly: the Session `factory` returns `null` (daemon path) until #35, the platform `tools` a daemon session calls back are answered `unsupported` until #37. The Schedule trigger is the platform's `scheduleTrigger()` (#42; §4 Schedule) with no environment probe wired yet, so a scheduled task that needs an environment waits `environment-offline` for the router (#37). Routing order in `entry.cloudflare.ts`: auth routes → the actor worker (`/_agentic/daemon/{machineId}` forwarded to the Machine object, actor mount, actor sockets) → server functions → document. The auth routes are resolved by `apps/web/src/auth/mount.ts` (`createAuthMount`, the same resolver the workers harness mounts, #180) from what the env has: `SESSION_SECRET` alone mounts `POST /auth/pair`, `GET /auth/me`, `POST /auth/logout`; `GET /auth/login` / `GET /auth/callback` need the GitHub app's secrets and an origin; the OAuth 2.1 server (#50) needs an origin — `APP_ORIGIN`, or on localhost the request's own. A dev-login-only `pnpm dev` therefore pairs a machine. `test:workers` (`@cloudflare/vitest-pool-workers`) drives the real object on SQLite storage; deploy steps are in `docs/runbook.md`.
- **Several objects per isolate, one global host (#137).** `@sigx/actors` resolves an ambient `actor(def, key)` through `globalThis.__SIGX_ACTOR_HOST__` (last `start()` wins), and `createHostDurableObject` starts one host per object — so with several `ActorHost` objects in one isolate (always in the workers test pool, in production whenever objects of the class share an isolate) a hop resolved through the last-booted object's host, whose placement answers `isSelf` for ITS actor: the callee ran locally inside the caller's object on the callee's storage ("Cannot perform I/O on behalf of a different Durable Object"; the callee reset, its unsaved turn lost). The platform hops ambiently wherever a call carries its own principal (`.with({ context: asPrincipal(p) })`: the Routing driver's clients, `routing().machineOnline`, the tool and learning ports, the Session's command sink). `apps/web/src/host-scope.ts` makes the seam an accessor over an `AsyncLocalStorage` (workerd under `nodejs_compat`): `ActorHost` runs `fetch`, the hibernation handlers and `alarm` under its own host (`runWithHost`), the Worker enters the scope ONCE at the top of `entry.cloudflare.ts`'s `fetch` around every route — auth routes included, since `POST /auth/pair`, the token lookup and the MCP mount hop too (#172: unscoped, the pair for a machine whose object the Pair page had just booted ran inside the Worker on that object's storage) — under its own host (`createActorWorker().host`, a thunk: the host boots once per isolate from `env` alone through `createActorWorker().boot(env)`, awaited before an auth route runs and by the actor mount otherwise — #182: booted only by the first mount request, an auth route hopping as the very first request of a cold isolate found no host at all), and a read outside any scope answers what `stampHost` last wrote — `@sigx/actors` is unchanged. Upstream: signalxjs/actors#456 (the seam should scope itself); `__tests__/workers/host-scope.test.ts` pins the two-machines-then-a-session-turn shape on the production class, and the two-machines-then-`POST /auth/pair` shape on the Worker.
- **Chat files (#207, `apps/web/src/files`).** `r2ChatFileStore` is the `ChatFileStore` on the `ARTIFACTS` bucket: `files/<ws>/<chat>/<fileId>`, custom metadata `name` / `mediaType` / `posted` / `at`; R2 cannot edit metadata, so `markPosted` rewrites the object; `sweepOrphans` reads one listing page of `files/` per call (with `customMetadata`) and resumes from its cursor. One instance per isolate (`platformFiles` in `actors.app.ts`) is `PlatformPorts.files`, passed to the five places §7 "Wiring the file store" lists, and serves the Worker's routes. `createFilesMount` resolves `POST /files/chats/:chatId` and `GET /files/chats/:chatId/:fileId` after the auth routes, in the `actors.boot(env)` branch (they hop). Both authenticate with `authenticateRequest` (the session cookie; an agent token may read; machines never) and address the chat in the CALLER's workspace, so another workspace's ids name nothing (404). Upload: a same-origin `Origin` (the CSRF guard for a cookie credential), `Content-Length` and a streaming cap at `CHAT_FILE_MAX_BYTES` (413), a type that parses and is not HTML / XHTML / an executable (415), `X-File-Name` URI-decoded to its last path segment without control characters, ≤ 200 characters; R2 first, then `Chat.registerUpload` as the caller — a refusal deletes the object and passes the Chat's status on; 201 `{ file, uri }`; then, at most once an hour per isolate, `sweepOrphans(1 day)` under `waitUntil`. Download: `Chat.fileAccess` as the caller (`null` → 404), the object streamed with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, max-age=3600` and `Content-Disposition` `inline` for png / jpeg / gif / webp, `attachment; filename*=UTF-8''…` for anything else (SVG included). The live chat (`pages/chat`) uploads from the composer's `files` event, posts `agentic-file:` parts with the text, and renders them through `/files/chats/…` (`entryTranscript`).
- **Hub turns hand slow work off (#492).** The host's default `callTimeoutMs` (30 s) is the deadline every caller of a busy actor gets, and a turn that awaits another actor holds its own queue for the duration — so a hub actor (the workspace's one Routing, a machine's one Machine) that awaits a slow turn stalls everything queued behind it, in chats that never touched the slow one. Prod, 2026-09-21: both daemons reconnected, `Routing.machineOnline` held the router 94 s, one `Session.forwardFrames` (a turn-end: transcript fold, learning, chat publish) held its Machine 85 s, and every new message in the workspace failed the browser's awaited `Routing.run` at 30 s before a session opened. The rule: a hub dispatches to a slow or unbounded turn `oneWay` — the mailbox keeps a caller's order — and the outcome is read from state (the page reads the task index and the chat's entries; the router follows the session's tail). `Machine → Session` frames, refs, titles and replies are one-way (§5b); the page's `Routing.run` is one-way (§10). What still holds a hub: the router's placement itself (`run` awaits the Machine, the Session and the project hooks' daemon round trips, up to 35 s) — a slow one delays the workspace's other placements, no longer fails them; moving it into a detached task is the follow-up. The `ActorHost` attaches `observeSlowTurns` (`apps/web/src/actors/slow-turns.ts`) to its host: any turn past `SLOW_TURN_MS` (5 s, queued plus ran) is one `console.warn` line naming type, key, method, queue wait and run time, so `wrangler tail` names the turn that held an object instead of showing wall time alone.
- Follow-up, not v1: split the DO host into a second Worker so UI deploys cannot evict live sessions.

### Audit

`packages/platform/src/audit` (issue #44, the platform half; the `/history` page is the UI track's). Every consequential action is one `AuditEvent` — `{ key, seq, kind, at, by, summary, agentId?, taskId?, sessionId?, data }` — recorded ONCE per occurrence by the actor that performs it, through `recordAudit(ctx, workspaceId, event)` (or the `AuditPort` the Session and Routing actors take in their ports; `auditPort()` is the default, `capturingAuditPort()` the test double). The helper is a ONE-WAY hop to `{ws}:audit`: it resolves at acceptance and swallows every failure, so the history never stalls or fails the turn that did the work. Idempotency is the emitter's: `key` derives from the source record (`{taskKey}:transition:{n}`, `{sessionKey}:{epoch}:{seq}`, `{agentKey}:v{n}`, `{machineKey}:paired`, …), so a retried turn or a replayed frame folds once. `by` is `user:|agent:|machine:|external:<id>` or `system:<name>` (`system:routing`, `system:policy`).

**Keys.** `{ws}:audit` is the live log: `record` stamps each event with the next `seq` and keeps the newest `AUDIT_WINDOW` (500) in state; once the window holds `AUDIT_WINDOW + AUDIT_ROLL_BATCH` events the oldest batch (100) rolls over into `{ws}:audit:{yyyy-mm}` archives — one per UTC month of the event's `at`, written through an idempotent `archive` hop (like Chat's pages; a crash between the hop and the save repeats it) — so a workspace's history never rewrites one ever-growing record and a month can be retained or dropped as a unit. The window-plus-monthly-archive shape was chosen over one actor per month (the Ledger's) because the history page wants ONE live entry point and one cursor: `list(query)` on the live key is a `read` (`useActorState(AuditActor, auditKey(ws)).list(q)` re-runs after every record), newest first, and walks the archives itself when the cursor passes the window (newest month first; `since` / `until` prune the months it cannot match). `list({ kinds?, agentId?, taskId?, sessionId?, since? (inclusive), until? (exclusive), cursor? (exclusive seq, `null` = newest), limit? (≤ 200) })` → `{ events, next }`, `next` being the seq to pass back or `null` when nothing older can match; `taskId` also matches a `delegation.created` by its child. `stats()` reports `inState`, `recorded`, `archived`, `months`. Over the wire only a user records; `archive` is never wire-callable — hops run no policy.

### Schedule

`packages/platform/src/schedule` (issue #28). One actor per entry, keyed `{ws}:schedule:{id}`, `defineScheduleActor({trigger: TriggerPort})`. Recurrence is `{kind: 'at', at}` (one-shot, epoch ms) or `{kind: 'cron', cron, tz}` — a 5-field cron subset (`*`, `n`, `a-b`, `a,b`, `*/n`, `a-b/n`; no names, no `L`/`W`/`#`) evaluated on the wall clock of an IANA zone. `next` is computed in `recur.ts` from `Intl.DateTimeFormat` parts only (no dependency, edge-safe); an unknown zone or bad expression is rejected at `create`/`update`, never stored.

Each occurrence is armed as a ONE-SHOT reminder (`ctx.reminders.set('fire', {due: next - now})`), re-armed from `onReminder` — the runtime's 60 s period floor is never requested, and on Cloudflare the entry's own alarm fires it with no machine or browser online (AST-03/04). `onReminder` posts a `ScheduleFired {workspaceId, scheduleId, key, kind, title, scheduledFor, firedAt, occurrence, skipped, agentId?, environmentId?, prompt?, offlinePolicy}` to the `TriggerPort` together with a `TriggerHop` (the actor's own `ctx.actor`, so the port reaches other actors as trusted hops — a reminder runs with no principal, and an in-process `actor()` from the port would be refused by `sameWorkspace`), then re-arms. A rejecting port is retried one floor (60 s) later up to 3 attempts, then the occurrence is logged `dropped` and the calendar moves on. Every mutation ends in `ctx.save()` inside the turn.

**Trigger (#42)** — `scheduleTrigger({environments?})` in `schedule/trigger.ts` is the platform's port, registered by `apps/web/src/actors.app.ts`. A `reminder` entry, or any entry without an `agentId`, becomes one Inbox notification of kind `reminder` (`body` = the prompt, `ref {kind: 'schedule'}`) through `Inbox.push`, so every configured channel delivers it from the entry's own alarm (AST-04, AC-08). An entry with an agent becomes a Task owned by and assigned to that agent, `origin {kind: 'schedule', scheduleId}`, objective = prompt (title when absent), with the id `scheduledTaskId(scheduleId, scheduledFor)` — deterministic and `Task.create` idempotent, so the actor's retry of a firing that threw half-way finds the task it already routed (exactly once per occurrence). AST-05: with an `environmentId` the trigger asks the `EnvironmentProbe` (the Machine actor's seam, #36; absent = every environment is offline). Offline under `queue` or `fallback-api` → `reportWaiting({kind: 'environment-offline', environmentId, policy})` — recorded for the router (#37) to resolve, never routed here; under `fail` → `fail({code: 'environment-offline'})` plus a `task-failed` notification. Online, or no environment → the task stays `queued`.

**DST rules (AST-07)**, fixtures in `__tests__/schedule/recur.test.ts` for Europe/Stockholm 2026:

- *Spring gap* — a wall time that does not exist (02:30 on 29 Mar, when 02:00 CET → 03:00 CEST) is skipped; `30 2 * * *` fires 28 Mar 01:30Z, then 30 Mar 00:30Z.
- *Fall overlap* — a wall time that exists twice (02:30 on 25 Oct, when 03:00 CEST → 02:00 CET) fires on its FIRST occurrence only (the CEST instant, 00:30Z); the repeated hour never fires a second time, whatever the minute pattern, so `*/30 * * * *` goes 00:30Z → 02:00Z that morning.
- *Catch-up policy `skip`* — a reminder that runs late (host down, alarm delayed) fires once for the occurrence it was armed for with `skipped = ` the number of later occurrences that fell before "now", writes a `skipped` log entry, and re-arms strictly after "now". Never a burst.
- Reminders are "at or after due" with the host's tick as resolution (60 s on the sharded table; exact on DO alarms); an entry due sooner than a tick fires on the next tick, never early.

## 5. Session execution paths

### 5a. Platform-managed API agent (`anthropic-api`)

The Session actor is built once per app over its ports (`packages/platform/src/session/ports.ts`): `defineSessionActor({ factory, commands })`. The `SessionFactory` maps a runtime id to an `OpenedSession` (`{ session: AgentSession, agentId, capabilities }`) or `null` for a daemon-hosted runtime; `@agentic/runtimes` supplies the `modelAgent` one, tests plug `mockAgent`. The actor never imports an adapter.

Which runtimes exist is the app's `RuntimeCatalogue` (#230, `packages/platform/src/routing/factory.ts`): runtime id → `RuntimeImpl`, `{ host: 'local', open(context, plugin) }` or `{ host: 'daemon' }`. The router and `createSessionFactory({ runtimes, registry })` share it: a `local` runtime is placed in-process and needs no environment, a `daemon` one goes to a machine, an id the catalogue lacks fails `unknown-runtime`. `anthropicApiRuntime(options)` is the built-in local one. Before any of it `Routing.run` asks `Registry.gate({ runtime })` once (§9): missing or turned off → the task fails `plugin-disabled` and nothing opens; the answer is recorded on the route and on the session spec (`SessionOpenSpec.plugins`), and the plugin's `config.defaultModel` is the session's model where the agent names none. A `fallback-api` (§7) asks the gate again for `anthropic-api`.

```ts
// open: record the spec — replaced on every re-open (#393) — open the runtime session (resume from the recorded ref), serve it in-process
const opened = await factory(spec.runtime, { spec, resume: state.ref, signal: ctx.abortSignal, transcripts, currentTaskId: () => currentTaskId(state) });
const served = serveSession(opened.session, { agentId, capabilities });   // command validation, busy/closed, one reply per commandId
// prompt(input, turnId, output?, commandId = turnId, { taskId }): idempotent by commandId (persisted), then the turn runs as a detached task
const reply = await served.handleCommand({ v: 1, commandId, type: 'prompt', turnId, input });
if (reply.kind === 'ack') { state.running = { turnId, commandId, input, taskId: taskId ?? spec.taskId }; await ctx.tasks.start('drive', { turnId }); }
// drive: subscribe from the durable head, one turn per event, until this turn's turn-end
for await (const ev of session.subscribe(state.head)) await ctx.turn((c) => appendEntry(c, { t: 'ev', ev }));
```

- **The turn owns the task** (#390; COL-04, OPS-08, MEM-07, AGT-06). A session serves many tasks over its life (§7), so `spec.taskId` is only the task it OPENED with. The prompt names the turn's task (`prompt(…, { taskId })`, the route's task from the router); on the daemon path it rides the command record (`CommandRecord.taskId`, never the `WireCommand`), so the ack that arrives later through `commandReplied` still starts the turn under it; `RunningTurn.taskId` holds it while the turn runs and `currentTaskId(state)` (`session/state.ts`) — `running?.taskId ?? spec?.taskId` — is what everything task-attributed reads: the minted agent principal, the audit rows of a request and its decision, `SessionRequestView.taskId`, the follow-up of a detached answer, the Ledger row and the budget verdict (`recordUsage`), the learning hook (`learnFromTurn`, whose plugin is built for that task), the chat message published at turn end, and a correction's origin. A `turn-end` drops `running`, so the driver reads the task before the fold and hands it to `finishTurn`. The tool ports read it per call, never once at open: `SessionFactoryContext.currentTaskId` → `createActorToolPorts({ taskId })` → `principalNow()` overlays it on the minted identity for every hop (`delegate`'s parent, `task_report`, a memory's provenance, `chat_post`'s task, the mentions a post activates). A sealed agent token (`auth/agent-token.ts`) therefore carries only the opening task; it is never the source of the task.

- `createPlatformModelAgent(cfg, { ports, anthropic: { apiKey }, store, skills, memories })` (`packages/runtimes/src/anthropic`) builds that `agent`: the roster is the platform tools the config grants (`deny` and skills never add one, AGT-04), `system` is assembled stable-first (identity, role, instructions, skills, tools, then the memory block), `pricing` is the `claude-*` table with `estimated: true` for an unlisted id, and it returns a `CapabilityReport` (AGT-09) plus `usageRow(event, …)` for the Ledger. Platform tools are `defineTool`s over abstract ports (`MemoryPort`, `TaskPort`, `ChatPort` in `packages/runtimes/src/tools/ports.ts`) the Session supplies under the agent principal; on the wire they are `memory_search`, `memory_remember`, `delegate`, `chat_post`, `chat_file_read`, `task_report`, `ask_user` (provider tool names allow `[A-Za-z0-9_-]` only). `chat_file_read` (#206) reads a chat attachment by its `agentic-file:` URI through the optional `PlatformPorts.files` (`ChatFilesPort.read`, the access decision is the platform's): text for a text file, cut at `CHAT_FILE_TEXT_MAX_BYTES` and flagged `truncated`, only a note with name, type and size otherwise; a host without the port fails the call. `chat_post` takes optional `attachments` URIs, passed on as `ChatPost.attachments`. `ask_user` goes through `ChatPort.ask` — the engine never raises an input `request` itself; the platform does (#122, below).
- Every event is durable before the next is read; the reducer (`applySessionEntry`) is pure and idempotent by `(epoch, seq)`, so a frame replayed twice folds once. At a turn end the driver folds the new events into the transcript snapshot, refreshes `ref`, publishes the final assistant text on `SESSION_EVENTS_TOPIC` keyed by the chat's actor key, and saves.
- **Where a ref comes from** (#389). The record holds only a ref a runtime actually gave it, so a placeholder can never be replayed as a resume token. Local path: `finishTurn` reads it from the live `AgentSession` at every turn end (and `ensureLive` when it opens one). Daemon path: only the daemon's `session.ref` frame, through `Machine.onSessionRef` → `Session.noteRef` (§5b) — never the synthesized `hello`, whose `sessionRef` is what `session.opened` carried before the first prompt (a `cc_…` placeholder for Claude Code). `open()` seeds `ref` from `spec.resume` when the spec is first recorded: that value is an earlier record's ref, so it is real. Nothing else writes it.
- **Re-open** (#393; EXE-12, EXE-13, MEM-07). `open()` on a record that is already open and not closed re-opens it: the spec is replaced by this placement's — the task, its objective and context, the memories `withRetrievedMemory` retrieves for them (retrieval ranks on the current objective, once per re-open), the machine, environment and folder (so `assertHostingMachine` admits the daemon the session comes back on after a restart on another connection) — and the status is `idle` again. A local runtime session that is gone is opened again by `ensureLive` from the recorded ref; on the daemon path the router passes that same ref as `OpenSpec.resume`. The ref itself is seeded from `spec.resume` on the first open only; a re-open never touches one a runtime reported. While a turn runs the record is left as it is (#395 decides what a mid-turn message does). `session-started` goes to the chat once, at the first open: the chat's binding (§6) is for the session's life, and the two statuses bracket it — a chat member's session is not closed when its task settles (§7).
- **Where the history lives** (#397; CHT-08, CHT-10, OPS-05, OPS-10). On this path there is no machine, so the platform owns both the event log and the model's history: every page is kept (`SessionState.pages` lists them all, `archivedTo` is never set), and the transcript the `modelAgent({ store })` saves at every turn end stays whole in the record while it fits `TRANSCRIPT_BYTES` and, once it outgrows it, goes whole to `SessionTranscriptPage`s (`{key}:t{n}`, ~`TRANSCRIPT_PAGE_BYTES` each, `createTranscriptStore` in `session/store.ts`) — either way it comes back whole from `load` on resume — the record's `transcript` is only the `boundTranscript`ed view, so `TRANSCRIPT_BYTES` is no longer a storage limit on what the model remembers; older tool outputs are never replaced by trim markers in the history the model resumes from. Whether a long history should be cut to a model's context window is a product decision (compaction, #401), not a storage one. On the daemon path (§5b) the machine owns the event history and the platform keeps a bounded window; the runtime (Claude Code) keeps its own transcript on the machine, so no transcript pages are written there.
- **The record's budget** (#198, #391; the Session row in §4 has the numbers). A live chat session (one per chat member, never parked) runs for weeks, so nothing in the record may grow with the number of turns: the window is paged, the index holds the last `INDEX_TURNS` turns and no prompt (`IndexedTurnStart`: cursor, turn id, bytes), a replied command keeps only its id, type and reply, and the transcript snapshot is bounded. What a reader needs from further back it reads from a page: `events(from)` / `tail(from)` through `eventsSince`, a `resume()` whose interrupted turn streamed its own start out of the window through the one page holding it (`eventAt`). The only whole-set readers are `get().grants` and `requests()`; `request(id)`, `respond`, `resolution`, `raiseInput` / `detachInput`, the decision's chat / Inbox / audit bookkeeping, `finishInterrupted` and learning look one record up (`findEvent`, `requestById`) without materialising the log — a tool call's approval path is O(window), not O(session lifetime).
- Eviction mid-turn loses nothing already saved. The runtime's task ledger restarts `drive({ turnId })` on the next activation; it finds no live session for that turn and closes it honestly: `tool-update cancelled` for calls still open, `request-resolved {outcome: cancel}` for open requests, `error {code: 'process_exited', recoverable: true, data: {interrupted: true}}`, `state idle`, then `turn-end {stopReason: 'error'}` — `isInterruptedTurnEnd(ev)` names it. The Task driver reads that and marks the Task `waiting {input}` with "Resume?". A model call is never replayed (OPS-05/06). A live session opened afterwards resumes from `ref` in a new epoch, so the log stays gapless per epoch.
- Approvals: `request` event → Task `waiting {approval}` + Inbox notification + Chat status entry → user responds → `Session.respond` reaches the live `AgentSession`. A decision that arrives after an interruption is a no-op ack: the interrupted turn is closed, not resumed.
  - As implemented (#40, `packages/platform/src/session/actor.ts` `appendEvent`, `src/policy/requests.ts`): the Session announces every request itself, on both paths — an `approval` / `input` Inbox notification with a `{ kind: 'session', sessionId, requestId }` ref (`SessionPorts.inbox`, one-way) and a chat status `request` with `ref` `approval:{id}` | `input:{id}`; the `request-resolved`, whoever caused it (`Session.respond` from the chat card, the inbox page or an external client; a policy rule; a timeout; a cancel), marks that notification read (`Inbox.ackRef`) and appends the pairing `request-resolved` status; the audit `approval.requested` / `approval.resolved` are emitted once each as before. `Session.request(id)` and `requests({ openOnly })` are live reads of `SessionRequestView` — the request joined with its `tool-call` (input, category, annotations), the decision, the agent / chat / task, and `rule: describeRule(ruleFor(approvalPolicy, …))` — so every client renders one record and the first `respond` wins (a second is an idempotent ack). A `session`-scoped allow is a grant: `SessionInfo.grants` lists them from the log (`sessionGrantsOf`); revoking is not offered — `@sigx/ai-agent` checks its private `SessionGrants` before the policy runs, so nothing of ours can undo one, and a daemon harness keeps its own; the control is not rendered until an adapter exposes them (AC-15). On the daemon path the same policy is compiled by the daemon from `OpenSpec.policy` (#121, §5b); what the harness still asks on its own terms (`permissions.every-call` unsupported for Claude Code) goes through the same inbox / chat / respond flow.
  - **Platform-raised input requests** (#122, `Session.raiseInput`, `packages/platform/src/routing/tools.ts` `chat.ask`): `ask_user` has no way into the runtime's own request flow, so the tool port (in-process on the local path, through the Machine's `tool.call` on the daemon path) asks the Session to raise `request { kind: 'input', requestId: 'ask:{callId}', callId, toolName: 'ask_user', message, options }` for the call — idempotent by call id, so a daemon re-sending an open `tool.call` after a reconnect re-finds the same question — then tails `Session.resolution(requestId)` until a decision lands; the `answers` are the tool result (`answerText`), a `cancel` a `cancelled` tool error. The event is the running turn's and is stamped by `platformCursor(head)` — strictly after the head, strictly before the runtime's next integer `seq` (fractional on purpose) — so it never collides with, nor skips, a runtime event: `applyEvent` folds by cursor, the local driver subscribes from the head, the Machine replays a daemon from its own cursor. On the local path the Session drains what the runtime already buffered first (the `tool-call` itself), so the question lands after its call. `respond` settles a platform-raised request itself (`platformRequests` on the state; a synthetic `request-resolved { outcome: 'input' | 'cancel', by: 'client' }`, a permission decision refused as `invalid`, a second decision an idempotent ack) — never sent to a runtime that does not know it. Everything else is the #40 flow unchanged: the chat `request` / `request-resolved` statuses, the `input` Inbox row and its ack, the router's `follow` parking the Task `waiting {input}` and releasing it, `Session.request(id)` rendering the card with the call's input; an input request is not audited. An eviction mid-question closes it like any open request (`finishInterrupted` → `request-resolved cancel`).
  - **Questions outlive the call** (#285). A blocking tool call cannot hold a question for hours: the engine's MCP tool timeout, the daemon's `toolTimeoutMs` and the router closing a chatless session at turn end all end it first. So in a chat `chat.ask` waits only `ASK_QUICK_WAIT_MS` (25 s, `askQuickWaitMs` on `createActorToolPorts` / `createToolCallPort` / `createSessionFactory`): a quick answer is still the tool result. After that it calls `Session.detachInput(requestId)` and answers `{ status: 'pending', questionId, note }` (`AskOutcome`, `packages/runtimes/src/tools/ports.ts`); the tool description tells the model to end its turn. `detachInput` is atomic with `respond`: an answer that beat it is returned instead, never lost. A detached request (`detachedRequests`, or any open platform request once the session is closed) stays open: `finishInterrupted` skips it, the close does not cancel it, `SessionRequestView.detached` says so (with `agentName`), and the router's `follow` releases the Task from `waiting {input}` at turn end so it completes. `respond` takes a platform request's answer before the `closed` check, so it is accepted on a closed session. An answer to a detached request is parked in `answeredDetached` and, once the session is closed or no turn runs on it (#393: a chat member's session is idle between turns and never closed at turn end, so `isDetached`, `respond` and `deliverAnswers` all gate on `closed || !running`, and `finishTurn` starts the delivery for answers that came mid-turn), handed one at a time to `SessionPorts.answered` by the `deliverAnswers` actor task, outside any turn (the hand-over prompts this session back, or places a task that does) and restarted after an eviction. A hand-over that throws is not dropped (#396): the answer stays parked with `attempts` and `nextAt`, the Session's `answers` reminder (`ctx.reminders`) runs the next attempt after `ANSWER_RETRY_MS` (5 s, 30 s, 2 min, 10 min), and only once `ANSWER_ATTEMPTS` (5) are spent is it dropped and said in the chat as a `task` status `answer-not-delivered:{step}:{cause}`, named by the hand-over (`AnswerDeliveryError`). `createAnswerFollowUp({ routing })` (`packages/platform/src/routing/answers.ts`) implements the hand-over: it posts the answer in the chat as the person who gave it, mentioning the asker (`@Ada — re: “…” → …`; once — a retry carries `posted`), then hands it to `Routing.deliverAnswer`, which prompts the asker's own live session with it under the asking task — the task stayed `waiting {input}` on a route parked `waiting-answer` when its turn ended with the question open — through the same seam a chat message takes, into the turn `answerTurnId(taskId, requestId)`: no new task, and the engine conversation that asked carries on (§7 "A late `ask_user` answer reaches the asker in its own session"). Only when no route waits on the question (the asking task was cancelled or failed, the session ended) does it create the asker's follow-up task, whose id is `answerTaskId(sessionId, requestId)` so a replay starts nobody twice: from `answerContract` — its origin that message, its context the question, the answer and the chat, `resumeFrom` the asking session, its depth the asking task's — placed with `Routing.run` as the workspace user. In a chat the follow-up is a chat task, so it runs in the asker's own live session when that can go on (#393: the chat's binding names it, and it is the `resumeFrom` session itself), prompted with the answer as the objective (`The answer to your question “…”: …`) plus whatever the chat said since; when that session cannot go on (§7) a fresh one opens: then the router resumes the engine conversation (`OpenSpec.resume` = the earlier session's `ref`) only when a daemon ran it for the same agent, runtime, environment and machine; a local API session's transcript lives in its own Session record, so that path opens fresh on the contract's context. A dismissed question (`respond {type: 'cancel'}`) is parked and handed over the same way (`cancelled`): `Routing.questionCancelled` releases the task waiting on it as it stands, nothing is posted, nobody is prompted. A chatless session (a delegated child) keeps the blocking wait: there is no chat to start it in. In the web app the Inbox card and a chat card for an open question whose session left `sessions` (`detachedQuestions`: the chat's `input` statuses, the session from the unread Inbox row) show who asked and, when stale, that answering starts that agent again (`QuestionPrompt` `stale`).
- `tail(from)` replays the log from `from` (exclusive) out of a state snapshot, then follows `ctx.changes()` until the session closes; `{ epoch: 0, seq: 0 }` gives a late joiner the whole log, and reducing it equals the driver's snapshot.
- Limits `{maxTurns, maxSteps, maxTokens, maxCostUsd, maxWallMs, maxDepth, maxConcurrentChildren}` enforced in the driver; every `usage` event → Ledger (estimated flag when pricing is unknown). As implemented (#45, `packages/platform/src/ledger`): `defineSessionActor({ factory, usage: ledgerRecorder() })` — after each **turn-scoped** `usage` event is durable (session-scoped events are cumulative totals, never counted) the driver prices the row with the `OpenedSession.usageRow` the factory returned (`createPlatformModelAgent(...).usageRow`; `estimated: true` for an unlisted model), else records the event's own `costUsd` as reported, else an unpriced row (provider data unavailable); the row's `key` is `{sessionId}:{epoch}:{seq}` so a replay folds once. `ledgerRecorder` appends it to `{ws}:ledger:{yyyy-mm}` one-way (the books never stall a turn) and, when the session works a task, charges `Task.recordUsage`; a `failed {budget}` task comes back as the verdict and the driver cancels the running turn — on the served session locally, through the `CommandSink` on the daemon path. `maxCostUsd`, `maxTokens` and `maxWallMs` are what the Task can measure today; `maxTurns` / `maxSteps` are runtime-side (`modelAgent({ maxSteps })`, `claudeCode({ maxTurns })`).
- API keys are user-provided (BYO), encrypted in Registry with `WORKSPACE_KEK`. As implemented (#230): a local runtime reads a secret its manifest declares through `RuntimePluginAccess.secret(name)` → `Registry.openSecret(name, pluginId)`, called as the workspace owner (the session's agent principal does not exist yet), so the plugin must be enabled and hold `secret:<name>`, and every open is audited `secret.opened` — once per session open (and once more if an evicted session is re-opened), never per turn. The plaintext lives for the length of the `open` call and is never cached in the isolate or written to a record. No `anthropic-api-key` → the open fails `no-api-key` naming `/plugins/anthropic-api` (task `session-open`); a plugin turned off between the gate and the open → `plugin-disabled`. Until #231 wires the catalogue into `apps/web`, the deployment still runs the deprecated `anthropic` resolver (no `registry` option → no secret lookup).

The daemon (#479, #481, #484), the Machine actor (#480, #481, #484), elevation (#478) and the page (#482) implement it; the seams are below and in §9.

**Lifecycle frames** (#359, contract; tracking #358): `update.*` and `harness.*` reach only a daemon whose `hello.features` lists `update` / `harness` — an older daemon drops a frame it cannot decode and keeps the socket. `ReleaseManifest`, `ReleaseAsset`, `UpdatePhase`, `HarnessPhase`, `HarnessReport` and `UpdatePolicy` are types in `@agentic/core` (`release.ts`); `compareVersions` / `platformKey` are runtime helpers in `@agentic/daemon-protocol` (#360). A host-side end is a `session.closed` with a `code` — no separate suspend frame: resume is the platform's, from the last `session.ref`. The schemas here are minimal; #360 bounds them.

**The machine owns the history** (#397; CHT-08, CHT-10, OPS-05, OPS-10; tracking #387 decisions). A daemon session's event stream is on disk on the machine before the platform sees it (the NDJSON log `serveSession` appends to), and that copy is the authority a reconnect replays from — so it is the copy that lives. The platform keeps a bounded recent window (the record's `events` plus the newest `RETAINED_PAGES` `SessionPage`s, §4) and asks for anything older with `history.request`: the events strictly after `from` up to an inclusive `to`, at most `limit` (`HISTORY_LIMIT` = 500) and about half a frame of JSON (`HISTORY_RESPONSE_BYTES`), `more` when cut so the reader asks again from the last event it got. `from` may be a platform-stamped cursor (`platformCursor`, a fractional `seq`): the log's next integer follows it. Platform-raised events (`ask_user`'s `request` / `request-resolved`, `finishInterrupted`'s) are the platform's alone — they never reach the daemon's log — so a forgotten range read from the machine holds the runtime's events; their decisions stay in the record's index (#391) while a request is open. A session the daemon no longer runs is still answered from its file (a restart loses no history); a session it has no log for is `unknown-session`; a range retention already forgot is `gap` with `earliest`, the oldest cursor still held — never an empty result that looks like history. **Machine-side retention**: after every `turn-end` the pump sends, the daemon trims that session's log to `retention.maxBytes` (`DEFAULT_LOG_MAX_BYTES` = 64 MB; `0` keeps everything) of the newest whole turns — the cut lands on a `turn-start`, never inside a turn, and runs after the turn is on disk, so `watchTurns`' own consumer of `served.events()` (#394) and a reconnect's `wanted` cursor still reach everything recent; `NdjsonEventLog.retain` is one `stat` while under budget, one pass past it, and `truncate` reads and rewrites inside the per-session write queue so a line appended meanwhile is kept. What a truncation forgot is a named `gap` to `history.request` and to a reconnect alike. `daemonConformance` has a `history` case (feature `history`): the same event frames the session streamed, `to` inclusive, `limit` + `more` continuing without a duplicate or a hole, `unknown-session`, and after `truncateLog` a `gap` naming `earliest` while the kept range still answers; the in-memory daemon answers from its per-session log (its `historyHole` fault proves the suite catches an empty answer where a gap is due).

**Folder browsing** (#185, frames #187, locate #331): `fs.request` asks a daemon for the immediate subfolders of a folder, to `git worktree add` a new branch, or for every checkout of a repo's origin, always inside the named environment's `cwdRoots`. `fs.response` answers with one of three things:
- a listing `{ path, parent?, git?, entries: [{ name, path, git? }] ≤ FS_LIST_MAX_ENTRIES, truncated }`, where `parent` is absent on a root and `git` is `{ kind: repo | worktree, branch? | head?, origin? }` — `origin` is the `origin` remote's URL as written in the repo's config, the repo's identity across machines (compared with core's `sameOrigin`);
- the added worktree `{ path, branch }`;
- the located checkouts `{ origin, matches: [{ path, git }] ≤ FS_LOCATE_MAX_MATCHES, truncated }`, roots first, shallowest first.

Refusals are named: `outside-roots`, `not-found`, `not-a-repo`, `branch-exists`, `invalid-branch`, `exists`, `timeout`, `unknown-environment`, `unsupported` and `internal`. The shared lexical check is core's `pathWithin`, and the daemon additionally resolves symlinks. `daemonConformance` has `fs-list` and `fs-locate` cases for daemons that declare the `fs` feature (`fs-locate` proves a match when the harness names a `knownOrigin`). As implemented in `agentic-daemon` (#188, `apps/daemon/src/fs.ts`): every path is checked lexically first (answered `outside-roots` before the disk is touched), then again after `realpath` of the path and of every root, and all reads go through the resolved path; `session.open` runs the same check on its `cwd` and refuses a missing one. Git badges are read from `.git` / `HEAD` / `config` files, never by running git — `origin` from the common config (`<gitdir>/config`, or for a worktree the config its `commondir` points to). A `locate` walks each root breadth-first at most `min(depth, FS_LOCATE_MAX_DEPTH = 3)` levels down, skipping `node_modules` and dot-folders, following a symlink or junction only when it resolves to a folder inside the roots and never visiting a resolved folder twice, and stops at `FS_LOCATE_MAX_MATCHES = 20` with `truncated: true`; a root missing on disk holds nothing. `worktree` runs `git -C <repo> worktree add -b <branch> -- <path> [base]` through `execFile` with no shell and a 60 s timeout, after `git check-ref-format --branch`.

**The `agentic-daemon` command** (#354, `apps/daemon/src/launcher.ts`): the daemon ships as an unpacked folder started by a service, so nothing puts its CLI on `PATH` — yet every instruction the product gives (Machine page, Pair page, both READMEs, the runbook) is spelled `agentic-daemon …`. The install scripts call `launcher install`, which writes a launcher that hard-codes the Node and entry the install resolved (so it runs where no Node is on `PATH`) and then takes the least invasive route onto `PATH`: its own folder already there → nothing, `~/.local/bin` or `~/bin` on `PATH` → a symlink, otherwise a fenced block in the profile `$SHELL` names, or the Windows **user** `PATH` via `[Environment]::SetEnvironmentVariable`. `launcherPlan` decides all of it from injected `platform` / `env` / `home` and touches no disk, so every OS's decision is tested from any one of them; `launcher remove` (the uninstall scripts) undoes each route. The web end is the Machine page's "command not found?" disclosure (`pages/machines/manage.ts` `fallbackCommand`), which spells the same command as `node <install folder>/bin/agentic-daemon.mjs …` for a machine installed before this.

**`agentic-daemon open`** (#336, `apps/daemon/src/open.ts`): the command-line entry into a chat, and no daemon frame — the daemon resolves the folder locally and the web resolves everything else from the query. `open [path] [--env <id>] [--no-browser]` takes the folder (default the current directory) and, over the daemon's own `environments.json`, finds the environment whose `cwdRoots` contain it with `checkWithinRoots` (lexically, then with links resolved, so the answer is the one `fs.request` would give); no environment → exit 1 with every environment's roots listed; several → exit 2 naming them until `--env <id>` picks one (checked the same way, exit 1 when the folder is not under its roots). It reads the folder's `gitInfo` for the `origin` (absent when the folder is not a checkout), prints `<platform>/chats/new?env=<id>&path=<lexical native path>[&origin=<url>]` (each value `encodeURIComponent`-ed; the platform URL from `credentials.json`, normalized as `pair` normalizes it) and opens it with the OS opener (`cmd /c start "" "<url>"`, `open`, `xdg-open`) unless `--no-browser`; the link is printed before the opener runs, so a headless box still gets it, and an opener that fails is a note, not a failure. Unpaired, or an unloadable `environments.json`, is exit 1 like `run`. The web end is §10 "Entry points".

**Web-managed environments** (#224, frames #236; decisions 2026-09-19 (c)): `env.request` asks a daemon to create or change (`put`, an upsert) or to `remove` an environment. `EnvironmentInput` is `{ id?, name, runtime, cwdRoots, concurrency?, accountLabel? }`.
- It has **no `profileDir`**. The daemon allocates one per environment, and its schema is strict: a frame whose input carries any key the contract does not name fails validation instead of having the key stripped.
- `env.response` answers with `{ environmentId }` or a named refusal: `policy-disabled`, `outside-allowed-roots`, `unknown-runtime`, `in-use`, `unknown-environment`, `invalid`, `io` (and `timeout`, which only the platform sets).
- The descriptors themselves travel in an `env` frame that comes with a `result`, before or after it.
- `hello` and `env` carry the optional `policy: { webManaged, allowedRoots, source?, requested?, locked? }`, the machine's policy as it stands. Since #355 the web sets it through `policy.request` (below); a daemon that predates it sends none, and one whose owner locked it reports `locked` and refuses every request.
- `daemonConformance` has `env-put`, `env-remove` and `env-policy` for daemons whose harness declares the `env-manage` feature. `agentic-daemon` does not declare it until it answers the frame (#238); the Machine actor's end is below.

The Machine actor is the platform end (#189). The daemon's reply arrives as a separate `socketMessage` turn on the same actor, so the answer is a **stored result**, never an awaited promise:
- `fsRequest(environmentId, op)` → `{ requestId }` (`fs_<uuid>`) validates the op against the protocol schema (400), refuses a revoked machine (403), an unknown environment (404) and an offline machine or one with no open socket (503), sends `fs.request` and stores `fs[requestId] = { environmentId, op, status: 'pending', requestedAt, deadline, by }`. `list` is open to session drivers (a user, an agent, an external client with `sessions`); `worktree` changes the machine and `locate` walks every root of it (#332), so only its owner (a user principal) may ask for those — checked inside the method, since `methodAuthorize` sees only the method. The router's driver is the workspace user, so a project feature plugin's `fs` (§7) may ask for both.
- `fsResult(requestId)` → `FsResultView { requestId, environmentId, op, status: pending | done | error, requestedAt, finishedAt?, result?, error? }`, 404 for an unknown, evicted or pruned id; one string argument, so the UI reads it live with `useActorState(defs.Machine, () => [k, 'fsResult', id], { live: true })`. Same principals as `fsRequest`.
- The `fs.response` case stores the result or error. An unknown id is ignored, and so is a second answer, except over a `timeout`: a late answer says what the daemon did. A result of the wrong kind is stored as `internal`.
- Bounds: a pending request fails `{ code: 'timeout' }` at its deadline (`fsTimeoutMs`, 30 s) through the `liveness` reminder, which stays armed while any request is pending; `socketClosed` fails every pending one with `timeout` "machine went offline" (`revoke` with "machine revoked"). At most `MAX_FS_REQUESTS` (16) entries are kept, the oldest evicted first, and finished ones are pruned `FS_RESULT_TTL_MS` (2 min) after they finished (on the next `fsRequest` or reminder tick).
- A successful `worktree` records `workdir.worktree-created` (§4 Audit) under the principal that asked, keyed `{machineKey}:worktree:{requestId}`.

Environment requests use the same machinery (#237):
- `putEnvironment(input: EnvironmentInput)` / `removeEnvironment(environmentId)` → `{ requestId }` (`env_<uuid>`) send `env.request` and store `envRequests[requestId] = { op, status: 'pending', requestedAt, deadline, by }`; `envResult(requestId)` → `EnvResultView { requestId, op, status, requestedAt, finishedAt?, result?, error? }`, read live like `fsResult`. The input is parsed by the strict `environmentInput` schema (400, so a `profileDir` never leaves the platform); 403 revoked; 503 `machine-offline` with no daemon or no open socket. `removeEnvironment` also refuses an environment the machine does not report (404) and one with a turn running or a session queued in it (409 `in-use`, naming them — #394); idle hosted sessions are closed first (`session.close`), and the daemon checks its own side too.
- **Owner only, and on no tool surface.** An agent must not widen where agents may work (decisions 2026-09-19 (c)): `methodAuthorize` admits a user principal only, and a source scan (`packages/platform/__tests__/machine/tool-boundary.test.ts`) fails if the platform tools, the daemon `tool.call` port or the platform MCP server ever call the methods — the policy, restart, log and login methods of #355 included.
- **The policy itself is set from the web (#355, #480; decisions 2026-09-22 — supersedes "edited only on the machine").** The Machine keeps the **desired** folders (`policyDesired`), set by `setPolicy` (owner, elevated — `requireElevated`) or preset on the Pair page (`registerMachinePending({ allowedRoots })` → `claimPairing` → `pair`), and sends them as `policy.request { op: 'set' }`; the daemon expands `~` to its user's home, checks every folder as `allow-root` does, writes `policy.json` with `source: 'web'` and `requested` (the roots as asked), and answers `policy.response` (read with `policyResult`) after the `env` frame carrying the policy. Convergence is core's `policyConverged(desired, reported, os)`: `source: 'web'` and the same requested strings, `~` literal — no home directory reaches the platform. **Reconcile** (`shouldReconcile`, `machine/policy.ts`): on `hello` and `env` only, once per drift, never while a request is in flight, never to a `locked` machine, and after a refused automatic request only when the owner changes the set or the daemon reconnects — one request per connect plus the local drifts, no loop. `browseMachine(path?)` (owner, elevated) lists the machine's folders for the picker. `allowBypassPermissions: true` on `putEnvironment` for an environment that lacks it is elevated; `revoke` is elevated; `rename` is audited (`machine.renamed`); the first elevated change of an elevation window records `auth.elevated`. `agentic-daemon policy lock` on the machine refuses every request `policy-locked` and the page shows the unlock command.
- The daemon decides. Its refusal (`policy-disabled`, `outside-allowed-roots`, `unknown-runtime`, `in-use`, `invalid`, `io`, `unknown-environment`) is stored unchanged; the descriptors arrive with the daemon's `env` frame. Timeout, disconnect, revoke, the late-answer rule and the bounds (`envTimeoutMs` 30 s, `MAX_ENV_REQUESTS` 16, `ENV_RESULT_TTL_MS` 2 min) are the folder requests'.
- Each answered request is recorded once — `environment.put` / `environment.removed`, keyed `{machineKey}:env:{requestId}` — with the roots that were asked for and the outcome (`ok` or the daemon's code). An unanswered one is not: whether the daemon applied it is unknown until it answers.
- `MachineView.policy` is the `MachinePolicy` from the last `hello` (dropped when a daemon sends none) and any `env` that carries one, so the Machine page can explain "web management is off on this machine" and offer the local command.
- **Sign-in from the web (#484):** `requestLogin(environmentId)` (owner, not elevated — signing in narrows nothing; 404 an environment the machine lacks, 409 a daemon without the `login` feature or a runtime whose `CapabilityReport.login` is not `relay`, or a sign-in already running for it, 503 offline) sends `login.request` and keeps `logins[environmentId] = { requestId, phase, startedAt, deadline, by }`; the daemon's `login.status` frames move `phase` and set `action` / `error`; `answerLogin(environmentId, text)` forwards the pasted text as `login.answer` inside the call and stores it nowhere (400 empty or over `LOGIN_ANSWER_MAX_CHARS`, 409 when nothing is expected); `cancelLogin` sends `login.cancel` (offline, it ends the record `cancelled` here); `loginState(environmentId)` is the live read. A disconnect fails a running one `failed`, a revoke `cancelled`, the liveness reminder `timeout` past `LOGIN_TIMEOUT_MS` (eleven minutes, past the daemon's own cap); an ended one is kept `LOGIN_RESULT_TTL_MS`. Every end is audited `machine.login { environmentId, outcome }`. The daemon (`apps/daemon/src/login-relay.ts`) runs the runtime's own CLI with piped stdio and parses it; the page (`LoginDialog`) shows the link or the device code.

History requests (#397) use the same machinery, with one difference — the answer is not stored on the record:
- `historyRequest(sessionId, range: HistoryRange)` → `{ requestId }` (`history_<uuid>`; session drivers, like `sendCommand`) sends `history.request` and stores `history[requestId] = { sessionId, range, status: 'pending', requestedAt, deadline }`; 403 revoked, 503 `machine-offline` with no daemon or no open socket. The session need not be hosted here any more: the log outlives the runtime session.
- The `history.response` case turns the record `done` — the events (unwrapped from their `event` frames) go to an activation-local map, never to the record, since one answer weighs up to half a frame and the Machine record is saved whole — or `error` with the daemon's code stored unchanged (`gap`, `unknown-session`, `internal`).
- The stream `historyAnswer(requestId)` yields once: the events (with `more`), or the error — when the response has landed, or the request failed (`historyTimeoutMs` 30 s through the `liveness` reminder, `socketClosed`, `revoke`, all `internal`); an id the record does not hold, or an answer the activation no longer has, is `internal` too and the caller asks again. `historyResult(requestId)` is the status view, `MAX_HISTORY_REQUESTS` 16 / `HISTORY_RESULT_TTL_MS` 60 s the bounds.
- `machineHistorySource(() => Machine)` (`packages/platform/src/machine/history.ts`) is the Session's `HistorySource` over the two: a fresh `actor()` call as the workspace user (the Session's own turn is where it runs; the answer arrives on a Machine turn of its own), `historyRequest` then `for await` on `historyAnswer`. `apps/web` wires it as `defineSessionActor({ history })`; without the port a Session forgets nothing.

- Machine DO routes `session.frame` → `actor(Session, id).forwardFrames(frames)` (one-way; `hello` records capabilities and lifts `disconnected` — not the ref it carries, which is the open's placeholder; `event` folds, `gap` marks `disconnected` and moves the head); `session.ref` → `Session.noteRef(ref)` after updating the hosted session's own `ref` (#389: the runtime's id, appended only when its identity — `id`, `data.epoch` — changed; a session the machine does not host is ignored); `session.title` → `Session.noteTitle(title)` (#460: nothing is kept on the record — it publishes a `title` session event to its chat; a session the machine does not host is ignored, and a record's refusal is swallowed like a frame's); `session.reply` → `Session.commandReplied` (a prompt ack marks the turn running, its `turn-end` frame snapshots the transcript and posts to the chat); `tool.call` → the platform tool under an **agent principal** `{kind: 'agent', ws, agentId, sessionId, taskId}` so Memory/Task authorize correctly. The Machine mints that principal from the task the session was OPENED for (`HostedSession.taskId`, fixed at `openSession`) — identity only: the turn owns the task (#390, §5a), so `createToolCallPort` (`routing/tool-call.ts`) reads the Session once per call and rebuilds the principal with `running.taskId ?? spec.taskId` before the tool runs; the same read gives `chat_post` / `ask_user` their chat and the memory tools their gate. One Session hop per daemon tool call, on a path that is already detached from the socket's turn. A Session's refusal of a `session.frame` or a `session.reply` (403 from `assertHostingMachine`: a session this machine does not host on the record — stale after a daemon restart, re-opened elsewhere, never opened here) never reaches the Machine (#393, #492): every hand-off to the Session — `forwardFrames`, `noteRef`, `noteTitle`, `commandReplied` — is dispatched one-way, so the Machine's turn ends at the Session's acceptance and a refusal, or any other failure of the record's turn, is dropped where it lands (dev: a host warning); what the dispatch itself throws — a failure before acceptance, an authorization or placement bug — still surfaces. The frame is dropped and the socket stays up, since the host's `webSocketMessage` would otherwise take every other session on it down with the throw — and the Machine is never held by a Session's slow turn-end (§3 "Hub turns"): a session's slow turn used to queue every other session's frames and every placement read (`get`, `openSession`) behind it, up to the 30 s deadline.
- Session → daemon: `Session.prompt` records the command as pending (idempotent while the reply is out) and hands it to the `CommandSink` port — the app binds it to `actor(Machine).sendCommand(sessionId, cmd)` → socket. Pending replies are stored in Machine state with a deadline so evictions do not leak promises.
- Reconnect: the daemon redials with backoff; `welcome.wanted` cursors drive gapless replay from the daemon's per-session NDJSON log (`%LOCALAPPDATA%/agentic/sessions/{id}.ndjson`); beyond that a `gap` marks the Session `disconnected` with "events lost" (OPS-04, distinct from failure). After a daemon restart a wanted session is replayed from that log and closed with `code: 'restart'`; the platform re-opens it with `spec.resume`, on the same log and a head that continues (#363).
- **Driver seam** (`@agentic/core` `RuntimeDriver<S, P>`): the daemon reads `LocalEnvironment` rows from `environments.json`, asks the driver to `inspect(env)` (auth status, isolation, `CapabilityReport`) and runs its `doctor(envs)` for `hello` / `env` via `toEnvironmentDescriptor` (the per-environment verdict `EnvironmentDescriptor.doctor = environmentVerdict(report, id, checkedAt)`; a throwing driver gives each of its environments an error verdict `driver-doctor-failed`), `open(env, OpenSpec, { sessionId, callTool, policy })` → `{ session, capabilities, title? }` on `session.open` (`title()` — the runtime's current title for the conversation, when the runtime keeps one (#460): the Claude Code driver reads the newest `custom-title` / `ai-title` row from the tail of `<configDir>/projects/<slug(cwd)>/<sessionId>.jsonl` (`readSessionTitle`), the Copilot driver keeps the CLI's `session.title_changed`; Codex has `thread/name/updated` but the driver does not read it yet), and runs `doctor(envs)` for `agentic-daemon doctor`. `callTool` is how a driver's platform tools reach the socket as `tool.call`. The daemon never branches on the runtime id; it picks the driver whose `runtime` matches the row.
- Multi-account isolation = `CLAUDE_CONFIG_DIR` per environment (the adapter's env allowlist passes it through). `claudeCodeDriver` (`@agentic/runtimes/claude-code`, #20) sets it from `profileDir` and removes the daemon's own `CLAUDE_CONFIG_DIR` and `ANTHROPIC_*` from every child, so an environment can only ever use its own account; `inspect` reads auth status from `<config dir>/.credentials.json`; every session runs with Claude Code's cross-session tools (`ListAgents`, `SendMessage` — they reach the operator's other Claude Code sessions, not platform agents, and run without a permission request) in the SDK's `disallowedTools` (#194, `withoutCrossSessionTools`); the memory block reaches Claude Code as `## Platform memory` and the `CapabilityReport` lists `memory.runtime` (CLAUDE.md, settings — loaded from the folder with `settingSources: ['project']`, #461, but the project's, not platform memory) as unsupported (MEM-10). macOS Keychain behaviour is unverified, so v1 validates Windows only; `doctor()` implements EXE-07 with the codes in `CLAUDE_CODE_DOCTOR_CODES` (`shared-config-dir` is the error). Isolation is pinned by `packages/runtimes/__tests__/claude-code/isolation.test.ts` (three profiles: every child env equal to the others except its own `CLAUDE_CONFIG_DIR`, a session in one profile changing nothing about another, a shared config dir refused and its verdict failing exactly the two) and AC-02 by the routing test "multi-account environments on one machine" (three environments selectable through Routing, every `session.open` naming the chosen one, accounts and verdicts untouched by execution); `docs/multi-account.md` has the mechanism, the verified / unverified matrix and the manual checklist for the real CLI (#43).
- Shared harness pieces (#318, `packages/runtimes/src/harness/`): `bridgedPlatformTools`, `openDaemonConnectors` / `withConnectorPolicy`, `profileEnv` (strip the parent's account variables, set the profile's home), `withPlatformMemoryLabel` / `withUnavailableConnectors`, `harnessCapabilityReport(subject, caps)` and the session guards (`assertCwdInRoots`, `assertRuntime`, `closingWith`). Claude Code uses them; the Copilot CLI (`copilot-cli`, `COPILOT_HOME`) and Codex (`codex-cli`, `CODEX_HOME`) drivers reuse them (#317).
- Copilot CLI (#319, `@agentic/runtimes/copilot-cli`): `copilotCliDriver` runs one `@github/copilot-sdk` client per environment, with `COPILOT_HOME = profileDir` and the parent's GitHub token variables stripped. Its `copilotCli` agent maps Copilot session events onto the event wire. Copilot's permission requests go to the daemon-compiled policy. Platform tools and connectors are native client tools, ruled on in their handler. The doctor codes are `COPILOT_CLI_DOCTOR_CODES`, and `shared-login` flags a profile running on the machine's `gh` keyring login.

- **Harness packages** (#369; EXE-08, PLG-02, PLG-09): the runtimes' native builds are not in the daemon zip (≈ 330 MB → ≈ 8 MB). They ship as separate release assets, and the daemon installs them into its own store.
  - **Packages.** `scripts/package.mjs --harness <runtime>` builds `harness-<runtime>-<version>-<os>-<arch>.zip` (the version in the name, so a zip is uploaded once per pinned version, #441): the runtime's native npm package for that platform, at the version the lockfile pins (the SDK's own, which pins its native package), laid out as `node_modules/<package>/…`, plus `manifest.json { runtime, version, platform, binary, packages, sha256 }`. `sha256` is the tree digest (`treeHash`: over `<path>\0<file sha256>\n` in path order); `binary` is the executable. `resolveClosure` leaves every platform's native package out (`isNativeHarnessPackage`). The release workflow builds a runtime's zips on every matrix OS when its pinned version is not on `daemon-latest` yet (all three on a tag; `manifest.mjs plan` / `stale`), and `manifest.mjs` lists them as `ReleaseManifest.harnesses[runtime] = { version, assets: { '<os>-<arch>': ReleaseAsset } }`. The table of SDK, native package and executable per runtime is `scripts/lib/harness.mjs` for packaging and `BUILTIN_HARNESSES` in `apps/daemon/src/harness.ts` for the daemon; `package.test.ts` keeps the two equal.
  - **Store and locator.** The store (`harnessStore`) keeps `<install root>/harnesses/<runtime>/<version>/` and `<runtime>/current.json { version, installedAt }`. `locate(runtime) → { version, dir, binary, source, installedAt } | undefined`.
    - Without `current.json` it falls back to the native package beside the SDK in the daemon's own `node_modules` (`source: 'bundled'`): a workspace checkout, never the release zip.
    - `state()` tells ready, missing and broken apart: `current.json` naming a version that is not there, a manifest that does not match, or a missing executable.
    - `stage` downloads a `ReleaseAsset`, checks its sha256 and size, unpacks it one entry at a time (`extractZipFile`; an entry leaving the directory is refused), and checks the runtime, version, platform and tree digest. It lands in `<version>/` beside the current one; `activate` switches `current.json` and `prune` removes the rest.
    - `hello.harnesses` / `harnesses` are its `reports()`. `current` there means the version this daemon's SDK pins.
  - **Drivers** (`builtinRuntimes({ harnesses })`). Each driver runs the located executable, and a runtime without a harness is still registered, as `harnessMissingDriver`: `unknown` sign-in, no capabilities, a `harness-missing` doctor error, and `open` throws `HarnessMissingError`, which the daemon answers `session.closed { code: 'harness-missing' }`. `rebuild(runtime)` builds a driver again; the quota sources are stable wrappers over whichever build is current. `doctor` names each harness and, for a missing one, a `claude` / `copilot` / `codex` on `PATH` — a hint only: the daemon never runs it.
  - **How each SDK is pointed at its executable (the spike, #369).**
    - Claude Code: the Agent SDK's `pathToClaudeCodeExecutable` → `claude(.exe)` at the root of `@anthropic-ai/claude-agent-sdk-<os>-<arch>`, also passed to the quota probe.
    - Codex: `codexPath` → `vendor/<target triple>/bin/codex(.exe)` of `@openai/codex-<os>-<arch>`, which is what `@openai/codex`'s launcher would run. `codexCommand` spawns a native path directly.
    - Copilot: `@github/copilot-sdk` 1.0.14 does have an override. `CopilotClient` takes `connection: RuntimeConnection.forStdio({ path })`, and honours `COPILOT_CLI_PATH` in its `env`, before it would resolve `@github/copilot-sdk-<os>-<arch>` beside itself (`ensureRuntimeBundle`). The spawned `prebuilds/<os>-<arch>/copilot-runtime(.exe)` loads `runtime.node` and the auth libraries next to it. So the harness carries only the platform package, the SDK's JavaScript (and `koffi`) stays in the daemon zip, and no `createRequire(<harness dir>)` is needed. The seam is `CopilotClientInit.cliPath` in `copilot-cli/sdk.ts`: `loadCopilotClient` turns it into the stdio connection, and the daemon passes it through the driver's existing `createClient`. `copilot-runtime` is not a user CLI (it refuses `login`), so `env login` for Copilot still runs `copilot` on `PATH`; Claude Code and Codex sign in with the harness executable.
  - **`harness.request`** (the `harness` feature). Requests run one at a time.
    - `install` / `update` emit `downloading`, `verifying` and `staged` from the store.
    - They then drain only that runtime. Its turn-starting prompts get `drainingReply` and a new `session.open` on it gets `code: 'draining'`, while other runtimes run on. The drain waits for the runtime's running turns, up to `HARNESS_DRAIN_TIMEOUT_MS` (10 min), or not at all with `mode: 'now'`. The `draining` phase is sent only when the runtime has live sessions.
    - `applying` closes its live sessions with `code: 'harness-update'` through the same `closeSession` as `stop`, disposes the driver, activates the version, rebuilds the driver and re-inspects: `env` goes out only when a descriptor changed. The old version is then pruned.
    - It ends with `done` and a `harnesses` frame. The platform re-opens the sessions from `spec.resume` (#420).
    - `remove` is refused `in-use` while any environment's runtime is the one named, and `not-installed` when the store has none. Failures are named: `invalid`, `download-failed`, `checksum`, `invalid-package`, `in-use`, `not-installed`, `io`, `unsupported`.
  - **`agentic-daemon harness list | install | update | rm`** (`harness-cli.ts`) uses the same store and reads the installers' manifests. By default a stable build reads its own `daemon-v<version>` release, anything else `daemon-latest`; `--version`, `--channel` / `AGENTIC_CHANNEL`, `--manifest` and `AGENTIC_RELEASES` override that. It does not drain or prune: a running daemon takes a terminal install on its next start, and prunes unused versions then (a live hand-off is #444). The installers install `AGENTIC_HARNESSES` (default all three, `none` for none) from the manifest they read, through the zip's `install.* --harness … --manifest …`.
  - **Selection and the heal on start: the migration.** A machine installed after #364 but before this change runs a daemon whose zip bundles the runtimes, and it takes updates. Updated to a build without them, it would start with no `<root>/harnesses/*`, and every runtime would be `harness-missing`; an `auto-when-idle` policy would do that unattended. So the daemon heals itself.
    - `<root>/harnesses/selection.json { runtimes }` records what the machine wants. The installers write `AGENTIC_HARNESSES` there with `harness select` (`none` → `[]`); `harness install` adds to it and `harness rm` takes out.
    - A **missing** file means every built-in runtime. That is the case for an updated machine from before the selection existed.
    - `run` under an install root passes `harnesses.heal = { manifestUrl }`: its own channel's manifest (`DAEMON_CHANNEL` `stable` → `daemon-stable`, `latest` / `dev` → `daemon-latest`; `AGENTIC_RELEASES` honoured).
    - After `start`, queued with the harness requests, the daemon installs every selected runtime it has a driver for whose harness is not ready. Each goes through the same `stage` → `activate` → driver rebuild as `harness.request`, logs, and sends a `harnesses` frame (and `env`, when the verdicts change). Until then `session.open` on that runtime is refused `harness-missing`.
    - A failure (no manifest, no build for this platform, a bad download) is logged and recorded in `<root>/harnesses/failures.json`. `doctor` shows it (`harness-install-failed`), the next start tries again, and a successful install clears it. It is never fatal.

- **Daemon** (`apps/daemon`, #19; the lifecycle: tracking #358, decisions 2026-09-21). Operating it: `docs/runbook.md` §5.
  - **Pairing and the socket.** `agentic-daemon pair <code> --url` posts to `POST /auth/pair` and stores `{url, workspaceId, machineId, token}` in `%APPDATA%/agentic/credentials.json`, owner-only (`icacls /inheritance:r /grant:r user:F` before the token is written; `0600` elsewhere). `run` dials `/_agentic/daemon/{machineId}` with `Authorization: Bearer <token>` (never in the URL), redialling with exponential backoff and jitter; every log line is redacted of the token.
  - **Session log and ref.** The session log is keyed by the **platform** session id (`ndjsonEventLog(dir).forSession(sessionId)` as the `serveSession` `eventLog`) — a runtime names its sessions its own way. `session.opened.head` is the served head, `(0, 0)` before any event — except on a re-open (below); `hello.resume` is the later of the head and the last frame sent. `session.opened.ref` is whatever the runtime calls the session before its first prompt — the Claude Code adapter's `ref` is a live getter whose id is a `cc_…` placeholder until the CLI's `system/init` event names it — so the daemon remembers the ref the platform last heard per session and, after every frame its pump sends (and at each pump start, which covers a reconnect), reads `session.ref` again and sends `session.ref {sessionId, ref}` when the identity (`id`, `data.epoch`, never the object) changed (#389). It is never tied to `turn-end`: a turn that errors before it ends still named the session. The title is (#460): after every `turn-end` seen off the served stream (`watchTurns`, so it lands while the platform is away and goes out at the next pump start), the daemon asks the driver's `title()` and sends `session.title {sessionId, title}` when it differs from the one the platform last heard; a turn that brought no new title is followed by one re-probe `TITLE_RECHECK_MS` (10 s) later, since a CLI titles from a background call that a short first turn outruns; a session re-opened from a ref is probed once at open. A probe that fails is logged, never the session's problem. Because `serveSession` replays whatever the store holds when its buffer has moved on, the daemon's pump checks each frame follows the last (next seq, or seq 1 of a later epoch) and sends a `gap {from: wanted, resumeAt}` before a hole. `session.open` is refused with a reason for an unknown environment, a runtime without a driver (or without a harness, `harness-missing`), a `cwd` outside `cwdRoots`, or a full environment (`concurrency`).
  - **Close codes and re-open** (#363; OPS-04/05/06, EXE-12). `Daemon.stop({ reason: 'stop' | 'restart' | 'update' | 'harness-update' })` closes each live session while the socket is up with `session.closed { code: reason }` (no code for a plain `stop`), then flushes the logs; `run` maps SIGINT / SIGTERM to `restart` and `until → 'update'` to `update` (the update client), and `harness-update` is the harness store's (#369). On Windows `Stop-ScheduledTask` kills without a signal, so the coded close is best-effort there — the platform treats an uncoded close the same (#420). A wanted session the daemon no longer runs (restart) is replayed from its log, then `session.closed` — with `code: 'restart'` when a log shows the machine ran it, as `unknown session` with no code otherwise. The platform owns resume: it re-opens a lost session under the same id with `spec.resume = session.ref`, and the daemon keeps **no session manifests**. The driver re-opens the runtime conversation (every driver forwards `spec.resume`; one that throws is answered `session.closed { code: 'resume-failed' }` and the platform starts fresh), the served session appends to the same NDJSON log, and `session.opened.head` is `(epoch, 0)` of the runtime's later epoch — the ref's `data.epoch`, which every driver reports, or else the log head's epoch + 1 — so it continues after the log's head. `serveSession` has no seam for an initial head, so the daemon keeps that base per live session (`LiveSession.base`) and reads the later of it and the served head (`headOf`); an upstream `serveSession({ head })` would remove it (`docs/promotion.md`). `inMemoryHarness()` does the same (`restart()`, the `resume` conformance feature) and `session-reopen` passes for both.

- **Capacity counts running turns, not open sessions** (#394; EXE-03, EXE-09, EXE-11). Once a chat member's session lives for the chat's life (#393), counting open sessions would let the first member own its environment and refuse every other chat, delegated child and scheduled run, and would make the environment impossible to remove. So `concurrency` bounds the turns in flight. On the daemon (`apps/daemon/src/daemon.ts`) each `LiveSession` carries `running`: set when a `prompt` command is taken (tentatively while its reply is out, kept on the ack), cleared when the turn's `turn-end` passes a per-session watcher on the served stream (`watchTurns` — off the socket pump, so a turn that ends while the platform is away still frees its slot). `session.open` is refused `at capacity` only when `env.concurrency` turns are running; a `prompt` that would start one beyond that is answered with the wire `busy` error before the runtime sees it (a session already running a turn is left to the runtime — a steer, or its own `busy`); the descriptor's `concurrency.active` reports running turns; the quota probe's "idle" is "no turn running". The Machine mirrors it: `HostedSession.running { turnId, since }` is set by a prompt's ack in `onSessionReply` and cleared by the turn's `turn-end` in `onSessionFrame`, and `activeIn` / `freeSlots` (`machine/state.ts`) count the hosted sessions that are running a turn or have a prompt pending — a slot is taken when the prompt leaves, not when its ack lands, so two prompts sent back to back cannot share one. A turn ending dequeues the next queued `session.open` and tells the router `slotFreed`. `removeEnvironment` refuses `409 in-use` only while a turn runs there or a session is queued for it, naming them (session, agent, turn); the idle hosted sessions are sent `session.close` first and the `env.request` follows on the same socket, so the daemon (which still refuses removal while it hosts any session) sees them gone — their chats re-open a fresh session wherever their member runs next (EXE-12). Per-session CPU and memory ride the `telemetry` frame (#400, above); capacity is admission only.
- Envelope contract (`@agentic/daemon-protocol`): one frame per WebSocket text message; `v` is checked before `t` before the schema, so a peer on another version is refused with `unsupported-version` and a malformed message with one of `too-large` (1 MiB, checked before parsing) · `not-json` · `not-object` · `unknown-type` · `invalid`. Every frame kind has a Standard Schema (zod) with bounded strings and lists (`LIMITS`); unknown keys are stripped. A daemon drops what it cannot decode and keeps the socket. `session.frame` traffic waits for `welcome`, so a replay driven by `wanted` always precedes live frames; `wanted` is the last cursor the platform holds and replay starts right after it; a cursor older than the log yields a `gap` frame, never silence. `daemonConformance(harness)` on `@agentic/daemon-protocol/testing` pins all of this from the platform seat (hello/welcome, malformed input, env, heartbeat, session, reconnect replay, gap, tool round trip); `inMemoryHarness()` is the reference daemon it is proven against and a stand-in for tests of the Machine actor. **Lifecycle** (#360): the frames #359 added are bounded too — at most `LIMITS.harnesses` (16) harnesses; an update or harness `target` is a strict `ReleaseAsset` (an `https:` URL, a 64-hex `sha256`, a whole non-zero `bytes`) or, for an update, `'previous'`; `drainTimeoutMs` ≤ a day; a status carries `error` exactly when it is `failed`, and `progress.bytes` ≤ `total`; `session.closed.code` is one of `SESSION_CLOSED_CODES`; a `hello.features` entry this end does not know is dropped rather than failing the hello, so a newer daemon still pairs. An old-style `hello` without any lifecycle field decodes, and an unknown platform frame type is `unknown-type`, which the daemon drops while it keeps the socket. The runtime helpers `compareVersions(a, b)` (semver; `x.y.z-main.<commit unix seconds>.<sha7>` orders below `x.y.z` and main builds by commit time, #437; malformed input lowest), `platformKey(platform, arch)` (the release asset key, `win32-x64`) and `isHttpsAsset` live in `release.ts`. A draining daemon answers a turn-starting `prompt` with `drainingReply` — the session wire's error codes are `@sigx/ai-agent`'s and have no `draining`, so it is `code: 'busy'` (the platform parks it like `busy`) with a message starting `draining:`, told apart by `isDrainingReply`. The conformance features `build`, `resume`, `update` and `harness` add `hello-build` (build and features reported), `session-reopen` (a `wanted` session the daemon lost to a `restart()` is answered `session.closed { code: 'restart' }`; a `session.open` with `spec.resume` re-opens it on a higher epoch), `update-drain` (a turn-starting prompt is refused `draining` while a `session.open` is accepted and the running turn finishes; phases in order; `session.closed { code: 'update' }` for what is left around `restarting`), `update-cancel` (`failed { code: 'cancelled' }`, no restart, new turns accepted again), `harness-install` (phases, then a `harnesses` frame with the new version) and `harness-remove-in-use` (`failed { code: 'in-use' }`). The harness names an `updateTarget` / `harnessTarget`. `inMemoryHarness()` implements `build`, `resume` (#363), `update` and `harness`.

## 6. Chat model

Entries: `msg {author: user | agent{agentId, sessionId?}, parts, mentions, replyTo?, sessionId?, taskId?}`, `member {op: add | remove, agentId, historyAccess}`, `status {agentId, kind: typing | session-started | session-ended | task, ref}`, `coordinator {agentId | null}`.

- Activation (CHT-06): activated = mentions ∩ members; none → coordinator if set; none and exactly one agent member → that agent; otherwise store only. `mentions: 'all'` addresses the group (every agent member). An agent's own post never activates itself. Agent-originated posts may mention other agents (COL-06) with the depth counter from the originating Task. As implemented (#222): a person's post is activated by the browser (`runActivation`); an agent's `chat_post` by the tool port (`createActorToolPorts().chat.post`), which starts a task only for the members the post explicitly mentions (never the coordinator fallback), gated by the poster's `collaborators` (COL-10), at the posting task's depth + 1 (`checkDepth`, so mention chains stop at `maxDepth`), contract from `mentionContract` (origin the message, the last 50 messages the member may read, the member's chat folder, the chat's machine (#414, `ChatSummary.machineId`), else the posting route's environment for an assignee with no default and no account); the tool result lists `activated` and `notActivated` with reasons.
- Each activation creates a Task (origin = the user's message, context = the entries visible to that agent since `historyFrom`, pre-rendered as the "Chat so far" block) and runs it in the member's **one live Session per (chat, agent)** (#393; CHT-01, CHT-11): the router takes the session from the chat's binding below (`sessions[agentId]`) and re-opens it for the task, or opens a fresh one — on the member's first activation, and whenever the bound one cannot go on (closed, its placement moved, or its runtime never named it; the rule is in §7). On a reused session the prompt carries the objective and the entries after the row's `seenSeq` (each message attributed by name, their chat-file parts once, at most the activation's 50), never the pre-rendered block: the engine keeps its own conversation. The session is not closed when the task settles, whatever the turn's outcome; it ends when the agent leaves the chat, the user resets it (#399), the placement moves, or the workspace is deleted. A coordinator and three members hold four live sessions that reach each other through `chat_post` / `delegate` exactly as before.
- Streaming deltas never pass through Chat: the UI subscribes to `Session.tail` for `chat.sessions`. Chat receives only final assistant messages and status through a topic subscription — `topic(SESSION_EVENTS_TOPIC, chatKey)` carrying a `SessionEvent` (`status` → a `status` entry that also maintains `sessions`; `message` → a `msg` entry attributed to the agent; `title` → a `rename` entry with `auto: {source: 'runtime', sessionId}`, #460 below). `typing` is ephemeral and never made durable (CHT-11: a chat coordinates N sessions, never one provider conversation).
- **A chat titles itself (#460):** so the list says what each chat is about. Three sources, ranked heuristic < model < runtime (`packages/platform/src/chat/titles.ts`): the user's first message names an untitled chat by its first line at once (`heuristicTitle`, ≤ 60 chars, in `post`'s own turn; notes and image-only posts do not); after the agent messages `TITLE_AT_AGENT_MESSAGES` = [1, 8] the actor's `title` task asks the `titles` port (`ChatOptions.titles`, a `ChatTitler`; the app composes `createChatTitler({ registry })`: the workspace's `anthropic-api-key` from `Registry.openSecret` as the owner — audited like a session's — then `generateChatTitle` from `@agentic/runtimes`, one `generateText` on `claude-haiku-4-5` over the first 8 messages; no key / plugin off → nothing, and the heuristic stays); a runtime that titles its own conversation (Claude Code, Copilot) reports it through the daemon (`session.title`, §5b) and the Session's `title` event, accepted only from the member's bound session (`sessions[agentId].sessionId`). `acceptsAutoTitle(state, source, sessionId?)` decides: anything names an untitled chat; a person's title (`rename`, `createChat({ title })` — no `auto` on the entry) is never replaced; a source replaces one of its rank or lower; a runtime title is replaced only by the same session's next one, so two members' runtimes never fight. Every generated title is a `rename` entry with `auto: AutoTitle` (core), folded into `title` + `titleAuto` (`ChatSummary.titleAuto`); the task re-checks before writing, so a rename that landed meanwhile wins, and a titler that fails is logged, never said in the thread. Start task (`apps/web/src/pages/task/start.ts`) no longer names the chat by the objective: the objective's post gives the same heuristic title, now one a runtime may improve. The title call is not ledgered (decisions 2026-09-21).
- **What the feed carries and what the entries hold (#398, CHT-08):** a member's session lives for the life of the chat (#393), so its log holds every turn it ever ran — and the chat never replays it. Each feed is anchored at `SessionInfo.transcriptAt`, the cursor of the last turn's end, and carries the turn running now and what follows it, nothing before (a session that has finished no turn is followed from its start while its first turn runs, from its head when idle — `feeds.ts` `feedAnchor`). Everything before the running turn comes from the chat's own entries: each turn's final assistant message is a `msg` entry, so the timeline loses nothing. **Past turns show their final message only** — expanding one does not fetch its event range through `Session.events(from)`; the final message is the durable artefact, the session log is the machine's (#397) and is read on the session page. Opening a chat reads the newest page of entries (`Chat.history(null, 200)`, a live read) and pages backwards from its `next` as the reader reaches the top, down to the caller's `historyFrom`; the pages are merged by `seq` (`keepEntries`), so a stretch the live page has slid past stays on screen.
- **The session binding (#392, CHT-01/CHT-11):** the chat durably knows which execution session belongs to each agent member, so the router finds a member's session instead of minting one. `ChatState.sessions` (and `ChatSummary.sessions`) is `Record<AgentId, ChatSessionRow>` with `{ sessionId, since, seenSeq }` (`packages/platform/src/chat/state.ts`), fed by the reducer alone — no extra hop, so it is replay-safe and eviction-safe: a `session-started` status entry carrying a `ref` creates the row (`sessionId` = the ref, `since` = the entry's `at`, `seenSeq` = 0) or replaces the member's existing one (new id, new `since`, `seenSeq` back to 0); `session-ended` deletes it; a `member remove` deletes it with the member. These two statuses bracket the chat's lifetime of that session, not a single turn's. **The watermark:** when a `msg` entry whose `author` is an agent that owns a row, authored under the row's own `sessionId`, is folded, the entry's reducer-assigned `seq` becomes that row's `seenSeq` — that is the member's own final answer, so every entry after it is what its engine has not seen; another member's or a user's message never moves it, a message from an agent with no row moves nothing, and a late final answer from a replaced session leaves the new row alone. `seenSeq: 0` means "nothing seen in this session" — the router (#393) treats it as "send from the member's `historyFrom`".
- History access (CHT-04): `members[agentId].historyFrom` is the index of the join entry (`'all'` → 0); `history`/`search` filter `seq >= historyFrom` when the caller is an agent principal, and an agent that is not a member reads nothing; context assembly uses the same rule; removal ends the agent's session for that chat (#399): `Chat.removeAgent` appends the `member remove` entry — which drops the membership and the binding — and then tells the router one-way, as the caller, through the chat's routing port (`ChatOptions.routing`, a `defineRoutingActor` thunk mirroring `MachinePorts.routing`; the app registers `defineChatActor({ files, routing })`) with the session id the binding held: `Routing.endSession` (§7) fails the routes on it, closes the session and purges its record and pages. Membership and the coordinator are changed by user or external principals only; machines never post.
- Attachments (#203):
  - **Storage:** a file is uploaded once into the chat and stored in R2 under `files/<ws>/<chat>/<fileId>` (`ChatFileStore`).
  - **References:** `msg` parts reference it as `agentic-file:<chatId>/<fileId>` in the `url` of an `image` or `file` part, and never carry the bytes, so actor state and daemon frames stay small.
  - **Access:** reading a file is allowed exactly when the caller can see the message it was posted in, by the same `historyFrom` rule as `history`. A pending, not-yet-posted upload is visible only to its uploader.
  - **Hydration:** when a turn starts, the router inlines the images the target agent may see as base64 `image` parts, within `CHAT_FILE_INLINE_BUDGET`. Every other file reaches the model as a text placeholder naming its URI, which the agent reads with `chat_file_read`.
  - **As implemented (#205, `packages/platform/src/chat`):** `Chat.registerUpload(file: ChatFile): Promise<ChatFile>` (users and external clients only; the web upload route calls it after its R2 write) records a pending upload keyed to the uploader (`principalKey`), at most `MAX_PENDING_UPLOADS` = 50 per uploader, forgotten after `PENDING_TTL_MS` = 24 h (the store's `sweepOrphans` must use at least that age); idempotent for the same uploader and id, 409 for another's or a posted id, 400 for another chat / a bad id / a missing name or type, 413 over `CHAT_FILE_MAX_BYTES`, 429 at the cap, 501 on a Chat without a file store. `Chat.post` checks every part whose url claims `agentic-file:` before storing anything: well-formed (400), THIS chat (400), the caller's own live pending upload or a file already posted in a message the caller can see — a re-share (404 unknown or another's pending, 403 not visible), and the file's own `mediaType` (400); it then calls `ChatFileStore.markPosted` for each pending upload it posts (a failure fails the post, nothing stored) and appends the entry. The reducer `applyChatEntry` indexes the chat-file parts of a `msg` into `ChatState.files[fileId] = { entryId, seq, name, mediaType, bytes, at }` — a pending upload moves there, a re-share moves `entryId`/`seq` to the newer message (visibility is "from a seq on", so the newest posting is the widest) — so the index replays and, living in the actor's state rather than the window, outlives archiving to `ChatPage`. `Chat.fileAccess(fileId): Promise<ChatFile | null>` (reentrant, closed to machines): a pending file for its uploader only; a posted file when `visibleFrom(state, principal) <= files[id].seq` — users and external clients always, a member agent from `historyFrom` on, anyone else `null`. An agent's final message arriving as a session event keeps a chat-file part only when the agent can see that file; any other becomes `[file unavailable]`, so no path but `post` makes a file readable. The store reaches the Chat actor as `defineChatActor({ files })` (`Chat` is the store-less default; both have type `'Chat'`, so every `actor(Chat, …)` client reaches whichever the app registers).
- **Member session options (#450, AGT-07):** a member's model and permission mode for this chat — `ChatMember.options: SessionOptions {model?, permissionMode?}` — are written as a `msg` note carrying `options {agentId, patch}` (a value sets a key, `null` clears it back to the agent's config; `applySessionOptions` folds it). The activation contract copies them into `TaskContract.options`; the router opens a fresh session with them (`OpenSpec.model`, `OpenSpec.permissionMode`) and configures a reused one to them before its prompt — the member's next turn, never the running one. The web lists the models its environment reports (`EnvironmentDescriptor.models`, from `RuntimeDriver.models`) and offers Claude Code's `bypassPermissions` only where the environment sets `allowBypassPermissions` (machine-local in `environments.json`, never set through `env.request`). Usage reads for the member's model: `memberWindows(snapshot, model)` keeps the account's shared windows and those scoped to that model, never another model's week.
- Memory privacy (MEM-11): retrieval runs under the assignee's principal against its own scope + declared shared scopes; `Memory.authorize` enforces it.

## 7. Task and delegation

`queued → active → (waiting ⇄ active) → completed | failed | cancelled`; `waiting` always carries a `WaitReason`.

Driver (`Task.tasks.run`): resolve environment (fixed at creation; offline → `waiting {environment-offline}` and the agent's policy `queue | fail | fallback-api`, the last only when explicitly allowed — never silent) → `Agent.snapshotForSession` → `Session.open` → retrieve memories → prompt → mirror session state → result (`verified: false` unless a verification step set it, LRN-03) → learning hook.

**A session may serve many tasks** (#390). A task owns a turn, not a session: the router prompts a session with the task the turn works (`Session.prompt(…, { taskId })`), and from then on the turn — its `delegate` parent, its `task_report`, its Ledger rows and budget check, its audit rows, its memories' provenance, its chat message — is attributed to that task (§5a "the turn owns the task", §5b for the daemon's `tool.call`). The task a session opened with (`spec.taskId`) is the fallback for a turn prompted without one. A chat's tasks share the member's live session (#393, below): each message is a new task and a new turn in the one session, so `spec.taskId` is only ever the task of the latest (re-)open, and everything task-attributed reads the turn's.

**DelegateTool** (`packages/runtimes/src/tools/delegate.ts`, a `defineTool({name: 'delegate', annotations: {openWorld: true}})`): `execute` calls `Task.delegate(spec)`, which checks collaborators, depth, concurrency and budget split, creates the child with the deterministic id `(parentTaskId, callId)`, moves the parent to `waiting {child}`, then awaits the child's `Task.result` stream (idempotent across restarts). In-process `agentTool` is used only for `modelAgent` named sub-agents within one session, never across machines.

Stop cascade (COL-12): `Task.cancel` → `Session.cancel` → each child (one-way) → wait for acks with a deadline → unacked children recorded `stopped: false` and listed as "could not be stopped".

As implemented (`packages/platform/src/task/`): `cancel(by, {timeoutMs})` transitions to `cancelled`, then calls `stop(by, deadline)` one-way on every unsettled child; a child acknowledges its parent through `childStopped(id, report)` (a reentrant method, so it lands while the parent's turn is parked on the deadline) after settling its own subtree, and each hop keeps a 20 % margin of the remaining time so the child's report precedes the parent's deadline. A task with a session attached also waits for `sessionStopped()` from the session driver (the `Session.cancel` hop above); until that arrives it lists itself in `notStopped`. The driver must hear of the cancel while that turn is still parked, but a change feed yields only after a turn ends, so the router follows `result({ eager: true })`: it also yields as soon as the `cancel` entry is committed (an in-process wake per activation), and after that the router reads nothing more from the Task — a FIFO `get()` would queue behind the parked turn — before it sends `sessionStopped` (#168). Children report terminal states to the parent with `childSettled(id, status)`, which frees the child's budget reservation and resumes a parent parked on `waiting {child}` once its last waited-on child settles. Limits default to `maxDepth 5` and `maxConcurrentChildren 8` when the contract sets none; the budget split clamps each of `maxCostUsd`/`maxTokens`/`maxWallMs`/`maxTurns`/`maxSteps` to the parent's remaining share after its own spend and live reservations, never widening. Budget exhaustion (#45, COL-11/OPS-08): `recordUsage` and `delegate` run `checkBudget(constraints, spent)` from `packages/platform/src/ledger`; once a budget is spent (`spent >= max`, estimates counted in full) the task ends `failed` with `error.code 'budget'`, cancels every unsettled child one-way (a queued child is cancelled before it ever starts), and `delegate` throws `TaskLimitError('budget')` before creating anything — distinct from the split's "nothing left to delegate", which refuses the child but keeps the parent alive. Every mutation is one `TaskEntry` through the pure reducer `applyTaskEntry` — `ctx.append` where the runtime ships it, the reducer plus `ctx.save()` otherwise — so the record is snapshot + log either way.

Approvals across delegation (AC-12): children run under `firstMatch(childPolicy, parentConstraints)` (never wider); a child `request` bubbles `waiting {child}` to the parent; the user's decision goes to the child session.

**Delegation, as implemented** (#39, `packages/platform/src/routing/tools.ts`, `packages/platform/src/policy`, `packages/runtimes/src/tools/delegate.ts`): `createActorToolPorts().task.delegate` serves the `delegate` tool on BOTH paths (in-process inside `modelAgent`, and through the Machine's `tool.call`): it checks the parent agent's `collaborators` (COL-10, `forbidden`), calls `Task.delegate` (depth, concurrency, budget split, child id `childTaskId(parentTaskId, callId)`, parent → `waiting {child}`; a `TaskLimitError` answers `limit`), hands the child to `Routing.run` — a 409 (already routed, or already settled because a restarted parent re-issued the call) is not an error — and awaits the child's `Task.result` stream, so the same call id always finds and re-awaits the same child. The tool result is `{ taskId, status, text?, output?, artifacts, verified, error?, notStopped? }`; on the local path the tool also emits an `agent-start` / terminal `agent-update` pair bound to its call (`AgentToolContext.emit`) so the UI renders a sub-agent card linking to the child task — the child's own events are never nested into the parent transcript (it may run on another machine). The tool takes an optional `environmentId` and `workdir` (#190; a `workdir` needs its `environmentId`, refused as invalid input otherwise) and an optional `projectId` (#332; the parent task's when absent, as with the environment) that `Task.delegate` puts in the child's contract (the child's environment defaults to the parent task's; when neither names one, the router falls back to the assignee's default, then the parent route's environment, #220); without a `workdir` the router's inherit rule applies — the parent's folder when the child lands in the parent's environment. A child runs on ITS agent's runtime and environment with no chat (`origin.kind === 'agent'`): background collaboration whose record is the Task tree and its transitions (COL-08/09). Approvals (AC-12): the child's `Route` carries `constraints` — the parent route's chain plus the parent's own `approvalPolicy` — into `SessionOpenSpec.approvalConstraints`, and `createSessionFactory` opens every local session under `sessionPolicy(spec)` = `constrainPolicy(agentPolicy(config), compilePolicy(constraints))`, where `agentPolicy` is `firstMatch(compilePolicy(approvalPolicy), grantPolicy(tools), allowAll)` and `constrainPolicy` lets the stricter side win (deny > ask > allow) so a child is never wider than its ancestors (the daemon path's compiled policy is #121). A child `request` parks the child `waiting {approval | input, requestId, sessionId}` (the parent already `waiting {child}`) and, like every request, reaches the Inbox and the chat through the child's own Session (#40, §5a); the user answers with `Session.respond` on the CHILD session. Stop (COL-12): the router's `follow` is the Task's session driver — a task settled from outside while its turn runs (cancelled by a user or a parent's cascade, failed on budget) has its session cancelled, and `Task.sessionStopped` is sent when the turn actually ends; a late confirmation (`sessionStopped` or a child's ack after the cascade settled) is re-acknowledged upward so every ancestor's `notStopped` is corrected. An aborted parent turn answers `cancelled` with `notStopped` naming the child when its stop is not yet confirmed. `follow` itself is one supervisor task per router (`ctx.tasks` is single-flight per name) that follows every `running` route at once and is woken by `prompt`.

**The `projects` tool** (#334, `packages/runtimes/src/tools/projects.ts`, `PlatformPorts.projects`; COL-02/04, PLG-01), beside `delegate` and `ask_user` and granted like them (`ToolGrant`, both paths — in-process and through the Machine's `tool.call`, the daemon bridge serving the same definition): `{ action: 'list' }` returns the registered projects as `{ id, name, description?, environments }` (the environments with a folder); `{ action: 'set', chatId, projectId | null, force? }` is `Chat.setProject` under the agent's principal (a member of the chat, else `forbidden`; an unknown project is `invalid`), which the Chat records as `chat.project-set` under the agent, so the tool audits nothing itself. The platform does no matching: the tool's description tells the coordinator to `list` only when the chat has no project and the user's message names a repo or project, to set the single registered project whose name or description matches, to ask with `ask_user` offering the candidates when none or several match (never guess), and never to pick a folder on disk — only a registered project. The one rule the tool enforces: a chat already in a project is left unchanged (the error names the current project) unless `force` is passed, which the description reserves for an explicit request from the user to switch the chat's project; setting the project the chat is already in is a no-op. `createActorToolPorts().projects` reads `Workspace.projects` as the workspace's user (the root actor admits its owner only, as `usage_limits` reads the machine index) and the Chat under the agent.

**Routing, as implemented** (#37, `packages/platform/src/routing`): the driver is the Routing actor, `{ws}:routing:main`, `defineRoutingActor({ sessions, machines })` (thunks — Session, Machine and Routing reference each other). `run(taskId)` on a `queued` task takes `Agent.snapshotForSession`, resolves the runtime and the environment ONCE and records both on a `Route`; nothing later changes them (EXE-12) — a retry always goes to the machine that reported the environment at resolution, never to another machine reporting the same id. **The resolution order (#414):** the machine is the task's `machineId` (a chat's, a schedule's), else — for a delegated task — the delegating task's route machine. Then: (1) the task's own `environmentId`, when no machine is named or the named machine reports it (`locateEnvironment` asks the named machine first, `preferMachineId`, since ids are minted per daemon and two machines may report `env_work`); an environment the named machine does NOT report is left aside together with the task's `workdir` — the audit says so (`ignoredEnvironment`, `ignoredWorkdir`) — and (2) applies; (2) with a machine named: an agent WITHOUT an account whose pinned `defaultEnvironmentId` the machine reports takes it as it stands (the pin names an environment, the task the machine; the pin's `defaultWorkdir` follows only on the machine the pin resolves to today — the first of the index — elsewhere the first root); else the assignee's ACCOUNT there — `execution.account` (the explicit binding: an agent carrying both runs by its account, a leftover pin yields; the form keeps them exclusive), else the login of the pinned environment as the pin resolves (the first machine of the index reporting it) — through `environmentsForAccount` (signed-in first, then by name; the rest named in `why`), bound to that machine at once (`Route.machineId`, `Route.account`, `requestedMachineId`); nothing names a login → the delegating task's environment on that same machine (#220), else the workspace's default environment when that machine reports it, else the task fails `no-account`; a runtime other than the agent's fails `runtime-mismatch` here as at placement; a machine the index does not list as paired, or revoked → `machine-unknown`; a machine that never reported its environments, or reports none for the account → `account-not-on-machine` (recoverable: sign in there, run again; an absent account is not "offline", so `fallback-api` never applies); (3) with no machine named: an account-bound agent without a pin fails `no-machine` ("pick a machine for the chat"); else the agent's `defaultEnvironmentId`, else — for a delegated task whose agent has no account — the delegating task's route environment (#220: a chat-started parent's environment lives on its route, never on its Task record), else the workspace's default (AGT-05). **The working folder** (#190, #332, EXE-06/12) is resolved once too, in this order: the task's `workdir`; the project's folder for the environment (`projectFolderFor(project, environmentId)`) when the task carries a `projectId`; for a delegated task without one that lands in its parent route's environment (on the same machine, #414), the parent route's `cwd`; the agent's `execution.defaultWorkdir` when the environment is the agent's `defaultEnvironmentId` (never elsewhere); else the environment's first `cwdRoots` entry (the one piece that needs the machine's report, so a route no machine reported at `run` takes it at placement). The `cwd` is stored on the route, in the `environment.chosen` audit data (`cwd`, and the source in the summary) and on the Session record (`SessionOpenSpec.cwd`), and sent as `OpenSpec.cwd`. Before any Session is opened — and on every placement, against the roots the machine reports then — it is checked with core `pathWithin(cwd, env.cwdRoots, machine.os)` (a machine that never reported its OS is taken for Windows): outside the roots, a sibling prefix or a relative path fails the task `{ code: 'workdir-outside-roots', recoverable: false }` and `Machine.openSession` is never called. A task's own `workdir` is noted on the Workspace (`noteWorkdir`, one-way). `anthropic-api` runs in no local folder: a `workdir` is ignored and the `environment.chosen` entry says so (`ignoredWorkdir`), as does the `fallback-api` entry for the folder it leaves behind. **Projects in the router** (#332, `routing/features.ts`): a task's `projectId` is read from `Workspace.projects()` at `run` — a project the Workspace no longer has fails the task `{ code: 'project-missing', recoverable: false }` before any route is written, never a guessed folder (a Workspace that cannot be read is `workspace-unavailable`, recoverable) — and again at every placement, including before a `fallback-api` is gated or recorded. The gate is asked for the agent's connectors AND the project's (`connectorIds(config, project)`, one per id; the `fallback-api` gate too), so the project's ready connectors ride `spec.plugins.connectors` into the `OpenSpec` beside the agent's. After the folder is final and the machine is there — before `Session.open` on both paths — the enabled feature plugins the build ships (`RoutingPorts.projectFeatures`, by plugin id; an enabled feature with no plugin here is skipped) run in the project's order: `beforeSession({ project, settings, taskId, chatId?, environmentId, cwd, fs })` with `settings` = the manifest's `projectSettings` defaults under `features[id]`, and `fs` = `machineFs(machine, environmentId)` — `Machine.fsRequest` then `fsResult` polled every 250 ms until the daemon answered (or `timeout` after 35 s; a refused request comes back as the daemon-shaped error: `unknown-environment`, `unsupported`) — on the daemon path, and `noDaemonFs` (always `unsupported`) on the local path, where `beforeSession` is only called when the route has an environment and a folder (a `fallback-api` route; a platform-hosted runtime runs in no folder). A returned `cwd` replaces the route's after the same `pathWithin` check (`workdir-outside-roots` otherwise); `instructions` plus every plugin's `instructions({ project, settings })` join with blank lines into `SessionOpenSpec.projectInstructions`, rendered as the prompt's `## Project` section — inside `system` on the daemon path (`buildSystemPrompt({ project })`), and by the API factory on the local one (`createPlatformModelAgent({ project })`). A hook that throws parks the task `waiting { kind: 'project-feature', pluginId, message }` (one line, ≤ 500 chars) with the route kept and no session opened; a later `Routing.run` on that task runs the hooks again on the same route (EXE-12: never a silent fallback). The chat section names the project (`ChatRoster.project`, from `Chat.get().project`). `anthropic-api` opens a local Session through the concrete `SessionFactory` (`createSessionFactory({ routing, anthropic })` → `createPlatformModelAgent` over the actor tool ports, BYO key per workspace, `no-api-key` when none) and prompts `objective + context` — on a reused session, the objective + the chat's unseen entries (#393, below) — under the turn id `{taskId}:turn:1` (idempotent), with the route's task (`prompt(…, { taskId })`, #390). A daemon runtime opens the Session record first (mode remote), then `Machine.openSession(sessionId, envId, OpenSpec, { taskId })`: `opened` → Task `active`, prompted when the machine reports `sessionOpened`; `queued` → Task `waiting {capacity, position}` (the position in the machine's queue), prompted on `sessionOpened` after a dequeue with a `waiting → active` transition that says so. Capacity counts running turns, not open sessions (#394, §5b): before every prompt on a daemon route the router reads the machine and parks the task `waiting {capacity, position}` (route `waiting-capacity`) when `freeSlots` is 0 — a reused live session whose environment is busy with another session's turn waits exactly like a queued open; a turn running on the route's OWN session is not counted against it, since that turn already holds the slot and `steerOrPrompt` (#395, below) joins it or waits `waiting-turn` for it — and the machine's `slotFreed` (a turn ended there, or a running session closed) wakes the routes parked in that environment whose session is open, one per free slot, through a `waiting → active` transition that names the turn; a queued open is woken by its `sessionOpened` as before, and both re-check the slot first. A daemon `busy` reply to a prompt (the machine's own admission, reported by `promptRefused`) parks the route the same way and the next prompt goes out under a fresh `commandId` (`{turnId}#{attempt}`), the turn id unchanged so `follow` keeps waiting for the same `turn-end`; any other error reply fails the task `prompt-{code}`. A local route is never parked on capacity (`anthropic-api` has no environment); machine offline → Task `waiting {environment-offline, policy}` then the agent's `offlinePolicy`: `queue` parks the route until `machineOnline` from THAT machine, `fail` ends the task `failed {environment-offline}` naming the environment, machine and policy, `fallback-api` — only when the config sets it — opens a NEW local session through a `waiting → active` transition whose `why` starts with `fallback-api:` and names the environment (the task's own `environmentId` stays what it was; the record says where it actually ran). An environment no machine of the workspace reports yet is offline under the same policy (`queue` waits for the first machine that reports it and binds the route to it then; `fail` ends the task `failed {environment-offline}` saying no machine reports it); an agent without an environment, or one whose runtime differs from the environment's, fails the task with a code (`no-environment`, `runtime-mismatch`). The `follow` actor task tails the Session and settles the Task at the turn end: `completed` with the final assistant text (or the `task_report` summary) and the `task_report` output when one was given, `failed` on an error, `waiting {input}` "Resume?" on an interrupted turn (OPS-05/06), `waiting {approval | input}` / back to `active` on `request` / `request-resolved`; then a chatless session is closed so the environment slot frees — a chat member's session is not (#393, below). Routing drives the other actors as the workspace user (v1: `workspaceId === userId`; `RoutingPorts.driver` overrides). `run` also adopts a task the schedule trigger (#42) left `waiting {environment-offline}` — the app hands every task a firing creates to `Routing.run` from `scheduleTrigger({ onOutcome })`, and the trigger's `EnvironmentProbe` is `createEnvironmentProbe({ machines })` over the same machine scan. Platform tools (`memory_search`, `memory_remember`, `chat_post`, `task_report`, `delegate`) run over `createActorToolPorts` under the agent principal on both paths — in-process inside `modelAgent`, and through the Machine's `ToolCallPort` (`createToolCallPort`, the same tool definitions, `SchemaValidationError` → `invalid`); `ask_user` raises a platform input request on the Session (#122, §5a) — `createActorToolPorts({ sessions })` / `createSessionFactory({ sessions })` name the Session definition; without it the tool answers `unsupported`. The local session policy is compiled from the config (`sessionPolicy`, #39); memory retrieval and the learning hook are #41's. **Chat roster** (#194, CHT-07): for a chat-originated task the router reads `Chat.get()` and each member's `snapshotForSession` into `SessionOpenSpec.roster` (`ChatRoster`: members by id, name and role, the coordinator, `self`) on both paths; `buildSystemPrompt` renders it as `## This chat` — every member by platform id, who coordinates, and that they are reached through `delegate` (the id as `assignee`) or `chat_post` @Name, never a runtime's own agent messaging. `delegate` refuses an assignee that is no configured agent with `invalid` before a child exists.

**One live session per chat member, in the router** (#393; CHT-01, CHT-07, CHT-09, CHT-11, COL-04, EXE-12, EXE-13, MEM-07). A route with a `chatId` — set only for `origin.kind === 'user'`: chat members, the coordinator, and members an agent `@mention`s — is a chat route; everything else (a `delegate` child, a schedule, a trigger, an external client) is chatless and unchanged: one throwaway session per task, closed at the turn's end. **Binding** (`bindSession`, once the placement is final, the folder included): a chat route takes `ChatSummary.sessions[agentId].sessionId` from the chat and, with it, the row's `seenSeq` onto the route; a chatless route, or a chat route with no binding, mints a fresh id. **Refusal** (`reusable`; never a migration): the bound record is not reused — it is ended with `Session.close` (its `session-ended` drops the chat's row; the fresh session's `session-started` replaces it either way) and a fresh id minted — when it is closed or was never opened, when the placement moved (`runtime`, `environmentId`, `machineId` or `cwd` differ from the record's spec), or when a daemon-path record has no `ref` (its runtime never named it, so nothing could be resumed; #389). A record that cannot be read is not reused. The git feature's `beforeSession` still runs per placement — it decides the folder the reuse is judged on — and is idempotent (`branch-exists` → the same worktree), so the worktree is made once per chat. **Re-open**: `Session.open` with the new spec (§5a) and, on the daemon path, `Machine.openSession` with `resume` = the record's `ref`; a session the machine still hosts answers `opened` without a frame, so the router prompts it at once, a session the daemon lost (a restart: it says `session.closed` for the one the platform wanted) is opened again on the daemon with that ref. **Prompt**: the objective, the triggering message's attachments, then — instead of the task's context — the chat's messages after `seenSeq` that the member may read (`Chat.history` as the agent, so `seenSeq: 0` starts at `historyFrom`), the triggering message left out, oldest first, each `Name: text` with attachments noted and their chat-file parts following once for `hydrateChatFiles`; nothing when nothing is new. **Follow**: the route records the head `open()` returned and `follow` tails from it, ending itself at its turn's `turn-end` — the log outlives the turn and nothing before it is replayed. **Mid-turn**: a second route on a session whose first turn still runs steers into it, or waits for it — never `prompt-busy` (#395, next paragraph). `sessionOpened` from the Machine applies to every route bound to the session that still waits for it to open, `sessionClosed` to those and to a route waiting for its turn to end. A chat route's session is not closed when the task settles, a failed turn included; `Route.sessionId`, `seenSeq`, `head`, `turnId` and `joined` are the state (`routing/state.ts`).

**A message arriving mid-turn steers into the running turn** (#395; CHT-09, COL-06, OPS-06; S7). The Claude Code CLI takes what you type while it works and picks it up at its next input check; a live session does the same. Every prompt of a route goes through one seam, `steerOrPrompt(route, input)` in `routing/actor.ts` (`async function steerOrPrompt(route: Route, input: readonly PromptPart[]): Promise<{ turnId } | 'busy' | wire error reply>`), which decides from the Session record — `SessionInfo.running` and `capabilities.steer` — BEFORE anything is sent, on both paths alike (a wire `busy` after that is the environment's, #394). **Idle**: the prompt starts the route's own turn `{taskId}:turn:1`, as before. **Running, and the runtime steers** (`mockAgent`, the Claude Code adapter): the task is parked `waiting { kind: 'turn', sessionId, turnId }` (the new `WaitReason`, `packages/core/src/task.ts`) and the prompt is sent under its own task (`Session.prompt(…, { taskId })`); `serveSession` answers a prompt that joins a running turn with THAT turn's id, so the route binds to it — `route.turnId` = the ack's `turnId`, `route.joined = true` — and the task goes `active` through `joined running turn {turnId}`, which is how the thread and the task page can show why two tasks share an end. On the daemon path the ack comes later (`Session.prompt` answers `pending`), so the route binds to the turn the record runs — the id a steering runtime answers; a refusal the daemon sends after that stays on the Session's command record, as every late daemon reply does. **Running, and the runtime cannot steer** (the in-memory daemon reports `steer: false`): nothing is sent; the route parks `waiting-turn` (`RouteStatus`) with the same `waiting {turn}`, and when that turn ends the follower calls the router's own `turnEnded(sessionId, turnId)` (a method turn, under the driver), which resolves the wait (`turn {turnId} ended`) and prompts the route again through the same seam — into a turn of its own now, or parked once more should a third message's turn be running. `sessionClosed` fails a `waiting-turn` route `session-refused` with the daemon's reason, like a route still opening. **Two tasks, one turn.** Each keeps its own record: `follow` runs one follower per route (a joined route tails from the head its placement saw, filtered on the shared `turnId`), so every route bound to the turn settles at its `turn-end` with the same outcome — the turn's final text, an error, a cancel — and each task's own transitions and result. `Session.running.taskId` stays the turn's first task (`currentTaskId`, #390), so a `task_report` filed during a shared turn reaches `Routing.report` under that task: `report` accepts it from the task named or from any route sharing its session and turn, and records it for the named task and every route bound to that turn, so both complete with it. Cancelling a joined task from outside does not cancel the turn — it is the other task's; the cancelled task hears `sessionStopped` when the turn ends. Cancelling the task that started the turn cancels the session's turn as before, and the joined task fails `turn-cancelled` with it. Attribution inside the turn stays the first task's (`currentTaskId`): a steered message adds to a turn that is billed, audited and remembered under the task that started it; only the joined task's own record says it joined. The `ask_user` answer path (#396, next paragraph) delivers a late answer through the same seam under the asking task's route.

**A late `ask_user` answer reaches the asker in its own session** (#396; CHT-09, COL-06, OPS-06). In a chat, `chat.ask` answers `pending` past its quick window (§5a "Questions outlive the call") and the agent ends its turn — and the asking task does NOT complete with it: `follow`, finding the task `waiting {input}` on a question the Session still reports open and detached (`Session.request(id).detached`), parks the route `waiting-answer` (`RouteStatus`; `Route.question` = the request id) and stops following it — no turn runs, nothing is polled, the task shows what it waits for. A chatless route (a delegated child, whose ask blocks anyway) keeps the old rule: the task completes and the question stays open on the record. When the answer comes, the Session's `deliverAnswers` hands it to `SessionPorts.answered` (`createAnswerFollowUp`, `routing/answers.ts`), which posts it in the chat as the person who gave it (`answerPostText`, once — a retried hand-over carries the message id it already posted, `AnswerFollowUp.posted`) and then calls **`Routing.deliverAnswer(sessionId, requestId, input)`** with the answer rendered as a user message (`answerPrompt`: `The answer to your question “…”: …` and "continue the work you were doing"). The router finds the route waiting on that question, moves the task `waiting → active` (`request {id}: input`), sets `Route.head` to the session's current head (so `follow` tails the answer's turn only) and puts the answer on the route (`Route.answer = { requestId, turnId, input }`), then takes the one `prompt` every route takes — the environment's capacity first (#394), then `steerOrPrompt` (#395) with the answer as the input and **`answerTurnId(taskId, requestId)`** (`{taskId}:turn:answer:{requestId}`, deterministic so a retry after an eviction runs once) as the turn to start. Idle → the answer starts that turn under the asking task and `follow` settles the task at its end, as any turn; running another turn → steered into it, or the route parks `waiting-turn` / `waiting-capacity` with the answer still on it and `prompt` sends it when `turnEnded` / `slotFreed` wakes the route (`route.answer` is cleared on the send); refused → the task fails `prompt-{code}` as any prompt would, and `deliverAnswer` answers `{ delivered: false, reason: 'refused' }`, which the hand-over treats like `no-route` below (the answer never reached the asker; its task is failed, so the follow-up task is the only way on). A second task waiting on the same question (two tasks that shared the asking turn) joins the answer's turn (`joined`). So the answer is a new user message in the engine conversation that asked — no second task, no lost context — and `Session.running.taskId` is the asking task, so `delegate`, `task_report`, usage and audit inside the answer's turn name it. **No route waits on the question** (`{ delivered: false, reason: 'no-route' }`: the asking task was cancelled or failed — `sessionClosed` fails a `waiting-answer` route `session-refused` like one still opening, and L's reset ends the session under it) → the follow-up task of #285 stays: `createAnswerFollowUp` creates `answerTaskId(sessionId, requestId)` from `answerContract` (origin the posted message, `resumeFrom` the asking session) and places it with `Routing.run`; as a chat task it binds to the member's live session when that can go on, else a fresh one resumes the engine conversation where the placement allows. **A dismissed question** (`respond {type: 'cancel'}` on a detached request) takes the same road as `AnswerFollowUp.cancelled` → `Routing.questionCancelled(sessionId, requestId)`: every task waiting on it is completed with what its asking turn said, nothing is posted, nobody is prompted. **Retry, then name the failure.** `deliverAnswers` keeps an answer whose hand-over threw in `answeredDetached` with `attempts` and `nextAt` (`ANSWER_RETRY_MS` = 5 s, 30 s, 2 min, 10 min — the last repeats — after attempts 1, 2, 3, 4) and arms the Session's `answers` reminder (`ctx.reminders`, at or after the due time; the host's tick is the resolution) which restarts the task; only when `ANSWER_ATTEMPTS` (5) are spent is the answer dropped and the failure said in the chat as a `task` status `answer-not-delivered:{step}:{cause}` — `createAnswerFollowUp` wraps every step in `AnswerDeliveryError` (a `ServerFnError`; `step` is `post` / `deliver` / `create` / `run`, `cause` the thrown error's message, which for a non-`ServerFnError` from another actor is the `Internal error` mask, so the step still says where; `posted` carries the message an attempt posted so no retry posts twice) and logs the cause with the error. A dismissed question's hand-over is retried the same way.

**Ending a session on purpose** (#399; CHT-04, CHT-09, AGT-07, OPS-10; `docs/decisions.md` 2026-09-21). A chat member's session lives until the agent leaves the chat, the user resets it, or the workspace is deleted — never parked, never evicted. `Routing.endSession(chatId, agentId, reason, sessionId?)` — `methodAuthorize` admits a user or an external client, never an agent, which must not wipe its own or another member's conversation — ends the session the chat binds to the member (`ChatSummary.sessions[agentId]`), or the one the caller names when the binding is already gone (a removal) — never on trust: with the binding there it must be that session (409), without one the record's own spec must name this chat and member (409; a record that is not open is nothing to end, `null`) — and forgets it, in this order: every route bound to the session fails `{ code: 'session-reset', recoverable: true }` naming the session and the reason — a running turn is cancelled the way any task settled from outside is (`follow`'s early-settle path, COL-12) and the chat hears `task-failed` (OPS-04); `Session.close` — a local runtime session is disposed, a hosted one gets the daemon's `close` (an offline machine sends it on its next `hello`); the chat's binding is dropped by `session-ended` — the Session publishes it on its ack, the router itself when the ack is still out or the record could not be reached — so the browser's feed closes and the next message finds no row and mints a fresh id (`bindSession`); then the record and every one of its pages (`SessionInfo.pages`, keys `sessionPageKey(key, n)`; the pages in batches of `PURGE_BATCH` = 8, all of them before the record) are purged through `RoutingPorts.store`, the same `WorkspaceStore` `Workspace.deleteAll` uses (each actor's own Durable Object in the web app, `apps/web/src/retention.ts`), so nothing of the conversation stays in storage; without the port the session is closed and unbound but its record stays. The fresh session's prompt carries the activation context again; the chat's own history is untouched. Returns the id ended, or `null` when the member had no session. `Chat.removeAgent` reaches it one-way through `ChatOptions.routing` (§6); `Workspace.deleteAll` reaches every chat's bound sessions and their pages through the same binding (`childRecords`: `Chat.get().sessions` → `Session.get().pages`), so a deleted workspace leaves none behind even on a storage that cannot list. The thread renders no `session-started` / `session-ended` rows — the entries still maintain the binding (`statusText` / `entryTranscript`, `apps/web/src/pages/chat/live.ts`) — and "New session" is on each member in the chat's context panel (in the drawer on a phone), behind a confirmation that says the agent forgets this conversation, work in flight stops, and the chat's history stays.

**A daemon restart mid-turn** (#420; OPS-04, OPS-05, OPS-06, EXE-12, CHT-09). A daemon that restarts (a crash, a kill, a reboot) under a running turn answers the platform's `welcome.wanted` with `session.closed` for it. `Machine.sessionGone` hands that to the record before the router hears it: `Session.hostEnded({ reason, code? })` (machine principal, the hosting machine only — `methodAuthorize` beside `noteRef`; `code` a plain string until #359 names the close codes, `closed` when absent). A turn still running is cut short the way an eviction cuts one (`finishInterrupted`): open calls cancelled, open requests resolved `cancel` (a detached question outlives it, #285), `error {process_exited, data: {interrupted: true, host: code}}`, `state idle`, then the `turn-end` whose message is `interrupted: {reason}` — `isInterruptedTurnEnd` matches any `interrupted: ` message under that code — and the chat hears `interrupted:{turnId}`. On the daemon path these events are stamped like a platform-raised request (`platformCursor`, fractional after the head), never with an integer the daemon may already hold past the head or stamp once the session is re-opened. The record then waits `idle` with its `opened`, `spec` and `ref`; a record whose runtime never named it (no ref, nothing to resume from) is `closed` and says `session-ended`. Idempotent: a second word changes nothing. `follow` reads the turn end as it reads an eviction's — the task waits `{input, resume:{turnId}}` and the route parks `interrupted` — and `Routing.sessionClosed` leaves a `running` route alone, since the turn was already ended. **Resume re-hosts first**: when the route's machine no longer hosts its session, `Routing.resume` re-opens it (`rehost`): `Session.open` with the record's own spec, then `Machine.openSession` with the ref as `spec.resume` — the same `hostSession` the bind-time open (#393) runs — and the route stays `interrupted` with `rehosting: true` (a second `resume` changes nothing) until `sessionOpened`, which resumes the turn (`Session.resume()`, a `{turnId}:resume` prompt over the intact transcript) and puts the route back to `running`. A daemon that refuses the re-open (`session.closed` while `rehosting`, and the machine no longer hosting it — a late word about the lost session is ignored) sends the task to a fresh session on the same machine: a new id, placed as any task is, resuming the engine conversation from the lost session's ref where `resumable` allows and prompted with the task's own input; so does a `resume` of a record its host closed. A new message to the member after the restart needs nothing of this: the record is `idle` with its ref, so `bindSession` / `reusable` re-open it with resume (#393) and the prompt starts a turn — never parked `waiting-turn` on a dead one, never steered into it. The daemon's close codes are #363's. A message parked on the live session — `waiting-capacity` (a slot, or a draining daemon's refusal) or `waiting-turn` — survives the host going away (#433): `sessionClosed` (the Machine passes the close `code` on) keeps the route `waiting-capacity` with `reopen` when the code is `restart`, `update` or `harness-update`, or absent with the record left `idle` with its ref; `reopenParked` re-opens the same session with its ref as `spec.resume` (`hostSession`) — at once when the machine is online, after the next `hello` (`machineOnline`) for an update, whose daemon is about to stop — and `sessionOpened` prompts the message into it under the same task. `resume-failed`, `harness-missing` or a closed record fail it `session-refused` (recoverable) as before, and so does a `waiting-answer` route.

**A machine that goes away, and `onInterrupt`** (#366; OPS-04, OPS-05, OPS-06, EXE-11, EXE-12, AC-15). When the Machine marks itself offline — its socket closed, or no heartbeat within the window — it tells the router `machineOffline(machineId)`. Every `running` route on that machine keeps `running`, gets `offlineSince`, and its task, when `active`, waits `{machine-offline, machineId, since}` — distinct from `environment-offline`, which is a placement that never started (a task already waiting on an approval or a question keeps that wait). The next `hello` (`machineOnline`) clears `offlineSince` and resolves the wait: a session the daemon still runs goes on from the `wanted` replay, and one it lost is answered `session.closed` and interrupted as above. While any route is offline the router keeps its `machine-lost` reminder armed; a route offline for `MACHINE_LOST_MS` (24 h) fails `{ code: 'machine-lost', recoverable: true }` (`expireOffline`), audited `task.machine-lost`, the chat told as any failure is. Its session is let go first (`Machine.closeSession` on the offline machine: the record's turn is interrupted and it waits `idle` with its ref) — so a chat member's next message re-opens it wherever the machine comes back — and a chatless session is closed. An interrupted route whose agent's `execution.onInterrupt` is `auto` is resumed once on its own, as `system:routing`: when the follower parks it on a machine that is online, and on that machine's next `hello`. Once per cut turn (`autoResumed`, the turn without its `:resume` suffixes): a second interruption of the same turn, or a resume that fails, waits for a person's Resume. Every interruption is audited where the record ends the turn (`session.interrupted { sessionId, taskId?, turnId, host }`, `host` the daemon's close code or `closed`), every resume where it goes on (`session.resumed { sessionId, taskId, how: 're-host' | 'fresh', by }`: a person, or `system:routing`).

**Chat attachments on the router and the tools** (#205, `packages/platform/src/routing/files.ts`, CHT-04 / MEM-11): before `prompt`, the router builds the turn's input as `[objective, …the triggering message's chat-file parts the context does not already carry, …context]` — the triggering message is read with `Chat.history` as the task's agent (the last 50 entries; best effort) — and `hydrateChatFiles` resolves every chat-file part through `Chat.fileAccess` asked as the TARGET agent (`mintAgentPrincipal` with the route's session and task): an image of a `MODEL_IMAGE_TYPES` type is read from the store and inlined as `{ type: 'image', mediaType, data }` (base64) while `CHAT_FILE_INLINE_BUDGET` base64 characters last, the triggering message's images first and then the newest (last) ones; an image over budget, or any image when no store is wired, becomes `[image "<name>" (<type>, <KB> KB) <uri> not inlined]`; every other file `[file "<name>" (<type>, <KB> KB) <uri> — read it with chat_file_read]`; a file missing, denied or without bytes `[file unavailable]`. The parts keep their order. `createActorToolPorts({ files })` adds the `files` port only when a store is given: `files.read(uri)` asks `Chat.fileAccess` as the agent (`invalid` for a malformed URI, `forbidden` when missing or not visible), then for a text-like type (`isTextLikeMediaType`) reads the store and returns the UTF-8 text cut on a character boundary at `CHAT_FILE_TEXT_MAX_BYTES` with `truncated: true` (`not-found` when the bytes are gone), for any other type the record alone without touching the store. `chat.post` turns `attachments` into parts the same way — each URI through `fileAccess` (`forbidden` if not visible), then an `image` part for a model image type or a `file` part with the name, typed by the chat's record — and `Chat.post` checks them again, so an agent re-shares only what it can see. `Workspace.deleteAll` deletes every chat's files (`ChatFileStore.deleteChat`) before purging the records. **Implicit grant:** `run` adds `{ name: 'chat_file_read' }` to the route's config for every chat-originated task (`withChatFileRead`) — the tool is read-only and every read is decided by `Chat.fileAccess`, like reading the chat itself — so it reaches the model's roster, the system prompt, `SessionOpenSpec.tools` / `OpenSpec.tools` and the compiled policy on both paths without the agent's config naming it; a config that names the tool (`ask`, or `deny` outright) keeps its own grant, and a task from outside any chat gets nothing implicit.

**Wiring the file store** (for the web app, #207): the store is one `ChatFileStore` (from `@agentic/core`, the R2 implementation) passed as the optional `files` option everywhere it is used — `defineChatActor({ files })` registered in place of `Chat` (`markPosted`), `defineRoutingActor({ …, files })` (`RoutingPorts.files`, hydration), `createSessionFactory({ …, files })` (the local path's `files` tool port), `createToolCallPort({ …, files })` (the daemon path's), and `defineWorkspace({ …, files })` (`WorkspaceOptions.files`, the purge); the MCP mount gets it too — `createAuthMount({ …, files })` → `createOAuthRoutes(…, { files })` → `createPlatformMcpHandler({ files })` (`chats_file_get`, #209). Absent anywhere, that piece degrades: the Chat refuses uploads (`registerUpload` and a `post` of a pending upload answer 501), notes instead of images, no `chat_file_read`, no purge of bytes.

## 8. Memory and learning

Interfaces in `@agentic/core`:

```ts
interface MemoryPlugin { id: string; version: string; capabilities: { semantic: boolean; export: 'full' | 'partial' }; open(scope: MemoryScope, ctx: PluginContext): MemoryStore }
interface MemoryStore { put(e: NewMemoryEntry): Promise<MemoryEntry>; update(id, patch); retire(id, why); delete(id): Promise<boolean>; get(id); query(q: MemoryQuery): Promise<RankedMemory[]>; export(): AsyncIterable<MemoryEntry>; import(rows: AsyncIterable<MemoryEntry>, opts): Promise<ImportReport> }
interface MemoryQuery { text?: string; tags?: string[]; kinds?: MemoryKind[]; subject?: string; limit: number; since?: number }
interface LearningPlugin { id; version; onTaskEnd(ev: TaskOutcome, mem: MemoryStore): Promise<Proposal[]>; onCorrection(ev: Correction, mem: MemoryStore): Promise<Proposal[]> }
type Proposal = { kind: 'memory'; entry: NewMemoryEntry } | { kind: 'instruction'; patch: string; requiresReview: true }
```

Default memory (`@agentic/memory`, #26): a pure core — `MemoryState` + `applyMemoryLog` reducer, BM25 over text/tags/subject/`conditions` × kind weight (preference 1.3 > lesson 1.2 > fact 1.1 > working 1.0 > record 0.9 > assumption 0.8) × confidence weight × recency decay (30-day half-life, floor 0.5) — and `createMemoryStore({ state, now, commit })` over it. `query` filters on `tags` (any-of; `conditions` tokens count as tags), `kinds`, `subject`, `since`, ranks on `text`, and never exceeds `limit` (default 20) or `maxBytes` (default 4096 bytes of `text`; a non-fitting entry is skipped). `working` entries expire `ttl` ms after `provenance.at` and are compacted on the next working put; a new `record` for a task retires the previous ones (`supersedes`). `retire` is soft: hidden from `query`, kept for `get` and export. Export is NDJSON with a header `{ format: 'agentic-memory', version: 1 }`; `import` reports `imported` / `skipped` / `droppedFields`. `memoryConformance(make)` (`@agentic/memory/testing`) runs against the in-memory store and the Memory actor over `memoryStorage()`; the Durable Object run is a follow-up (#33).

The Memory actor (`@agentic/platform/src/memory`) is that store over `ctx.state` with `ctx.save()` per mutating turn (`ctx.append` once `@sigx/actors` ships signalxjs/actors#312). Methods: put, update, retire, delete (MEM-05 / MEM-08: gone for good, `false` for an unknown id — `retire` keeps the history), get, query, exportPage, importBatch, compact, setAcl/getAcl, stats. Access: `memoryAuthorize` (same workspace; a user or a `memory`-scoped external client owns every scope; an agent only `agent:{self}`) and, inside the turn, the shared-scope ACL `{ read, write }` — no ACL, no agent access (MEM-04/11, AC-10). Embeddings later as a plugin via export/import (MEM-09) with the fidelity report.

Migration (`@agentic/memory`, #49, MEM-09): the export/import contract is the path between plugins, and `migrate(from, to, { dryRun, onConflict })` is the helper that walks it — every entry of `from` (retired included) imported into `to` kind by kind, returning a `MigrationReport` with `entries` / `imported` / `skipped` / `droppedFields` in total and per kind; a field is listed only when an entry of that kind carried it. A dry run asks the target's `fidelity(entry)` seam (`MemoryFidelity`, on every store of the package: the fields `import` would drop, `null` for a row it would skip) and `get` for id conflicts, so it reports the same numbers without writing; a target without the seam migrates for real only. The **flat plugin** (`flatMemoryPlugin()`, `agentic.memory.flat`, `capabilities.export: 'partial'`) is the deliberately narrower second implementation the path is proven against: it holds id, kind, text, tags, subject, provenance, confidence and `retired`, drops `conditions`, `evidence`, `supersedes` and `ttl` (`FLAT_UNSUPPORTED_FIELDS` — reported by `import`, by `fidelity`, and logged at `warn` by a `put` / `update` that carried one), ranks by the number of query terms found as substrings of `text` with recency as the tie-break (no kind or confidence weight, conditions are not tags), never expires a `working` entry and never compacts records. A round trip default → flat → default therefore reports exactly those four fields and nothing else (AC-11). `memoryConformance` marks the four cases those features need with `requires` (`conditions`, `kindWeights`, `ttl`, `supersedes`); a plugin runs the suite `without` the ones it lacks — the flat plugin all four, the default plugin and the Memory actor none. Retirement reasons are not part of `MemoryEntry`, so no export carries them: a limitation of the format, shared by every plugin.

Learning: explicit "Correct" action on any assistant message (v1); agent-detected correction classification is off by default. Memory writes are automatic; instruction/skill patches require review and land as new Agent config versions (AGT-06, LRN-08). Lessons retire through `supersedes` / `retire` (LRN-06). Copying a lesson into a shared scope keeps provenance (LRN-07). LRN-09: Ledger counts corrections per agent per week.

As wired (#41, `packages/platform/src/task/driver.ts` + the Session actor's `learning` port; the memory page is #89): the steps are pure functions the Session actor runs and a Task driver can reuse. **Session start** — `open` (before the factory or a daemon sees the spec) runs `retrieveMemories` **as the minted agent principal** over `agent:{id}` + `memoryPolicy.shared` (so `Memory.authorize` and the ACL decide, MEM-11; a refused scope is listed in `spec.retrieval.skipped`), ranked on `spec.objective` + the last text part of `spec.context`, filtered on `spec.tags`, merged under one budget (8 entries / 4096 bytes by default, MEM-07); the hits are recorded as `spec.memories`. **One rendering per path** (#135): on the local path the router opens the session without a `system` and `createSessionFactory` hands `spec.memories` to `createPlatformModelAgent({ memories })`, whose `buildSystemPrompt` composes the whole prompt (identity, role, instructions, skills, tools, then the memory block) — the record composes no second prompt, so `spec.system` stays absent and what the model saw is what `spec.memories` says; on the daemon path the caller builds `spec.system` (`placeRemote`: `buildSystemPrompt` over the config, the granted tools and the chat roster — the same prompt the API path composes, #194) and `open` appends `## Platform memory` + an ownership note to it (MEM-10) — the heading `claudeCodeSystemPrompt` relabels to, so a daemon carries it verbatim. Both `placeLocal` and `placeRemote` put the task's `objective` and `context` on the `SessionOpenSpec`, so retrieval ranks on the task (`spec.retrieval.text` is the objective plus the latest context text) and a correction's lesson gets `Tasks like: <objective>` as its conditions. Pinned by `packages/platform/__tests__/routing/memories.test.ts` (the real factory over a `mockModel`: every request's `system` carries the lesson) and AC-09. **Turn end** — a task session's regular `turn-end` becomes a `TaskOutcome` (`end_turn`/`max_*` → completed, `cancelled`, else failed; a result with text is `claimed`, `verified`/`refuted` only from the `verify` port, LRN-03) for `plugin.onTaskEnd`; memory proposals are applied by the plugin, instruction proposals parked; an interrupted turn is no outcome. **Correct** — `Session.correct(messageId, text, what)` builds the `Correction` for the assistant message (`by: 'user'`, or `'agent'` for an agent principal; never a machine) and runs `plugin.onCorrection` as the agent, so the lesson lands in `agent:{id}` with the user's provenance. The plugin port may be a factory over `{ workspaceId, agentId, sessionId, taskId?, objective?, tags? }`, which is how `contextFor` gives a lesson the task's conditions. **Review** — instruction proposals park on the Agent actor (`propose` / `listProposals` / `reviewProposal`); an acceptance is a new config version with the patch appended to `instructions`, reversible by `rollback` (LRN-08). AC-09 is scripted end to end over `mockAgent` in `packages/platform/__tests__/session-learning.test.ts`.

**Through the active plugin** (#242, MEM-02, LRN-01, AC-13): `memory` and `learning` are single-slot plugin kinds, and a session uses the workspace's ACTIVE plugin of each, over its config — the Registry's answer `Routing.run` already recorded on the spec (`spec.plugins`, #230), so no second hop. The app hands `platformLearningPorts` the build's implementations by plugin id (`memoryPlugins: Record<id, (config) => PlatformMemory>`, `learningPlugins: Record<id, (config) => LearningPlugin | LearningPluginFactory>`, composed in `apps/web/src/plugins/catalogue.ts` as `memoryCatalogue` / `learningCatalogue`); `memoryAccess(ports, gate)` and `learningAccess(ports, gate)` resolve them. The default memory plugin is `memoryActorImpl()` — `memoryActorPlugin` over the Memory actor, reached as the calling principal so the ACL still decides (MEM-11); the flat one is `flatMemoryActorImpl()` — `flatMemoryActorPlugin` over the **FlatMemory actor** (#281), reached the same way (below). Config knobs: memory `retrievalLimit` (entries a session starts with, default `DEFAULT_RETRIEVAL_LIMIT`; `0` asks no scope), learning `repeatThreshold`. **Turned off** — the memory plugin: `open` retrieves nothing and records why in `spec.retrieval.skipped` (`memory is turned off for this workspace: …`), nothing is written, learning is off with it, and the stored memories stay where they are (the Memory page still browses them); the learning plugin: `onTaskEnd` is not called and `correct` refuses with the reason. An active id the build does not implement is off the same way. `memory_search` / `memory_remember` stay listed and answer the same reason (`ToolCallError('unsupported')`), so the agent learns memory is off; they reach the same store the session retrieved from — on the local path through `anthropicApiRuntime({ memory })`, on the daemon path the `tool.call` port reads the gate from the calling session's spec, only for a memory tool. No gate on the spec (no Registry behind the router, a test): the static `memory` / `plugin` / `retrieval` ports, as before. **Switching with migration** (#243, MEM-09, AC-11): `Registry.previewActivation('memory', id)` is the dry run and `Registry.activate('memory', id, { migrate: true })` the move, both over `defineRegistry({ memoryPlugins })` (the app passes `memoryCatalogue`; without both ends a move refuses `no-migration`). `switchMemory` (`packages/platform/src/memory/switch.ts`) walks every scope the workspace's agents imply (`workspaceMemoryScopes`: each agent's own, then every shared scope any of them reads) through `migrate(from.open(scope), to.open(scope))` as the owner — the AC-11 path; the actor-backed stores carry the plugin's `fidelity` seam (it depends on the entry alone, so a local store of the same kind answers it), so the dry run reports per scope and in total what would be imported, skipped and dropped without writing. For real, each scope is VERIFIED — the target must hold exactly `imported` more entries than before — and `active` flips last: any failure is `migration-failed` and the old plugin stays active. Ids the target already holds are skipped, so a switch back imports only what is new; what a failed move already copied stays in the target; the source store is never touched (retention removes it with the workspace). The move runs inside the Registry's turn, so other Registry mutations wait for it; a session still writing to the old plugin while the move runs can leave its newest entries behind. The audit summary of `plugin.activated` carries the counts. The plugin page's "Make active" on a memory plugin shows the dry run (what moves, what is dropped, by agent) in a confirmation and moves only on confirm.

**The flat plugin's durable backend** (#281): the FlatMemory actor, one per scope under the SAME key as the Memory actor (`{ws}:memory:{scope}`) but its own type — so it is its own object and the two plugins' stores never mix, and `memoryAuthorize` (a static check on the key) guards both unchanged. Its state is `createFlatMemoryState()` (the flat store's plain records, JSON-safe; `createFlatMemoryStore({ state })` reads and writes it in place) plus a `rev` the pages follow; `persistence: 'explicit'`, a `ctx.save()` at the end of every mutating turn. Its method table is the Memory actor's (`put` … `importBatch`, `compact` always `0`, `getAcl`, `stats`), so `actorMemoryStore` (typed over `MemoryStoreClient`), the pages and the workspace export reach either the same way. **One ACL per scope, the Memory actor's** (MEM-11): who reads a shared scope belongs to the scope, not the plugin, so an agent on a shared scope is checked against the ACL the FlatMemory actor reads from that scope's Memory actor, as the workspace owner — one hop, only for an agent on a shared scope; there is no `setAcl` here. Switching the active plugin therefore never changes who reads a shared scope, and #243 has no ACL to move. The flat plugin ships enabled, not active. `exportAll` writes its entries into `memory.ndjson` marked `plugin: 'agentic.memory.flat'` and `deleteAll` purges both records of every scope. The agent pages read the active plugin's store (`useActiveMemory` on `Registry.overview().active.memory`).

Default learning (`@agentic/learning`, #27) works over any `MemoryStore`. `onCorrection` writes a `lesson` — `text` the correction, `evidence` one line per occurrence, `conditions` from `contextFor(correction)` (the task objective; the correction itself when unknown), `confidence: 'stated'`, `provenance.source: 'user'`; agent-detected corrections are dropped unless `acceptAgentCorrections`. A correction of the same `what` with ≥ 0.6 word overlap supersedes the live lesson (merged conditions, the newest `evidenceCap` evidence lines behind an uncapped `corrections in total: N` line, old one retired). The `repeatThreshold`-th repetition (default 3, and each multiple) adds an instruction proposal with `requiresReview: true`; nothing applies it here. `onTaskEnd` writes a `record` per task — `verified`/`refuted` are `confidence: 'verified'` + `source: 'verification'`, `claimed`/`none` are `assumed` + `agent`, the tag says which (LRN-03) — plus a lesson when a claim was refuted. Memory proposals are applied by the plugin (`apply: false` returns them instead); `applyProposals` is the one writer and runs `assertPermissionFree` over the batch first: no permission key (`permissions`, `grants`, `allowedTools`, `policy`, …) at any depth and no field outside `NewMemoryEntry` / the instruction shape, mirrored at the type level by `PermissionFree<T>` (LRN-08). `relevantLessons(memory, { objective, tags })` is the pre-task read: lessons only, no retired entry, no lesson sharing no word with the context. Counters go through the `CorrectionLedger` port (`recordCorrection({ agentId, week, what, at })`, ISO week in UTC); the Ledger actor (#45) implements it.

## 9. Plugins, MCP, A2A, auth

- `PluginManifest {id, version, kind: runtime | connector | memory | learning | notification | trigger | a2a | project-feature, name, description, capabilities[], config: ConfigSchema, secrets?: [{name, title, description, required}], permissions: [{scope, reason}], compat}`. `ConfigSchema` is a typed JSON-Schema subset core can validate (`validateConfig`) and the UI can render; secrets are declared beside it, never inside it; `pluginReadiness(state, facts)` is the one readiness verdict the pages and the platform share (#226). v1 plugins are in-repo modules registered at build time. Notifications v1 (`packages/platform/src/notify`): the seam is `NotificationChannel {id, deliver(notification, {workspaceId, subscriptions}) → {ok, error?, expired?}}`; a `notification` plugin implements it as a `ChannelPlugin {open({config, secret}) → NotificationChannel}`, and the app passes `defineInbox({channelPlugins, registry})` (#244): per notification `Inbox.push` asks `Registry.gate()` once — however many subscribers — which notification plugins are on, and opens each this build implements with its merged config and a `secret(name)` that goes through `openSecret` as the workspace owner (enabled + granted, audited). The channel opens the private key only when a notification has a subscription to go to, and without a contact, public key or private key it records a failed attempt naming what is missing, never an unsigned push. Browsers subscribe in Settings → Notifications (`apps/web/src/push`): `/sw.js` (`apps/web/public`) shows a generic "something needs you" notification per push — it cannot read the inbox itself — and focuses or opens the app on click. Triggers v1: HMAC-validated webhook → Task. **Runtime kinds (#313):** a `runtime` manifest declares what it is with a capability: `harness` (a product with its own loop and sign-in, driven through its CLI or SDK, e.g. Claude Code), `model` (the platform runs the loop over a model API, e.g. `anthropic-api`) or `remote` (an A2A peer). Core's `runtimeKindOf(manifest)` reads it. This is independent of `daemon-hosted` / `platform-hosted`, and `/plugins` groups runtimes by it. **Usage limits (#261)** are a runtime capability, `usage-limits`: the runtime supplies a `QuotaSource {id, version, runtime, probe?(env, ctx), fromSignal?(signal, env)}`, which is not a plugin kind. The daemon runs the build's sources (`builtinQuotaSources()`). `claudeCodeQuota()` maps a session's `rate_limit_event` to one window and probes an idle account's `/usage`; `anthropicApiQuota()` answers `not-reported` with its reason. Snapshots are normalized (`QuotaWindow`: utilization 0..1, `resetsAt`, `status`), merged with `mergeQuota`, and stored on the Machine.
- **Project feature plugins (#330 contract, #332 wiring, #335 git).** `ProjectFeatureManifest` is a manifest of kind `project-feature` with a second schema, `projectSettings`: what a project stores under `features[id]` (its presence enables the plugin for that project); `config` stays the plugin's workspace-wide settings. A stdio connector bound to another machine (`machine`, `*` = any) is left out and, with every missing or turned-off one, named in the prompt's "Connectors not available". ### Target — plugins track (#224)

What the bullets above describe is built but not load-bearing: nothing in production registers a plugin, calls `requireEnabled`, reads `PluginState.config` or opens a Registry secret (`docs/runbook.md` §10). This is the design the sub-issues of #224 implement (`docs/decisions.md`, 2026-09-19); each replaces its part of this subsection with the as-built text.

- **As wired in the app (#231).** `apps/web/src/plugins/catalogue.ts` exports `pluginCatalogue` (the manifests, memory default before flat so it is the slot's default) and `runtimeCatalogue(options)` (`anthropic-api` → `anthropicApiRuntime`, the harness runtimes `claude-code`, `copilot-cli`, `codex-cli` → daemon, #322); `platformActors` hands the first to `defineRegistry({ kek, catalogue })` and the second to both `createSessionFactory({ registry, runtimes })` and `defineRoutingActor({ registry, runtimes })` (overridable as `PlatformPorts.catalogue` / `runtimes`). The Worker has no `ANTHROPIC_API_KEY`: the only key is the workspace's `anthropic-api-key` secret. Memory and learning follow the active plugin (`memoryCatalogue` / `learningCatalogue`, #242; the flat memory plugin durable on the FlatMemory actor, #281); notification implementations are still wired statically (#244). The A2A server (#245) is `{ manifest: a2aServerPlugin, enabledByDefault: false }`; its implementation is the Worker's A2A mount, which asks the Registry on every request (see the A2A bullet above).
- **Catalogue = manifest + implementation, assembled at the composition root.** Manifests live beside their code (`@agentic/runtimes`: `anthropic-api`, `claude-code`, `copilot-cli`, `codex-cli`; `@agentic/memory`; `@agentic/learning`; `notify`: web push; `mcpConnector()` and an A2A peer template mint one manifest per instance a user adds). `apps/web/src/actors.app.ts` builds `{ manifest, impl }[]` and injects it: `defineRegistry({ kek, catalogue })` gets the manifests; Session, Routing and Inbox get the implementations — runtime `{ host: 'local', open } | { host: 'daemon' }` (replaces `if (runtime !== 'anthropic-api')` in `createSessionFactory`), memory → `MemoryPlugin`, learning → `LearningPluginFactory`, notification → `NotificationChannel`. `packages/platform` never imports a plugin package it does not already depend on.
- **Manifest.** `config` becomes `ConfigSchema`, a typed JSON-Schema subset with a pure `validateConfig` / `configDefaults` in core; `secrets[]` is declared apart from it, each entry with its `secret:<name>` scope. `pluginReadiness(state, facts)` — `ready | disabled | needs-config | needs-secret | needs-grant | needs-machine | no-kek` — is one pure core function the pages and the platform share; the caller supplies the facts (secret names, environments, whether a KEK is set), the function hops nowhere.
- **Built-ins are virtual until touched — as built (#229).** `defineRegistry({ kek, catalogue })`; an entry is a manifest or `{ manifest, enabledByDefault: false }` for one that ships switched off. `current(id) = stored record ?? catalogue default` (enabled, every declared scope granted, `registeredAt: 0`); state keeps the owner's config values only and every view merges them over `configDefaults`, so a new build's defaults flow through. Reads never write (pinned by a test on the storage's saves); the first mutation materialises the record and saves in the turn; a stored built-in's manifest is always overlaid from the build — undeclared grants lapse, a scope no build declared before is granted once (`seenScopes`), one the owner revoked stays revoked; `register` over and `remove` of a built-in refuse `builtin`; a plugin a later build drops falls back to its stored record. `openSecret` works for a built-in that was never materialised. `memory` and `learning` are single-slot kinds: `active[kind]` names the one plugin in use.
- **Secrets are never config — as built (#229).** In through `Registry.setSecret`, out only through `openSecret(name, pluginId)` (enabled + granted, audited). `configure` (and `register`'s config) validates against the manifest's `ConfigSchema` with defaults filled in — `BadConfigError` names every path, unknown keys included, and nothing is stored. A manifest's `secrets[]` entry without its `secret:` permission is a `bad-manifest`.
- **One hop.** The Registry side is built (#229): `gate({ runtime })` → `{ runtime: { id, enabled, config } | null, memory, learning, channels: { id, config }[] }` — `null` when no runtime plugin has that id, memory / learning the ACTIVE plugin of the slot, channels the enabled notification plugins, every `config` ready to use; it reports and never throws. `overview()` is one live read (plugins, active slots, secret names, `hasKek` — the `pluginReadiness` facts minus the machines) and `dependentsAll()` one walk of the workspace for every plugin. Still to come (#230): `Routing.run` calls `Registry.gate({ runtime })` once, before a route is written: `{ runtime: { enabled, config }, memory, learning, channels }`. The result rides on the `SessionOpenSpec`, so the session's memory and learning ports need no second call. Pages read `overview()` and `dependentsAll()` — one call each, not one per plugin.
- **Flow: a key set in the UI reaches a turn.** `/plugins/anthropic-api` → `Registry.setSecret('anthropic-api-key', …)` (sealed under `WORKSPACE_KEK`) → a message → `Routing.run` → `gate()` (applies `config.defaultModel` when the agent names none) → the session factory's local runtime → `Registry.openSecret('anthropic-api-key', 'anthropic-api')` → `createPlatformModelAgent`. No key → `no-api-key`, naming the plugin page. There is no deployment-wide key, and no plaintext is cached in the isolate.
- **Flow: a plugin is disabled.** `Registry.disable` saves, audits and returns the dependents → the next `Routing.run` fails the task `plugin-disabled` (recoverable); schedules follow, since a firing goes through `Routing.run`; the `fallback-api` path is refused; `openSecret` refuses as defence in depth; running sessions finish. Memory or learning disabled → new sessions skip retrieval and writes, the data is kept. Re-enabling restores everything.
- **Flow: an environment is added from the web.** Machine page → owner-only `Machine.putEnvironment(input)` (never a platform or MCP tool; elevated when it turns `bypassPermissions` on) → `env.request` frame, tracked like `fsRequest` → the daemon checks its `policy.json` (set from the page through `policy.request`, or on the machine; locked there wins), contains every root by realpath, allocates the `profileDir` itself, writes `environments.json` atomically, calls `setEnvironments` → `env` + `env.response` → the Machine folds the descriptors and the page shows the row, `signed-out`, with **Sign in…** (the runtime's login relayed, #484) or `agentic-daemon env login <id>` for a runtime the daemon cannot relay.

## 11. Zero feedback loop

This app is the dogfood consumer for `@sigx/zero`. ## 12. Risks and chosen defaults

| Risk | Default |
|---|---|
| Durable Object eviction during long model calls | task-based driver, append per event, "interrupted, resume?" |
| `CLAUDE_CONFIG_DIR` isolation on macOS Keychain | Windows only in v1; EXE-07 conformance test before enabling macOS |
| Node 22 global WebSocket in the daemon | assume it works; fall back to `ws` |
| Chat log growth | 200-entry window in state, rest in the log, compaction on save |
| Session record growth (a live chat session runs for weeks) | window paged out to `SessionPage`s, index without prompts and capped to `INDEX_TURNS`, replied commands without inputs, transcript snapshot bounded (#198, #391); the machine owns a daemon session's history — the platform keeps `RETAINED_PAGES` pages and reads older events over `history.request`, a hole is a named error (#397) |
| API transcript growth (the model's history on resume) | whole, in `SessionTranscriptPage`s outside the record, so no storage cap trims what the model remembers (#397); cutting it to a context window is compaction, #401 |
| Daemon session log growth (one file per chat member for the life of the chat) | trimmed after every turn to `retention.maxBytes` (64 MB) of whole turns; what went is a named `gap` (#397) |
| Web Push on Workers | VAPID ES256 over WebCrypto, keys per workspace through the Web Push plugin (#244); contentless push, so the notification is generic; `aes128gcm` payload encryption is a follow-up |
| Collaborator policy (open decision 4) | `'all'` within the workspace, depth 3, concurrency 3 |
| Learning review policy (6) | memory automatic, instructions reviewed |
| Billing (7) | user-provided keys |
| Search (CHT-10) | substring per chat; full-text later |
| `@sigx/actors` pre-1.0 churn | pin `^0.9.2`, accept minor churn |
| `@sigx/cli` `actors` scaffold layer throws | scaffold `--target cloudflare`, add the DO class by hand |
