# Decisions

Dated product and engineering decisions that the requirements leave open (requirements §18). Newest last.

## 2026-09-17 — bootstrap

- **Estate packages**: `@sigx/ai*` 0.1.0 is published before feature work starts (signalxjs/ai#15); the repo pins every sigx package from npm through the `catalog:`. Local checkouts are never linked.
- **First integrations (open decision 1)**: Claude Code via `@sigx/ai-agent-claude-code` + Anthropic API via `modelAgent` over `@sigx/ai-anthropic`. Copilot CLI second.
- **Daemon platform (2)**: Windows first; macOS/Linux follow from the same Node code once EXE-07 isolation is validated there.
- **Environment isolation (3)**: Claude Code accounts are isolated by `CLAUDE_CONFIG_DIR` per environment; setting sources are `['project']` only — the repository's own instructions load, the operator's `~/.claude` never does (#461).
- **Collaboration policy (4)**: agents may delegate to every agent in the workspace by default; depth 3, concurrency 3, budgets split from the parent.
- **Learning policy (6)**: memory writes are automatic; instruction/skill changes require review and become new config versions.
- **Credentials and billing (7)**: users bring their own API keys, encrypted at rest with a per-deployment key. Runtime OAuth credentials stay on the machine.
- **Mobile (8)**: responsive web only in v1; a Lynx native shell is a later phase.
- **Plugin model (9)**: in-repo modules registered at build time; enable/disable per workspace; no marketplace.
- **Interoperability (11)**: A2A 1.0 JSON-RPC binding (SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask); MCP Streamable HTTP client for tools; platform MCP server as the orchestration surface.
- **Login**: GitHub OAuth behind an `AuthProvider` interface so more providers can be added.
- **Skin**: `@sigx/zero-daisyui`, derived into the `agentic` design system (`@agentic/ui/design-system`) with the `control-room` theme from `docs/design/HANDOFF.md`.
- **Theme (2026-09-17, #84)**: dark only in v1 — `control-room` is the one theme, set as both scheme defaults; no toggle in the shell. A light pair is a later issue if wanted.
- **Repo scope**: all work stays in `andtii/agentic` as private `@agentic/*` packages; generic pieces are tracked in `promotion.md`. Friction with `@sigx/zero` is filed on andtii/zero-wip.
- **Process**: issue → worktree → PR → green CI → squash merge. `main` requires a PR and green checks, zero approvals. ~~No Copilot review step.~~ Revised 2026-09-21 (#448): the sigx-standard flow in full — Copilot is requested as reviewer on every PR and its threads are resolved before merge; the ruleset already required thread resolution, so the deviation only made PRs stall.
- **Orchestration from outside**: every capability is an actor method; the platform MCP server projects them so an external MCP client can drive every daemon on every machine (phase 3), and the principal model carries an `external` kind with scopes from the first contracts issue.

## 2026-09-18 — working folders (#185, #190)

- **Where work runs is chosen within `cwdRoots`, never beyond them.** The environment's `cwdRoots` (decision 3) stay the security boundary and stay machine-local — they are edited in the daemon's `environments.json`, never from the web. Inside them a folder is picked per task (`TaskContract.workdir`), per chat member (`Chat.setWorkdir`, sticky for that chat and copied into each activation's task), as an agent's default (`execution.defaultWorkdir`, only in its `defaultEnvironmentId`) or per schedule (`ScheduleSpec.workdir`). A folder always travels with its environment (`WorkdirRef`). The router resolves it once per task (EXE-12: task → a delegating parent's folder in the same environment → the agent's default → the first root), checks it with `pathWithin` on the machine's OS, and fails the task `workdir-outside-roots` rather than open a session anywhere else. The daemon adds a realpath check against symlink escapes, and creates new git worktrees only inside the roots, for the owner only (#188). **Amended 2026-09-19 (#224):** "never from the web" holds only until #236 – #239 merge — from then the roots may also be set from the web, inside what a machine-local policy allows; see "plugins you enable and configure" (c) below.

## 2026-09-18 — chat attachments (#203, #204)

- **References, not bytes.** A file pasted, dropped or picked into a chat is uploaded once and stored in R2 under `files/<workspace>/<chat>/<fileId>`. A message references it as `agentic-file:<chatId>/<fileId>` in an `image` or `file` part. Actor state and daemon frames never carry attachment bytes, except the images the router inlines into one turn, within `CHAT_FILE_INLINE_BUDGET`.
- **Access follows history visibility.** Whoever can see the message a file was posted in can read the file:
  - users and external clients: every file in the chat;
  - an agent member: files from its `historyFrom` onward;
  - a non-member agent: nothing (fails closed, as in MEM-11).
  There is no separate per-file access list. An agent may re-attach a file it can see.
- **Retention.** Attachments live as long as their chat. There is no lifecycle rule on `files/`, unlike the 30-day artifacts rule (decision 12). They are deleted when the chat or workspace is purged. An upload never posted into a message is swept after 1 day.
- **v1 scope.**
  - jpeg/png/gif/webp images reach the model as image blocks.
  - Text-like files are read through `chat_file_read`, up to 256 KiB.
  - Any other file, up to 10 MiB, can be uploaded and downloaded by users; agents see only its name, type and size.
  - PDFs as document blocks, image blocks in tool results, and materializing files into a claude-code cwd are follow-ups.

## 2026-09-19 — plugins you enable and configure (#224, #225)

Setting up a runtime meant editing files: a deployment-wide `ANTHROPIC_API_KEY` for `anthropic-api`, a hand-written `environments.json` for `claude-code`. The plugin system that should own this — `PluginManifest`, and the Registry actor with enable / disable / configure / grant / dependents / sealed secrets — shipped complete and tested with no production caller: nothing registered a plugin, nothing called `requireEnabled`, and the live Plugins page was always empty. Three decisions make it the way a workspace is set up. The scope of row 9 is unchanged: in-repo modules, no marketplace, no dynamic code loading, no out-of-process isolation.

- **(a) Plugins are load-bearing. Amends row 9.**
  - **Catalogue.** Every capability in the build — runtimes, connectors, memory, learning, notification channels, A2A — has a manifest beside its implementation. The composition root (`apps/web`) assembles `{ manifest, implementation }` pairs: the Registry gets the manifests; Session, Routing and Inbox get the implementations. "Installed" means "present in the build".
  - **Built-ins are virtual until touched.** `effective(id) = stored record ?? catalogue default` (enabled, the schema's defaults, the declared grants). A read never writes — the Registry's `list` is a live read, and `onDeactivate` never runs on Workers — so existing workspaces need no migration. The first mutation materialises the record and saves inside the turn. A stored built-in always carries the build's manifest (a new build is the upgrade), and `remove` on a built-in is refused.
  - **First-party scopes are granted by default — the explicit exception to PLG-04.** PLG-04 exists so that installing something does not hand it every secret. A built-in is not installed by the user: it is the platform's own code, shipped in the same build, and PLG-05 requires it to work before the user has assembled anything. So a built-in's *declared* scopes are granted by default, and a scope that a later version newly declares is granted once (`seenScopes`) — otherwise an upgrade would silently break a working runtime. What PLG-04 protects still holds: a built-in gets only what its manifest declares, each scope with a reason the user can read and revoke, and a plugin instance the user adds (an MCP connector, an A2A peer) gets nothing until granted.
  - **Secrets never live in `PluginState.config`.** `list` / `get` return config to every principal of the workspace, agents and machines included. A manifest declares its secrets separately (`secrets[]`, each with a matching `secret:<name>` scope); values go in through `Registry.setSecret` and come out only through `openSecret` — plugin enabled, scope granted, every open audited. `configure` validates against the manifest's schema and rejects unknown keys, so a secret cannot land in config by accident.
  - **The gate has teeth, in one hop.** `Routing.run` asks the Registry once per task (`gate()`). A disabled or missing runtime fails the task `plugin-disabled` (recoverable) before a route is written — schedules included, since a firing goes through `Routing.run`, and the `fallback-api` path included. Running sessions are never interrupted (AC-13 as written).
  - **Memory and learning are single-slot kinds.** Exactly one plugin of each is active per workspace. Disabling the active one means new sessions skip retrieval and writes; stored memories are kept and stay browsable. Switching the active memory plugin is a migration (MEM-09) that flips the slot last.
- **(b) Strict BYO key. Amends row 7.** The deployment-wide `ANTHROPIC_API_KEY` is removed, not kept as a fallback. The key of `anthropic-api` is the Registry secret `anthropic-api-key`: set on the plugin's page, sealed under `WORKSPACE_KEK`, opened once per session open (never per turn, never cached in the isolate). Why no fallback: one key silently serving every workspace is the opposite of row 7's "users bring their own keys", it hides who pays, and it keeps a second, file-based way to configure a runtime alive — the thing this track removes. Consequence, accepted: an existing deployment's API agents fail `no-api-key` (the message names `/plugins/anthropic-api`) until the owner enters a key once. `pnpm dev` no longer reads or writes the variable; a leftover line in `.dev.vars` is ignored.
- **(c) Environments may be managed from the web, under a machine-local policy. Amends "working folders" (2026-09-18).** That entry kept `cwdRoots` editable only in the daemon's `environments.json`, "never from the web". In practice that meant hand-written JSON and a daemon restart per change, on every machine. `cwdRoots` remain the security boundary; what changes is who may move it, and how far.
  - **Threat model.** A compromised platform or web session can already execute code inside an environment's `cwdRoots` — that is what a session is. Web-managed environments add two risks: *widening* the roots (reaching `C:/Users/me` from sessions that were confined to `C:/src`), and *prompt injection* (an agent talked into adding an environment for itself).
  - **Controls.**
    - The ceiling is set on the machine, never from the web: `policy.json` beside `environments.json`, `{ webManaged, allowedRoots }`, **off by default**, changed only by local commands (`agentic-daemon pair … --allow-root <dir>`, `agentic-daemon policy …`). No frame can alter it, so a hijacked web session can place roots only inside what the machine's owner allowed at the keyboard.
    - `Machine.putEnvironment` / `removeEnvironment` are owner-only actor methods and are **never** a platform tool or an MCP tool: no agent principal and no external client can reach them. A test enumerates those surfaces.
    - The daemon checks every requested root by realpath containment in an allowed root, and refuses UNC paths, junction and symlink escapes, its own config and state directories, and any `profileDir`.
    - `profileDir` is never accepted over the wire — the frame's type has no such field. The daemon allocates it (`<configDir>/profiles/<environmentId>`), and it still never leaves the machine (decision 3).
    - The runtime must be one the daemon has a driver for; removal is refused while the environment has active sessions; every put and remove is audited with the requested roots.
  - **What stays local.** Signing in to the runtime (EXE-10): the page shows `authStatus` and the command to run (`agentic-daemon env login <id>`), never a path. The file and the CLI (`agentic-daemon env add | list | rm`) stay first-class: a machine with the policy off is set up entirely from its own terminal, without hand-editing JSON and without a restart.

## 2026-09-19 — connector credentials reach a daemon by `tool.call`, not on the spec (#280)

An agent's MCP connectors now open on daemon-hosted sessions, so their credentials have to reach the machine.

- **Not on `OpenSpec`.** The Machine actor keeps every hosted or queued session's spec in durable state and re-sends it after a reconnect (EXE-09). A value on the spec would be persisted by the platform, against EXE-10 and decisions 2026-09-19 (a).
- **The daemon asks, per open.** The spec carries secret NAMES (`OpenSpecConnector.auth`). While opening, the daemon makes its own `tool.call` `connector_credentials {connectorId}`, which is never offered to the model. The platform answers only for a ready connector named by the calling session's recorded gate. It opens each secret under the connector plugin's own `secret:` grants, as the workspace owner, and the Registry audits each one. The value travels once in the `tool.result` and is recorded nowhere.
- **On the machine.** Values stay in memory for that session: request headers for HTTP, the child's environment for stdio (on top of the allowlist, never the daemon's whole environment). They are scrubbed from any error the agent sees and are never logged or written to the event log or any file.
- **Why not a new frame pair.** `tool.call` already carries the agent principal the Machine minted for the session, and the answer runs where the session's gate is. A dedicated frame would repeat that plumbing without adding a check.

## 2026-09-19 — provider usage limits per account (#261)

With several Claude Code accounts connected, neither a person nor an orchestrating AI could see how close each account is to its plan limits. `claude` → `/usage` shows it, and OPS-07 asks for it.

- **Quota is not the Ledger.** The Ledger records what was consumed ($, tokens). A quota snapshot records what is left, as the provider reports it (`QuotaWindow`: utilization 0..1, reset time, status). They are separate types, and the words differ too: "usage" stays the Ledger's word, "quota" is the new concept. The MCP/OAuth scope is still named `usage`, so a later `usage_summary` over the Ledger can live beside `usage_limits`.
- **One source per runtime.** A runtime supplies its own `QuotaSource` (`probe?`, `fromSignal?`). *Amended by #313:* this is not a plugin kind of its own; the runtime plugin lists the `usage-limits` capability. Only normalized snapshots cross package boundaries and the wire; credentials and profile paths stay on the machine (EXE-10).
- **v1 is Claude Code subscriptions.** `anthropic-api` reports `not-reported` with its reason (per-minute rate limits, not a plan allowance), never an empty bar (PLG-09).
- **The probe uses an experimental SDK call, behind a flag.** Freshness comes from two places:
  - the rate-limit events of running sessions, which are passive and always on
  - an idle-account probe through the Agent SDK's `usage_EXPERIMENTAL_…` call on a query that is never prompted

  The spike measured the probe on four local profiles: no model call, cost 0, no leftover process, 0.25–0.9 s. It ships **on**. `agentic-daemon run --quota-probe off` leaves the stream only, and the probe returns `null` on any failure, so an SDK change degrades to passive rather than breaking.
- **No automatic account switching (EXE-12).** The limits are information for planning. `usage_limits` and the UI never move or re-place work; the caller chooses an environment explicitly, as `sessions_open` already requires.

## 2026-09-19 — `ask_user` questions outlive the turn (#285)

A blocking `ask_user` lost every answer that came after the tool call timed out. That includes the engine's MCP timeout, which the platform does not control, and the router closing the session at turn end.

- **Async, not a longer wait.** Raising timeouts would only move the cliff: an hours-long pause still needs the engine, the daemon and the machine to stay up throughout. In a chat, `ask_user` waits a short window (25 s) and then answers `pending`. The agent ends its turn, and the answer starts it again as a new task in the chat. The question outlives the turn and the session; it is not cancelled when the call ends.
- **The answer is always visible.** It is posted in the chat as the person who gave it, mentioning the asker, before anyone is started. If starting the agent fails, the chat says so.
- **Continue the same conversation where possible.** The follow-up resumes the asking session's engine conversation when a daemon ran it on the same machine, environment and runtime. Otherwise it opens fresh, with the question, the answer and the chat as context.
- **Chatless asks keep blocking.** A delegated child runs outside any chat, and its parent already has its result by the time a late answer could start it again. Its `ask_user` waits as before, capped by the daemon's tool timeout.

## 2026-09-19 — harness, model and remote runtimes (#313)

A `runtime` plugin is one of three kinds, independent of where it runs:

- **Harness runtime.** An agent product with its own loop, tools and sign-in: Claude Code, and later Codex, Copilot and others. We drive it through its CLI or SDK package; the delivery doesn't matter. The platform hands it a turn and follows its events, and credentials stay with its account. Capability `harness`.
- **Model runtime.** The platform runs the agent loop itself over a model API with the workspace's key (`anthropic-api`). Capability `model`.
- **Remote agent.** An independently hosted agent reached through an adapter, such as an A2A peer. Capability `remote`.

Where it runs is the other axis: `daemon-hosted` or `platform-hosted`. Today every harness is daemon-hosted and every model runtime is platform-hosted, but nothing forces that. "CLI runtime" is not used, because a harness can arrive as an SDK.

**Usage limits are a runtime capability, not a plugin.** A runtime that reports its accounts' plan limits lists `usage-limits` and supplies a `QuotaSource`. #261's separate `quota` plugin kind and its `claudeCodeQuotaPlugin` manifest are removed: the manifest had nothing to configure, and its switch did nothing. `/plugins` shows Harness runtimes, Model runtimes and Remote agents as separate sections.

## 2026-09-19 — GitHub Copilot CLI is a harness runtime, driven through its SDK (#319)

`copilot-cli` is the runtime id, plugin id and agent id. The daemon drives Copilot through `@github/copilot-sdk`, which starts the Copilot runtime once per environment and speaks JSON-RPC to it. The SDK is not the interactive CLI, and it ships the runtime for each platform. That gives us permission callbacks, native client tools, resume by session id, and `account.getQuota` for usage limits without a model call.

- **Isolation:** each environment gets its own `COPILOT_HOME`, and the parent's `GH_TOKEN` / `GITHUB_TOKEN` / `COPILOT_GITHUB_TOKEN` are stripped. That is not airtight. A profile with no Copilot login of its own falls back to `gh auth token`, and the GitHub CLI reads its token from the OS keyring whatever its config dir. So the doctor warns (`shared-login`) instead of claiming isolation, and `env login` gives the profile its own login, which Copilot prefers.
- **Usage limits:** Copilot meters requests per month. Premium requests, chat and completions each become a `month` window counted in `requests`. An unlimited entitlement has no utilization.
- **Permissions:** `harness-filtered`. Copilot runs reads inside the folder without asking. Platform tools and connectors run in the daemon as client tools with `skipPermission`, and their handler asks the platform policy, so every call to one is ruled on.
- **Memory:** repository instructions and config discovery are on (`skipCustomInstructions: false`, `enableConfigDiscovery: true` — #461, previously off), so `.github/copilot-instructions.md` / `AGENTS.md` in the folder apply as in the interactive CLI. Memory comes from the platform, labelled as such (MEM-10).

## 2026-09-19 — Codex runs through `codex app-server` (#320)

The Codex harness runtime has the id `codex-cli`. The id is the plugin id, the `RuntimeId`, the `Agent.id` prefix and the quota source's runtime.

**It drives `codex app-server`**, the stdio JSON-RPC protocol the Codex IDE extension uses. It does not use `codex exec` or `@openai/codex-sdk`, which wraps `exec`. `exec` has no per-call approvals, so our policy could only choose a sandbox mode up front. It also reports no rate limits. The app-server provides:

- per-call approval requests, which go to the session's policy
- `turn/steer` and `turn/interrupt`
- `thread/resume`
- `account/read` for auth status
- `account/rateLimits/read` and `account/rateLimits/updated`, for the 5-hour and weekly windows (usage limits)

We use only the stable surface (`experimentalApi: false`). The types we use are trimmed by hand from `generate-ts` of codex-cli 0.155.1.

**Tools reach Codex over MCP, not `dynamicTools`.** The platform's tools and the agent's connectors are served on a loopback Streamable-HTTP MCP server per session, behind a bearer token. The thread's config names it as `mcp_servers.agentic` (`url`, `http_headers`). The app-server's `dynamicTools` would avoid the port, but it is experimental. Codex runs MCP tools without asking, so each tool call first goes through the session's policy before it runs. Permissions are `harness-filtered`: Codex decides which of its own commands and edits need an approval.

Isolation is one `CODEX_HOME` per environment, with the daemon's `OPENAI_*` removed. The profile's own `config.toml` still applies inside that home, including any MCP servers configured there.

## 2026-09-20 — a removed project leaves its chats pointing at it (#332)

`Workspace.removeProject` does not walk the chats: a chat keeps its `projectId`, its summary shows the id without a name, and the web renders "removed project". The router does the same for a task: a `projectId` the Workspace no longer has fails the task `project-missing` (visible, `recoverable: false`) rather than guessing a folder from the chain below (EXE-12). Reasons: the chat's project is a note in its own log, so rewriting it would mean a write per chat on a rarely used path; and a task that ran "somewhere" because its project vanished would be the silent fallback the PRD forbids. A chat is moved on with `Chat.setProject(other | null)`.

## 2026-09-21 — live sessions: one per (chat, agent), never parked (#387)

The live-sessions track (#387) replaced "one message = one task = one session = one process, killed at turn end" with a session that lives as long as the chat member does. The decisions the track took, and the answers to the questions it had to settle:

- **Sessions live per (chat, agent).** One execution session per agent member of a chat, created on the member's first activation, alive until the agent leaves the chat, the user resets it ("New session"), or the workspace is deleted. Never parked: no idle timeout, no LRU eviction, no tearing down to free capacity — agents start dev servers and watchers, and killing the process between messages breaks the dev flow. Resume is recovery only (a daemon restart, a reboot), from the ref the runtime itself reported; a session whose machine, environment or folder changed starts fresh instead of migrating (EXE-12, EXE-13). A message arriving mid-turn steers into the running turn (#395). Capacity counts running turns, not open sessions (#394). The machine owns the full history; the platform keeps a bounded recent window (#397).
- **Approval grants across a restart.** A session-scoped grant ("allow for the rest of this session") survives a re-open of the *same* session id: it lives in the record's event log, which the re-open continues, so the platform-side policy still honours it. It dies with "New session" and with the member's removal, since those delete the record. Reason: the user granted it to this conversation, and a re-open continues that conversation; a reset or a removal ends it.
- **Configuration drift on a live session (AGT-07).** `model` and tool grants apply on the next turn, through `Session.configure`. Approval rules and constraints apply at once: they are evaluated platform-side per request, so no runtime call is needed. Instructions / system prompt, environment, folder and runtime require "New session" — a placement move already forces a fresh id. Reason: it matches what `configure` can carry to a running runtime session versus what only `open` can.
- **Past turns collapse to their final message in the chat feed.** There is no `Session.events(from)` range fetch for expanding an old turn (#398). Reason: #397 moves old history to the machine, and the chat's `msg` entry is the durable artefact of a turn.

## 2026-09-21 — an agent is an account, a chat is a machine (#414)

Three Claude Code accounts on two machines were six environments and therefore six agents, although "claude-2 on the Mac" and "claude-2 on the PC" are one login. Projects already resolve *where the code lives* per environment; this track does the same for *where the login lives*.

- **An account is derived, never stored.** An account is `(runtime, identity ?? label)` of the environments that report it (`accountKeyOf`, `packages/core/src/account.ts`): the identity the runtime's `inspect` read from the profile — an email for Claude Code — or, until it is signed in, the environment's account label. Environments on different machines with the same key are one account. No actor, no record: the directory is folded from the machine index on demand, so a sign-in on a machine shows up without anyone registering anything. An identity never matches a label (`sameAccount`), so a label-bound agent stops matching an environment once it reports an identity, and the config page says so rather than guessing.
- **An agent binds to an account** (`ExecutionDefaults.account`). `defaultEnvironmentId` stays as the pin to one environment, and as the account's source when a task names a machine but the agent names no account — so existing agents keep working unchanged, with no migration.
- **A chat names the machine** (`Chat.setMachine`), a note entry exactly like the project, copied into every activation's task as `TaskContract.machineId`; a delegated child inherits the parent route's machine, a schedule takes one. The router resolves `(machine, account) → environment` once at `run` and binds `environmentId` and `machineId` together — no scan of the machine index, so two daemons that both minted `env_work` cannot be confused (they are, today, by `locateEnvironment`'s index order; a task's machine is the disambiguator). EXE-12 holds: fixed at resolution, recorded in `environment.chosen` with the machine and the account, never rebound.
- **A pick is required; nothing is auto-placed.** New chat preselects the last used machine (`Workspace.lastMachineId`, as `lastProjectId`). A chat without a machine behaves as before; an account-bound agent with no machine named fails `no-machine`. An account absent on an online machine fails `account-not-on-machine` (recoverable: sign in there, run again) — it is not "offline", so `fallback-api` never applies to it; an explicit task `environmentId` wins when the named machine reports it and is otherwise ignored, with the audit saying so.
- **A machine switch is a placement move, not a migration.** The live-sessions rule above (#387) already refuses a bound session whose machine, environment or folder changed and opens a fresh one; `Chat.setMachine` rides it — the next message of each member runs on the new machine in a fresh session, work in flight finishes where it runs, the chat's history stays. A changed `execution.account` applies the same way.

## 2026-09-21 — the daemon keeps itself current (#358)

The track made an installed daemon something the platform keeps current: versioned releases and channels, updates decided on the web, a supervisor that swaps and rolls back, harnesses as separate installs, and an interrupt / resume path so a restart, an update or a crash never strands a task. Operating it: `docs/runbook.md` §5.4–§5.6; the seams: `docs/architecture.md` §5b and §7. The decisions, as shipped:

- **Re-planned after live sessions (#387).** The track was written before a chat session became live for the life of the chat, so it was re-planned before any of it landed:
  - **The platform owns resume.** It already holds each session's spec and the runtime's own ref (`session.ref`), and re-opens a lost session under the same id with `spec.resume = ref`. So the daemon keeps no session manifests, and there is no `hello.resumable` and no `session.suspended`. A host-side end is a `session.closed` with a `code` (`SessionClosedCode`: `restart | update | harness-update | draining | harness-missing | resume-failed`); an uncoded close is handled the same way.
  - **Idle means no running turns, and drain means no new turns.** A live session with no turn running never blocks an update. A draining machine refuses turn-starting prompts (they park as at capacity and go out after the restart) and still opens sessions; running turns finish, or are interrupted at the timeout or with "now".
  - **An update restarts every live session and stops its background processes** (dev servers, watchers). Conversations continue through resume: a running turn is interrupted and offered Resume; an idle session re-opens with its next message, and a message parked on it is delivered there (#433). The Update-now confirm names the turns it interrupts and the sessions it restarts.
  - **The host-side interruption was a live bug and was split out as #420**, landing first with no contract dependency: `Session.hostEnded` ends a running turn interrupted, and `Routing.resume` re-hosts the same session (`rehost`), falling back to a fresh session with `resumeFrom` when the runtime refuses (`resume-failed`).
- **Versioned releases and channels via rolling releases.** A `daemon-v<semver>` tag builds the GitHub release `daemon-v<semver>` with a `manifest.json` (version, channel, commit, protocol, notes URL, per-`<os>-<arch>` asset URL + sha256 + bytes, and the harness packages). Two rolling pre-releases carry one manifest each at a fixed URL: `daemon-latest` (every `main` push, channel `latest`) and `daemon-stable` (the newest non-prerelease tag, channel `stable`). Nothing reads GitHub's "latest release", because release-drafter's app releases own it. The version is stamped at build (`hello.build`), and the installers take `AGENTIC_CHANNEL` / `AGENTIC_VERSION`, verify sha256 and honour `AGENTIC_RELEASES`. Reason: fixed manifest URLs let the installers, the CLI and the platform's `ReleaseDirectory` read a channel without GitHub's API or its notion of latest.
- **Main builds are `<x.y.z>-main.<commit unix seconds>.<sha7>`** (#437). The commit time is a numeric prerelease identifier, so semver orders main builds by when their commit was made and all of them below the `x.y.z` release; a digits-only sha7 with a leading zero is written `g<sha7>` so the version stays valid semver. The earlier `-main.<sha7>` ranked by sha, which says nothing about age; the daemon went to `0.1.1` with the change so every `0.1.0-main.<sha7>` machine sees the new builds as newer.
- **Feature flags, not a protocol bump.** `hello.features` (`update`, `harness`) gates the new frames; the protocol stays `v: 1` and every new field is optional. A daemon below `MIN_DAEMON_VERSION` is marked `outdated` but still served.
- **The platform decides, the daemon executes, the supervisor swaps.** A global `ReleaseDirectory` reads the channel manifests hourly; the Machine compares, holds the update state, channel and policy (`manual` by default, `auto-when-idle`, `window`), sends `update.request`, and judges it on the next `hello`. The daemon downloads, verifies, stages, drains and exits `75`; the supervisor (`<root>/supervisor/supervise.mjs`, outside the folder it swaps) keeps `daemon.prev` and rolls back when the new version is not ready within 90 s or crashes twice in 2 minutes. It also fixed #353: the service now runs the supervisor, which relaunches the daemon after any exit.
- **`draining` travels as `busy`, pending an upstream code.** `@sigx/ai-agent`'s `WireErrorCode` has no `draining`, and widening it would change every platform use of `WireReply`. So a draining daemon answers `code: 'busy'` with a message starting `draining:` (`drainingReply` / `isDrainingReply`); the platform already parks `busy` and prompts again, which is the behaviour a drain needs. A real code is on `docs/promotion.md`.
- **Harnesses are separate packages, and the Copilot seam is the SDK's stdio connection.** The daemon zip keeps the SDKs' JavaScript and drops their native packages (≈ 330 MB → ≈ 8 MB); each runtime ships as `harness-<runtime>-<version>-<os>-<arch>.zip`, uploaded once per pinned version (#441), installed under `<root>/harnesses/<runtime>/<version>/`. Claude Code is pointed at its executable with `pathToClaudeCodeExecutable` and Codex with `codexPath`. For Copilot the spike found that `@github/copilot-sdk` takes `connection: RuntimeConnection.forStdio({ path })` before it resolves its platform package, so the seam is `CopilotClientInit.cliPath`, passed through the driver's existing `createClient`; no `createRequire` into the harness folder. `copilot-runtime` is not a user CLI, so Copilot still signs in with `copilot` on `PATH`. A harness on `PATH` is never used silently. A machine without `selection.json` wants all three, and a starting daemon installs what it lacks, so a machine updated from a bundling build heals itself.
- **Owner-only update and harness methods, never a tool.** `Machine.requestUpdate` / `cancelUpdate` / `setUpdatePolicy` / `setChannel` / `requestHarness` admit a user principal only, like `putEnvironment` (decisions 2026-09-19 (c)), and the tool-boundary source scan covers them: no platform tool, no MCP tool and no agent principal can restart, update or reconfigure a machine.
- **Ask before resuming, per-agent opt-in.** `execution.onInterrupt` is `ask` by default (OPS-06: nothing re-runs unseen); `auto` resumes once per interrupted turn on the machine's next `hello`, and a second interruption of the same turn asks.
- **A machine that vanishes is a wait.** Running routes on a machine that goes offline wait `machine-offline` (shown apart from `environment-offline` and from failure, OPS-04) and go on when it returns; after 24 h they fail `machine-lost`, recoverable.
- **Deviations the sub-issues recorded.** Whole-daemon drain accepts `session.open`, while a harness drain refuses a new session on that runtime with `draining`. One harness request per machine at a time (not per runtime), and never during a daemon update. `hello.features` lists `update` only under the supervisor, since exit 75 without one would just stop the daemon. Rollback from the page is offered after an applied update, to its `from`.

## 2026-09-21 — model and permission mode per chat member (#450)

The member card switches a member's model and Claude Code permission mode. The decisions the track took:

- **Per chat member, not the agent's config.** `Chat.setOptions(agentId, {model?, permissionMode?})` writes a note like the folder override; `null` clears a key back to the agent's config, then the runtime plugin's `defaultModel` / `defaultPermissionMode`. Other chats and the agent's config versions are untouched.
- **Next turn, never the running one (AGT-07).** The router reads the member's options when it places a turn: a fresh session opens with them (`OpenSpec.model`, `OpenSpec.permissionMode`); a reused one is configured to them (`Session.configure`) before its prompt. A prompt that steers into a running turn joins it as it is. An override cleared to nothing (no config value, no plugin default) sends the runtime's own `default` for that key, so a clear never leaves the old value running. The Session records what it runs with (`SessionInfo.options`): the first open's, then each configure's — a re-open for the next task refreshes the spec, not the options.
- **The account's own model list.** The daemon asks each environment's runtime (`RuntimeDriver.models`, Claude Code's `supportedModels()` on an unprompted query) after `welcome` and at most every 6 h, and reports it on the descriptor. Without one, the web offers the runtime plugin's `defaultModel` enum.
- **`bypassPermissions` only where the machine allows it.** `allowBypassPermissions` on the environment in `environments.json` — set by hand on the machine, never through `env.request`, kept by a replace. Without it the router fails the task `permission-mode-not-allowed` (recoverable) and the driver refuses to open; the web does not offer the mode.
- **Modes stay within the agent's grants.** Platform tools are granted and gated by the platform in every mode. The agent's approval rules reach Claude Code's native tools only when Claude Code asks: in `default` and `plan`. In `acceptEdits` (edits), `auto` (its classifier), `dontAsk` (denies what is not pre-approved) and `bypassPermissions` (nothing asked) Claude Code decides for its native tools — the mode is the user's explicit choice for that member.
- **Leaving plan mode is an approval (#454).** In `plan` Claude Code ends with `ExitPlanMode` and the plan. The Claude Code driver asks for that call ahead of every rule, grant and fallback (`withPlanReview`), so it always reaches a person: the approval card shows the plan as markdown and answers **Approve · default**, **Approve · accept edits** or **Keep planning** (a deny that tells the model to revise). An approval — from the chat or from "Needs you" — makes the chosen mode the member's for the chat (`Chat.setOptions`) and configures the session at once: the CLI waits on this answer, so it is the one mode change inside a running turn.
- **A capability name bug fixed on the way.** A harness reports `session.configure-model`, `session.fork`, `turn.structured-output` and `agent.list-sessions`; the wire mapping only read the short names, so daemon-hosted sessions never exposed `configure`. Both mappings (daemon, Machine) now read both.

## 2026-09-21 — chats title themselves: the runtime's title first, a generated one otherwise (#460)

The chat list named every untitled chat by its members, so ten chats with Atlas read "Atlas" ten times. Claude Code's `--resume` picker shows a title per session; the list should too.

- **The runtime's title wins over anything the platform generates.** Claude Code titles every conversation itself (an `ai-title` row in its transcript, refreshed as the work moves on; `/rename` writes a `custom-title` that wins) and Copilot CLI emits `session.title_changed`; both know the whole conversation, cost the platform nothing and follow the work. The daemon reads them after every turn and reports a change as `session.title`, the runtime's ref's twin (#388). The platform generates a title only where no runtime does: the `anthropic-api` runtime runs the loop itself, and Codex names its threads but the driver does not read it yet.
- **Something at once, better later.** The first user message names the chat by its first line the moment it is posted — free, offline, every runtime. A model title (one `generateText` on `claude-haiku-4-5` over the first eight messages, with the workspace's own Anthropic key) replaces it after the first reply and once more at the eighth, so the title reflects what the chat became; a runtime title replaces either. No key means the heuristic stays: a title is a courtesy, never an error in the thread, and never a reason to hold a message.
- **A person's word is final, and runtimes do not fight.** A `rename` (or `createChat({ title })`) carries no `auto`, and no generated title ever replaces it. A runtime title is replaced only by the same session's next one, so two members' runtimes in a group chat never rename it back and forth; the provenance lives on the entry (`auto: {source, sessionId?}`), so a replay reaches the same answer.
- **Read the transcript, not the SDK.** `getSessionInfo` reads exactly the rows we want, but from the calling process's `CLAUDE_CONFIG_DIR`, not the environment's; the driver already isolates each environment by config dir, so it reads the tail of the session file itself.
- **The title call is not ledgered.** ~40 output tokens on the cheapest model, once or twice per chat, under the workspace's own key; the Registry audits every `openSecret` like a session's, and the plugin's secret and permission texts say so. A ledger row per title would cost more than the title.

## 2026-09-21 — resource pressure is shown and warned, never enforced (#400)

#387 keeps a chat's runtime session alive for the life of the chat and refused a session cap, an idle timeout and eviction: agents hold dev servers and watchers. The answer to resource pressure is to see it.

- **The daemon charges process trees, not processes.** A session's cost is its runtime process and everything under it — the dev server the agent started is that session's — sampled from one process-table read per heartbeat. Claude Code keeps one process per session, so its sessions are attributed (the driver runs each `prompt` in an async context its `spawn` reads); Codex keeps one app-server per environment, so its environments are and its sessions read unknown; Copilot's SDK starts its own runtime, so both read unknown. **Unknown is `null`, never zero.**
- **Memory warns; CPU is only shown.** A session over 2 GiB resident, or a machine over 90 % of its memory, is told to the Inbox once as `resource-pressure` and shown amber on the Machine page, and told again only after it fell under 80 % of the limit (or the session closed). A build pegging every core for a while is normal work: no CPU warning, ever.
- **Nothing is ended, throttled or moved.** The warning names the agent, the session and the number, says nothing is stopped, and leaves the decision to a person. Enforcement would break exactly the dev flow #387 protects.
- **macOS memory is what Activity Monitor calls "Memory Used"** (wired + compressed + anonymous pages from `vm_stat`), not `os.freemem()`: free pages alone read every Mac as full.
