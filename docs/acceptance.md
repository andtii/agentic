# Acceptance suite — requirements §17

Every acceptance scenario of `docs/requirements.md` §17 (`AC-01` … `AC-15`; the table skips `AC-03` and `AC-04`) maps to one scripted scenario under `apps/web/__tests__/acceptance/` and, where a part cannot run offline, to a manual checklist entry below. One file per scenario, each running end to end through the real actor host with mock daemons, drivers and models — never a re-import of a unit test. Where a deeper test proves the same path, the scenario file names it.

```sh
pnpm --filter @agentic/web test:acceptance
```

runs the whole suite: first the workerd half (`ac-NN.workers.test.ts`, `vitest.acceptance.config.ts` — the real `ActorHost` Durable Objects on Miniflare, the Worker in `__tests__/acceptance/worker.ts`), then the in-process half (`ac-NN.test.ts(x)`, the root vitest config). CI runs it in the `test` job on Node 22 (`.github/workflows/ci.yml`, "Acceptance suite"); the in-process half also runs under `pnpm test`.

Everything goes over the HTTP actor mount as a signed-in user (`workers.ts`). |
| in-process, app registry (`host.ts`) | AC-05, AC-09, AC-10, AC-11, AC-12, AC-13, AC-14 | `platformActors()` from `src/actors.app.ts` — the app's own definitions and ports — on the platform test host over memory storage; the `anthropic-api` runtime is the real local path (`createSessionFactory` → `createPlatformModelAgent` over the platform tool ports) on a scripted `mockModel`, so `delegate`, `memory_search` and the approval policy run as with a real model. |
| in-process, live pages (`../pages/live-harness`) | AC-06, AC-15 | The pages mounted as a browser tab mounts them, over the real actor wire, a `mockAgent` behind the Session actor. |

## Manual checklist

The parts no offline test can stand in for: a real Claude Code daemon, a real GitHub login, real push delivery, a real phone. Each entry names the exact commands; the deployment side is `docs/runbook.md`.

- **M1 — real machines and a real Claude Code agent (AC-01, AC-05).** On two machines with Claude Code installed and signed in: `pnpm --filter @agentic/daemon start` after pairing each through `/pair` (the code from `/machines` → "Pair a machine"). Check `/machines` lists both with their environments and `online`; stop one daemon and check only that machine goes offline. Then, on the preview deployment (`docs/runbook.md` → "Preview deploy"), create an agent on the `claude-code` runtime with one of the environments as its default and a second agent on `anthropic-api` with the `delegate` tool, and ask the second to delegate to the first; open `/tasks/:id` on the parent and check the child's owner, objective, origin (agent · task · call), status and result.
- **M2 — several accounts on one machine (AC-02, AC-15).** Sign Claude Code into two or three accounts, one config dir each (`docs/multi-account.md`); `pnpm --filter @agentic/daemon start` reports them as separate environments with their doctor verdicts (`/machines/:id`). Run one task per environment and check each session's environment line and that `/machines/:id` shows every account unchanged. Open `/sessions/:id` of a Claude Code session and check the capability list says what the driver declared (`packages/runtimes/src/claude-code/capabilities.ts`) and that no control exists for an unsupported operation.
- **M3 — return on a phone (AC-06).** From a laptop, post to a chat on the preview deployment and close the tab mid-answer; on a phone, sign in (GitHub, `docs/runbook.md` → "Secrets and bindings"; the walk-through's dev login is preview-only) and open the same chat: the history, the finished answer and the task's status on `/tasks/:id` are there. The 400 px layout of every route is `pnpm --filter @agentic/web e2e:mobile` (Playwright, mock data; CI's `e2e` job).
- **M4 — push delivery (AC-08).** Once the Web Push channel is wired with VAPID keys (`docs/runbook.md` → "Not wired yet"): subscribe a phone from `/settings`, create a reminder one minute ahead on `/schedules`, stop every daemon and close every tab; the notification arrives and `/` shows it in "Needs you". Until then the central path is the scripted scenario only.
- **M5 — suspend and resume on a real Claude Code (OPS-05).** `docs/runbook.md` §7 step 8 on a machine installed with the one-line installer (§5.3): restart the service mid-turn, check the interruption names the restart, press Resume and check the Claude Code conversation continued (it remembers the task, the same session id on `/sessions/:id`) and the task completed; post again and check the idle session re-opened; repeat with `onInterrupt` "Resume automatically, once". Also check the service registration itself on each OS: `Get-ScheduledTask -TaskName agentic-daemon | Get-ScheduledTaskInfo`, `launchctl print gui/$(id -u)/agentic-daemon`, `systemctl --user status agentic-daemon` show the supervisor running, and a killed daemon process is back within the backoff (`state/supervisor.log`).
- **M6 — an update with a running session (OPS-03).** On a machine a release behind its channel (install it with `AGENTIC_VERSION=daemon-v<older>`, or set the channel to `latest` on an older build), start a long turn in one chat and leave another chat's session idle. **Update when idle** on the Machine page: check the card waits naming the running turn, a message posted meanwhile waits, the turn finishes, the phases run to "Updated to …", the waiting message is delivered in the same session and the idle chat's next message works. Then **Update now** (or **Roll back**) with a turn running: the confirm names it, the turn is interrupted with "was updated" and Resume continues it. `agentic-daemon update --check` on the machine agrees with the card.
- **M7 — a machine offline (OPS-04).** Mid-turn, take the machine off the network (or put it to sleep) for longer than the heartbeat window: the task reads "Waiting for <machine> (offline since …); fails after 24 h", not failed; reconnect and check the turn goes on or is offered Resume. `machine-lost` after 24 h is left to `offline.test.ts`.
- **M8 — a rolled-back update (OPS-05).** Start an update from the page and, as soon as the phase is `restarting`, cut the machine's network (or stop `pnpm dev` on a local platform) for more than 90 s so the new version never reaches the platform: `state/update-failed.json` says `not-ready`, `state/supervisor.log` shows `rolling back`, `<root>/daemon` is the old version again, and after reconnecting the card says the previous version was restored, with `machine.update-failed` in History and `update-failed` in the Inbox (`docs/runbook.md` §9 "A rollback happened").
- **Demo smokes.** `smoke:demo1` (`docs/runbook.md` → "Demo 1 smoke") walks sign-in → agent → config → chat → answer against a deployed Worker with the real model; run it before signing off M1–M3 on a fresh preview deploy.

## Known gaps the suite pins

- **#135** — on the routed local path the retrieved memories stop at the session record: `createSessionFactory` never hands `spec.memories` to the model agent, and `Routing.placeLocal` opens the session without the task's objective. `ac-09.test.ts` carries an `it.fails` case that flips when it lands.
- **#137** — `@sigx/actors` keeps the current host in one global; with several `ActorHost` objects in one isolate an ambient `actor()` hop can run another object's actor locally ("Cannot perform I/O on behalf of a different Durable Object"). `__tests__/acceptance/worker.ts` scopes each object's entry points with an `AsyncLocalStorage`; the production `ActorHost` does not yet.
- The Routing actor opens local sessions for `anthropic-api` only, so a remote A2A agent is not yet a runtime a task can be routed to (the `a2a` plugin kind, architecture §12); `ac-14.test.ts` opens the Session directly, as the router would.
